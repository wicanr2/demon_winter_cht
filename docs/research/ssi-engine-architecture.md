# SSI 兩段式啟動架構研究 — 從 Demon's Winter 反推 `.INT` 的真相

> 研究對象：《Demon's Winter》(Strategic Simulations, Inc., 1988/1989, DOS)
> 日期：2026-07-24 ｜ 狀態：核心結論已實證，跨作品比較待驗證
>
> 每一項結論都標明證據等級。`[實證]` = 有反組譯或位元組層級證據；
> `[推論]` = 有間接證據支持但未直接驗證；`[待驗證]` = 尚無證據，僅列出驗證方法。

---

## 摘要

SSI 在 1988 年前後的遊戲採用「小型 loader + 大型主程式」的兩段式啟動架構，
主程式的副檔名是 `.INT`。這個副檔名長期被理解為 interpreter，
容易讓人以為 SSI 用了類似 SCUMM / AGI / SCI 的位元組碼虛擬機。

**這個理解是錯的。** 反組譯證實：`.INT` 是一個結構完整的 MS-DOS MZ 可執行檔，
由 loader 透過 DOS 的 `EXEC` 服務（INT 21h, AH=4Bh）當作子程序載入執行。
它不是被直譯的位元組碼，而是原生 8086 機器碼。

這對逆向工程的路線選擇有直接影響：**不需要先找虛擬機、不需要還原指令集**，
主程式就是普通的 x86 二進位檔，可以直接反組譯。而遊戲的「資料驅動」層另有其物，
在資料檔那一側，且是宣告式表格而非可執行腳本。

## 1. 兩段式啟動架構

### 1.1 檔案角色 `[實證]`

| 檔案 | 大小 | 角色 |
|---|---|---|
| `DEMON.EXE` | 6,036 B | loader |
| `DEMON.INT` | 173,380 B | 引擎本體 |

兩者都是標準 MZ 格式。`DEMON.INT` 的 MZ header 解析結果：

| 欄位 | 值 | 意義 |
|---|---|---|
| pages / lastpage | 339 / 324 | image size = 173,380 B，**恰等於檔案大小 → 無 overlay** |
| relocations | 3,807 | 需要重定位的遠指標數量 |
| header paragraphs | 960 | code 起始於檔案 offset `0x3C00` |
| 進入點 CS:IP | `2037:0009` | |
| 初始 SS:SP | `21F0:A09A` | |

3,807 個 relocation entry 是關鍵指標：**位元組碼不需要重定位**。
只有原生機器碼中的段位址（far pointer）才需要載入時由 DOS 修正。
這個數字本身就排除了「`.INT` 是 bytecode 容器」的可能。

### 1.2 loader 如何啟動引擎 `[實證]`

`DEMON.EXE` 檔案位移 `0xAAC` 附近的反組譯：

```asm
mov  ax, ds
mov  es, ax
mov  ax, [bp+8]        ; ─┐
mov  [0x2b0], ax       ;  │
mov  [0x2b2], es       ;  │ 填 EXEC parameter block：
mov  ax, [bp+0Ah]      ;  │ 環境段、命令列指標、FCB 指標
mov  [0x2b4], ax       ;  │
mov  [0x2b6], es       ;  │
mov  ax, [bp+0Ch]      ;  │
mov  [0x2b8], ax       ;  │
mov  [0x2ba], es       ; ─┘
mov  ax, ds
mov  es, ax
mov  bx, 0x2ae         ; ES:BX → parameter block
mov  dx, [bp+4]        ; DS:DX → 程式路徑字串
mov  ax, 4B00h         ; AH=4Bh, AL=00h = Load and Execute
int  21h               ; ← DOS EXEC
mov  ss, cs:[0x85c]    ; EXEC 會破壞呼叫者的堆疊，回來後自行還原
mov  sp, cs:[0x85e]
pop  es
pop  ds
jae  ok                ; CF=1 表示 EXEC 失敗
mov  [0x2c6], ax       ; 保存錯誤碼
mov  ax, 0FFFFh
```

這是教科書式的 DOS EXEC 呼叫序列。搭配 `DEMON.EXE` 內的明碼字串 `\demon.int`
（位於檔案位移 `0x1704`），可以確定 loader 的最後一步就是把 `DEMON.INT` 當作
一個獨立的 DOS 程式執行。

### 1.3 loader 在 EXEC 之前做什麼 `[實證 + 推論]`

`DEMON.EXE` 內找到三處 `mov ah, 3Fh`（DOS 讀檔）`[實證]`，
以及三個明碼字串 `[實證]`：

| 檔案位移 | 字串 |
|---|---|
| `0x1704` | `\demon.int` |
| `0x1713` | `vagyok` |
| `0x1746` | `8087/80287 is required!` |

另有字串 `\dem_data\open.pie` 與 `\dem_data\open.pic`
（分別是 EGA 版與 CGA 版的開場畫面）。

由此推得 loader 的職責 `[推論]`：

1. **偵測 8087/80287 協同處理器**。主程式編譯時使用了硬體浮點指令，
   在沒有協同處理器的機器上會產生無效опcode 例外。這個檢查必須在主程式載入**之前**做，
   否則玩家看到的是當機而不是錯誤訊息。這解釋了為什麼檢查邏輯放在 loader 而非引擎裡。
2. **顯示開場畫面**。依顯示卡能力選擇 `OPEN.PIE`（EGA）或 `OPEN.PIC`（CGA）並載入顯示。
   1988 年的軟碟機讀取 173 KB 主程式需要可觀的時間，先放一張圖是當年的標準做法。
3. **EXEC 主程式**。

字串 `vagyok` 是匈牙利文的「我是」`[推論]`。位置緊接在 `\demon.int` 之後，
不像是功能性字串，較可能是開發者留下的簽名或標記。**此線索在 DOSBox 實跑後解開，見 §1.5。**

### 1.4 為什麼要拆成兩個檔 `[推論]`

拆分本身有成本：EXEC 之後 loader 仍留在記憶體中，在 640 KB real mode 的環境下
白白佔用 6 KB。SSI 願意付這個代價，合理的解釋是：

- **錯誤處理的時序需求**。8087 檢查必須先於主程式載入（見上）。
  這一條有直接證據支持，是最強的解釋。
- **磁片切換**。1988 年的發行媒介是軟碟，loader 與主程式可以分屬不同磁片，
  loader 顯示提示後再要求玩家換片。
- **loader 可能是 SSI 的共用元件**。若多款遊戲共用同一份 loader 邏輯
  （偵測硬體 → 顯示開場圖 → EXEC），拆分就有工程上的複用價值。
  這一條是本研究對 Gold Box 系列最有價值的假設，驗證方法見 §4。

### 1.5 移植鏈：Apple II 原版 → Novotrade（匈牙利）移植成 IBM PC 版 `[實證]`

DOSBox 實跑原版，開場畫面（`workplace/dosbox/shots/01-ega-opening.png`）底部印著：

```
Adapted for the IBM by Judit Burczolich and Laszlo Fazekas
NOVOTRADE          STRATEGIC SIMULATIONS INC.
```

這一張畫面把先前三條分散的線索接成一條完整的移植鏈：

| 線索 | 出處 | 指向 |
|---|---|---|
| `vagyok`（匈牙利文「我是」） | `DEMON.EXE` 字串 `[實證]` | 移植者的母語簽名 |
| Applesoft BASIC 殘留（Town Maker、`PEEK(-16384)`） | `TOWN*.DAT` 未初始化緩衝區 `[實證]`（§2.5） | 原始製作平台是 Apple II |
| `Adapted for the IBM by … NOVOTRADE` | 開場畫面 `[實證]` | IBM PC 版由 Novotrade 移植 |

**Novotrade 是匈牙利布達佩斯的遊戲公司**，`Judit Burczolich`、`Laszlo Fazekas` 是匈牙利人名，
與 `vagyok` 的匈牙利文完全吻合。因此結論是：

> **Demon's Winter 的原始開發平台是 Apple II（SSI 本部），IBM PC / DOS 版是外包給匈牙利的
> Novotrade 移植的。** `vagyok` 是 Novotrade 程式設計師留在 loader 裡的簽名，
> `TOWN*.DAT` 裡的 Applesoft BASIC 殘留則是資料檔從 Apple II 版原封搬移的證據。

這條移植鏈也修正了 §1.4 的一個假設：DOS 版的 loader **不一定是 SSI 的共用元件**，
也可能是 Novotrade 為這次移植另寫的。判斷 loader 出自誰手，要比對其他 SSI 自製 DOS 版
（非 Novotrade 移植者）的 loader，這併入 §4 對 Gold Box 的檢查。

> **對 Gold Box 的意義**：若某款 SSI 遊戲的 DOS 版也帶有非英語的開發者簽名或他廠 logo，
> 就要先確認它是 SSI 自製還是外包移植——兩者的技術血緣不同，
> 從一款外包移植版反推出的結論不能直接套到 SSI 自製版上。這是 §4 檢查時的一個陷阱。

## 2. 資料層：宣告式表格，不是腳本

既然 `.INT` 不是虛擬機，那這款遊戲「資料驅動」的部分在哪裡？答案在 `DEM_DATA/` 目錄。

### 2.1 事件表 `[實證]`

`DATA1.TXT` .. `DATA5.TXT` 是地城事件表，每筆記錄的結構為：

```
敘述文字 \0 [遭遇數量 \0 怪物ID×N \0 (255 終止符) \0 trailer(0~3 個數字)]
```

- 分隔符是 NUL（`0x00`），不是換行
- **數字以 ASCII 十進位文字表示**，不是二進位。`"255"` 是三個位元組 `32 35 35`
- 怪物 ID 是 `MONSTER.DAT` 的 0-based 索引（該檔共 99 隻怪物）

驗證方式是把怪物 ID 反查 `MONSTER.DAT` 的名稱，與同一筆記錄的敘述文字比對：

| 事件敘述文字 | 解出的怪物 ID | 反查名稱 |
|---|---|---|
| 「四隻狗頭人的帳篷」 | `[26, 26, 26, 26]` | Kobold ×4 |
| 「Uffuspgot 狗頭人隊長的帳篷」 | `[26, 26, 85, 2, 2]` | Kobold ×2 + **Uffuspgot** + Orc ×2 |
| 「cave bear 的巢穴」 | `[67]` | **Cave bear** ×1 |

文字敘述、怪物種類、隻數三者完全吻合。劇情角色 Xeres (91)、Remondadin (93)、
Jesric (96)、Eregore (97)、Guardian (98) 也都對得上攻略記載的出場場景。

### 2.2 這個設計的意義

事件表裡**沒有 opcode、沒有條件判斷、沒有跳轉指令**。它只回答兩個問題：
這個房間顯示什麼文字、這裡有哪些怪。所有的控制流——房間之間怎麼連、
事件在什麼條件下觸發、狀態怎麼推進——全部寫死在 `DEMON.INT` 的機器碼裡。

這與 SCUMM / AGI / SCI 的設計哲學相反。那些引擎把流程邏輯編譯成位元組碼放進資料檔，
引擎只提供直譯器；SSI 這一代則是把流程寫在程式碼裡，資料檔只提供內容素材。

對重製工作的影響是雙面的：

- **好處**：不必還原指令集與直譯器語意，資料格式相對單純。
- **代價**：流程邏輯沒有現成資料可抄，必須全部從反組譯裡挖出來。
  這也是本專案風險清單上最主要的一項。

### 2.3 其他已確認的資料格式 `[實證]`

| 檔案 | 結論 |
|---|---|
| `MONSTER.DAT` | 99 隻怪物。**純 ASCII 文字、NUL 分隔**，每筆為名稱 + 11 個數值欄位。已驗證 6 個欄位（速度、力量、技巧、攻擊類型/sprite 索引），其中 sprite 索引的證據很強：四種熊共用同一值、各種龍共用另一值 |
| `ITEMS.DAT` | 30 件道具（8 武器 + 5 護甲 + 其他），同樣是 ASCII + NUL 分隔，每筆 7 個數值欄位。武器與護甲的**排列順序與手冊完全一致**，是很強的對位錨點 |
| `TEMPLAT1/2/4/5.DAT` | **不是**角色範本。`DEMON.INT` 中 `TEMPLAT%d.DAT` 這個格式字串的位置，緊鄰「發光球體基座」的獨特道具敘述文字，因此是**特定地點的特殊道具資料**。這也解釋了 `TEMPLAT3.DAT` 為何不存在——這類場景大概只有四處 |
| `FILES.DTT` | 主字串池，501 個 NUL-terminated 字串。種族 (5)、技能 (32)、武器 (8)、護甲 (5)、法術、幻術召喚生物 (12) 全部對得上遊戲內清單 |
| `FILES.DAT` | **不是**資源索引（原假設已否證）。無檔名字串；與 `FILES.DTT` 位移做交集，命中率僅隨機基準的 2.55 倍。實際是數張互不相關的小型二進位表串接 |
| `T/T2C/T2D/EREGORE/WIN/TOWN.TXT` | 純文字表，無數字欄位。`*` / `**` / `***` 是段落結束控制標記 |
| `TOWN1..25.DAT` | 每筆記錄 17 bytes（錨點 `0a 01 01 XX` 間距精確 `0x11`），512 = 30 × 17 + 2 |
| `MAP1/3/5.MAP` | 4,097 B = 1 + 64 × 64，推測為 1 byte header + tile 陣列 |
| `nSS.DAT` / `ALL_SS.DAT` | `ALL_SS` = 5 × 512 B。結構為 3-byte 記錄 (座標, 座標, 屬性)，稀疏填充。語意未定 |

### 2.4 顯示模式的雙軌素材 `[實證 + 推論]`

CGA 與 EGA 素材成對存在，副檔名以最後一個字母區分（`.PIC`/`.PIE`、`.SHP`/`.SHE`、`.FNT`/`.FNE`）。
兩者檔案大小呈**精確 3.5 倍**對應 `[實證]`：

| CGA | EGA | 比例 |
|---|---|---|
| 1,728 | 6,048 | 3.5 |
| 2,048 | 7,168 | 3.5 |
| 2,816 | 9,856 | 3.5 |
| 6,528 | 22,848 | 3.5 |
| 15,360 | 53,760 | 3.5 |

3.5 可分解為 `2 × 1.75` `[推論]`：色深從 2bpp（CGA 四色）增為 4bpp（EGA 十六色）是 2 倍，
掃描線從 200 增為 350 是 1.75 倍。據此推測 EGA 版素材為 **320 × 350、four-plane** 佈局。

`.PIC` → `.PIE` 是 5,184 → 18,160，等於 3.5 倍再加 16 bytes，
多出的部分推測是 16 色調色盤 `[推論]`。

字型檔的數字關係與此假設一致 `[推論]`：`ASC.FNT` 為 3,073 B（1 + 3,072），
`ASC.FNE` / `GOT.FNE` 為 2,688 B。若 CGA 字型為 2bpp 8×12（24 B/字）、
EGA 字型為 1bpp 8×21（21 B/字），字高 12 → 21 恰為 1.75 倍，與掃描線推論吻合。
兩者皆為 128 字：128 × 24 = 3,072、128 × 21 = 2,688。此假設尚未以實際解碼驗證。

> **⚠ 2026-07-25 實作解碼器後的修正**：上述以檔案大小推出的佈局推論，**只有一部分成立**。
>
> | 推論 | 實測結果 |
> |---|---|
> | CGA `.PIC` 佈局 | **成立**，但細節與直覺相反：`OPEN.PIC` 是 **linear** 不是硬體 odd/even 交錯 |
> | CGA `.SHP` sprite frame | 猜過 32×16 與 16×32，**都錯**。實際是 **16×16、64 B/frame** |
> | EGA `.PIE` 為 4-plane、多出 16 B 是調色盤 | **成立**（用標準 EGA 調色盤會失真，反證內嵌表為真）；檔內高度 ×1.75 也成立。但顯示時還會再水平加倍（144×252 → 288×252）|
> | 「320 × 350」這個具體尺寸 | **未證實**。畫面模式已確認是 EGA 640×350（`217b:0662` 清 28,000 B），但素材檔各有自己的尺寸 |
> | EGA `.SHE` 精靈圖同樣是 four-plane | **成立**。檔內 frame **16×28、224 B**，載入時水平加倍成 32×28、448 B |
> | 字型 `.FNT`/`.FNE` 的 8×12 / 8×21 推論 | **不成立**。實際是 CGA 8×8 2bpp（16 B）、EGA 16×14 1bpp（28 B），見 `docs/re/17` |
>
> **方法論教訓**：檔案大小的算術關係只約束「總位元數」，不約束佈局方向，
> 也不約束切分單位。sprite frame 尺寸這一項本專案連續猜錯兩輪，
> 每一輪的錯誤版本都整除、都通過全部自動測試。
> 定案靠的是**遊戲初始化時自己宣告的常數**（`[0x5226]`：EGA 224、CGA 64）。
> 算術自洽是必要條件，肉眼比對原版才是充分條件。詳見 `docs/formats/graphics.md`。

## 2.5 開發工具鏈的殘留：SSI 的 Town Maker `[實證]`

分析 `TOWN*.DAT` 時發現了一件與遊戲執行無關、但對理解 SSI 工程實務極有價值的東西：
**25 個城鎮檔中有 14 個含有未初始化緩衝區的殘留資料，內容是 SSI 內部關卡編輯器的片段。**

### 發現的字串

```
TOWN7.DAT :  "DEMON'S WINTER TOWN MAKE[R]"
             "TOWN # ( FOR NEW)";T
             "1) LI[ST]  2) ADD  3) ED[IT]"
             "CHAR GEN."
             PLAY.OBJ0",20736
TOWN5/6.DAT: "SELECT ONE ?"   "MENU    "   " 3.3  COP[YRIGHT]"
TOWN1..24   : "ELRIC     "  （後接符合五項屬性的數值區塊）
```

### 這些殘留是 Applesoft BASIC

`TOWN5.DAT` 位移 `0x100` 起的位元組不是資料，是 **tokenized Applesoft BASIC 程式碼**。
以 Applesoft 的 token 表解碼（`0xBA`=PRINT、`0xB9`=POKE、`0xAD`=IF、`0xE2`=PEEK、
`0xC9`=負號、`0xD1`=`<`、`0xC4`=THEN、`0xD0`=`=`、`0xCE`=OR、`0xAB`=GOTO）：

```basic
PRINT A$ : NORMAL
K = PEEK(-16384) : IF K < 128 THEN ...
POKE -16368,0 : IF K = 161 OR K = 162 THEN ... GOTO "MENU"
IF K < 177 OR (K > 1...
```

`PEEK(-16384)` 讀取 `$C000`（Apple II 鍵盤資料暫存器），
`POKE -16368,0` 寫入 `$C010`（清除鍵盤 strobe）。
這兩行合起來是 Apple II 上讀取單一按鍵的標準慣用寫法，不會出現在其他平台。
搭配 `" 3.3  COP"`（Apple DOS 3.3 的版權字串）與 `PLAY.OBJ0",20736`
（`BLOAD "PLAY.OBJ",A20736` 的殘骸），平台歸屬沒有疑義。

### 推論 `[推論]`

1. **SSI 的關卡編輯器「Demon's Winter Town Maker」是用 Applesoft BASIC 寫的，跑在 Apple II 上。**
   選單結構（`1) LIST  2) ADD  3) EDIT`、`TOWN # ( FOR NEW)`）指向一個互動式的城鎮編輯工具。
   同時存在的 `"CHAR GEN."` 暗示還有一支獨立的角色生成工具。
2. **這些殘留是寫檔時未清空緩衝區造成的洩漏。** 編輯器把 512 bytes 的緩衝區寫出成
   `TOWN*.DAT`，但實際城鎮資料只填滿了前面一部分，緩衝區尾端還留著上一次使用時的內容——
   也就是編輯器自己的程式碼與變數。
3. **DOS 版的城鎮資料是從 Apple II 版直接搬移的。** 這是最有意思的一點：
   Apple II 才有的 BASIC 程式碼殘留出現在 DOS 版的資料檔裡，
   表示 SSI 移植時把資料檔原封不動搬過去，連垃圾資料都一起帶走了。
   `"ELRIC     "` 與其後符合五項屬性格式的數值區塊，同理是角色編輯器留下的測試角色。

### 為什麼這件事重要

- **對本專案**：這些殘留是垃圾資料，重製引擎時不必解析，但**必須知道它們是垃圾**——
  否則會浪費大量時間試圖為這些位元組找出「遊戲意義」。這正是資料格式逆向常見的陷阱。
- **對 SSI 研究**：這是直接證據，證明 SSI 在 1988 年前後的開發流程以 Apple II 為主要製作平台，
  DOS 版是移植產物。若 Gold Box 系列的資料檔中也找得到類似殘留，
  就能用同樣的方法反推該系列的製作平台與工具鏈。這是 §4 建議的檢查項之一。
- **對數位保存**：一款商業遊戲的資料檔裡意外封存了開發工具的程式碼片段。
  原始工具幾乎確定已經佚失，這些殘片可能是它僅存的痕跡。

## 3. 方法論：這些結論是怎麼得到的

記錄可複用的做法，供後續研究其他 SSI 作品時參考。

### 3.1 先問「這個檔為什麼存在」

面對 loader + 主程式的組合，最有價值的第一個問題不是「主程式怎麼運作」，
而是「為什麼需要 loader」。這個問題的答案（DOS EXEC）一刀切開了整條路線：
確認了主程式是普通 exe，後續就不必浪費時間找虛擬機。

### 3.2 用位元組模式定位，用反組譯確認

搜尋 `B8 00 4B`（`mov ax,4B00h`）可以快速定位候選點，但**單一位元組模式可能是巧合的資料**。
必須反組譯上下文，確認它前面有 parameter block 的填寫、後面有 `int 21h` 與堆疊還原，
才能斷定是真的 EXEC 呼叫。跳過這一步就是猜測。

### 3.3 用檔案大小的算術關係推格式

3.5 倍、`4097 = 1 + 64²`、`512 = 30 × 17 + 2`、`2560 = 5 × 512`——
這些關係都能在寫任何解碼器之前就大幅縮小假設空間。老遊戲的資料檔多半沒有壓縮、
沒有 header magic，檔案大小往往是最先能拿到的線索。

**但要知道它的界線：同樣的 byte 數，不同的方向。**
算術只約束「總位元數」，完全不約束佈局方向。本專案在這件事上踩過四次，全部是同一類錯誤：

| 錯誤方向 | 正確方向 | 怎麼被抓到 |
|---|---|---|
| CGA sprite 32×16 | 16×32（後來發現這也錯，見下） | 肉眼看 PNG（byte 數兩者完全相同） |
| `OPEN.PIC` 硬體 odd/even 交錯 | **linear** | 肉眼比對 DOSBox 截圖 |
| `SUM.MAP` RLE 用 row-major 游標 | **column-major**（`cursor += 64`，越界 `-4095` 換欄） | ASCII 算繪：row-major 版出現貫穿全圖的垂直色帶——地圖裡自然的**水平** RLE 長條被鋪成**垂直** |
| EGA `.SHE` 沿用 `.PIE` 的 plane 佈局（16×56） | 列內 plane 分塊 | 八種假設輸出全是雜訊；改讀 blit 常式的迴圈次數才解開 |
| sprite frame 尺寸 CGA 16×32／EGA 32×28 | **CGA 16×16、EGA 16×28** | 讀視訊初始化裡遊戲自己宣告的 `[0x5226]`（EGA `0xe0`=224、CGA `0x40`=64），並用它乘出各檔大小 |

**錯誤版本幾乎都能通過所有自動化測試**（大小對、值域對、格數對），
最後兩次畫出來還「像那麼回事」——`.SHE` 的 32×28 版把兩個相鄰 frame
的左右半邊錯位疊成 2×2，當時被合理化成「美術打包慣例」。
只有把產物 dump 出來、跟原版擺在一起看，並且**要求每個 frame 自成一體**，
才分得出來。

最後一次的額外教訓：**靜態溯源要追到資料的來源端，不能停在消費端。**
`.SHE` 的 blit 常式讀的是已經被載入器水平加倍過的緩衝區，
只讀 blit 端就會把記憶體 stride 當成磁碟格式。

這條教訓直接決定了本專案的驗收規則：**視覺產物一律肉眼比對原版，
不接受「解碼器沒回傳 error」當通過**。

### 3.4 交叉驗證勝過自圓其說

事件表的結論之所以可信，不是因為「這樣解釋說得通」，
而是因為怪物 ID 反查名稱後，與敘述文字、隻數、以及攻略記載的場景三方吻合。
一個能自圓其說的解析器很容易寫出來；能對上外部事實的才算破解。

### 3.5 字串在程式碼中的「位置」會洩漏它的用途

`TEMPLAT%d.DAT` 原本被假設為角色範本檔（檔名如此暗示）。真正解開它的線索不是檔案內容，
而是**這個格式字串在 `DEMON.INT` 裡的鄰居**——它緊挨著「發光球體基座」的獨特道具敘述文字。
編譯器通常把同一段程式碼用到的字串排在一起，所以字串的物理位置本身就是弱型別的呼叫脈絡。

這個技巧成本極低（一次 grep 加上前後文檢視），在自動分析進不了主邏輯時特別有用。

### 3.6 願意否證自己的假設

`FILES.DAT` 原本被假設為資源索引（檔名如此暗示）。實測後以量化方式否證：
無檔名字串，且與字串池位移的交集命中率只有隨機基準的 2.55 倍。
**不得憑檔名臆測內容**是本專案的明文規則，這次驗證正是這條規則的實例。

## 4. 對 Gold Box 系列的可遷移性 `[待驗證]`

SSI 的 Gold Box 系列（*Pool of Radiance*、*Curse of the Azure Bonds*、
*Champions of Krynn* 等 AD&D 授權作品）與本作是同一家公司、相近年代的產物。
本研究的結論是否適用於該系列，**目前沒有任何證據**，以下純屬待驗證的假設。

需要說明的是：Demon's Winter 是 *Shard of Spring* 的續作，屬於 SSI 的自有世界觀作品線，
與 Gold Box 的 AD&D 授權作品線是不同的產品線。兩者是否共用底層技術，不能從公司相同就推定。

### 建議的驗證順序（成本由低到高）

1. **檢查檔案組成**。Gold Box 遊戲目錄中是否存在「小型 `.EXE` + 大型非標準副檔名主檔」的配對？
   若有，量測主檔的 MZ header：relocation 數量是否也在數千量級（原生碼的指標）？
2. **搜尋 EXEC 呼叫**。在 loader 中搜尋 `B8 00 4B` / `B4 4B`，
   依 §3.2 的程序反組譯確認。若命中，兩段式架構的假設即成立。
3. **比對 loader 的職責**。Gold Box 時代的目標機器已較普及 EGA，
   協同處理器檢查是否仍存在？開場畫面載入的模式是否相同？
4. **檢查資料層設計哲學**。Gold Box 的資料檔（已知社群多有研究）
   是宣告式表格，還是包含控制流的腳本？若同為前者，
   本研究「流程邏輯全在機器碼裡」的結論可能同樣適用，
   意味著 Gold Box 的重製工作重心同樣落在反組譯而非格式破解。

### 若假設成立的價值

「兩段式啟動 + 原生碼主程式 + 宣告式資料表」若被證實是 SSI 這個時期的共通模式，
那麼針對任一款 SSI 作品建立的反組譯環境設定、資料格式推導手法、
甚至部分共用函式庫的識別特徵，都可能在系列間遷移。
這比逐款從零開始省下可觀的工作量。

**在取得 Gold Box 的實際檔案並完成上述檢查之前，本節的一切都只是假設。**

import struct
d = open('DEMON.INT', 'rb').read()
lastpage, pages, relocs, hdrpara = struct.unpack('<HHHH', d[2:10])
ip, cs = struct.unpack('<HH', d[20:24])
image_size = (pages - 1) * 512 + (lastpage or 512)
# → pages=339 lastpage=324 relocs=3807 hdrpara=960
# → image_size == len(d) == 173380（無 overlay）
```

objdump -D -b binary -m i8086 \

```
