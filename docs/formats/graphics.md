# EGA / CGA 美術素材格式（2026-07-25）

驗證方法：依假設寫解碼器（`internal/assets/gfx/`）→ 輸出 PNG（`workplace/dump/gfx/`，
不入版控）→ 肉眼比對 DOSBox 原版截圖（`workplace/dosbox/shots/`）。這份文件只記錄
**已經拿截圖或跨格式一致性驗證過**的結論，卡住的部分誠實列出試過哪些假設。

---

## 1. 3.5 倍假設：部分成立，部分推翻

PLAN.md 原假設「CGA→EGA 檔案大小精確 3.5 倍 = 2bpp→4bpp(×2) × 200→350 掃描線(×1.75)」。

結論：**分解方式對，但套用對象要分兩類**：

| 素材類別 | 3.5× 規律 | 驗證狀態 |
|---|---|---|
| 全螢幕圖 `OPEN.PIC`(16,000B) | 不適用(`OPEN.PIE` 是 102,160B，見 §5) | **已驗證**只有 CGA 版適用簡單模型 |
| 場景/人像框 `PIC*.PIC`/`PRIEST.PIC` 等(5,184B → 18,160B) | **成立** | **已驗證**(肉眼比對，見 §3) |
| 精靈圖 `*.SHP`/`*.SHE`(1,728~15,360B → 6,048~53,760B) | **成立** | **已驗證**(指令級常數 + 肉眼比對，見 §4) |
| `OPEN.PIE`(102,160B) | **不成立**，非 3.5× 整數關係 | **已解**（不靠 3.5× 規律，靠窮舉 stride），見 §5 |

`3.5 = 2bpp→4bpp(×2) × 200→350掃描線(×1.75)` 這個分解本身是對的。
它在**檔案層**的表現是：色深 ×2、高度 ×1.75，寬度不變（檔案存的是半寬圖）。

**顯示層則多一次寬度加倍**。EGA 素材一律「檔案存半寬、顯示時寬度 ×2、
高度 ×1.75」，差別只在加倍發生的時機：

| 素材 | 加倍時機 | 函式 |
|---|---|---|
| `.SHE` 精靈圖 | **載入時**就地展開緩衝區 | `FUN_1d9f_0a8b` → `FUN_217b_0adf` |
| `.PIE` 全螢幕圖/人像框 | **blit 時**逐列展開 | `FUN_217b_0884` → `FUN_217b_0a95` |

所以「檔案解出來的寬度」跟「畫面上看到的寬度」差兩倍，這一點在 §4 上讓本專案
連續猜錯兩輪 frame 尺寸。

## 2. CGA 格式：全部已驗證

### 2.1 全螢幕圖 `.PIC`（`OPEN.PIC` 16,000B = 320×200÷4）

**已驗證**：320×200，2bpp（4 色），**線性排列**（不是 CGA 硬體 framebuffer
的偶/奇掃描線交錯！），每列 `width/4` bytes，每 byte 4 個像素、MSB-first。
調色盤是 CGA palette 1 高亮度：`{黑, 亮青, 亮洋紅, 白}`。

**肉眼比對**：`workplace/dump/gfx/open-pic-cga-linear.png` 與
`workplace/dosbox/shots/05-cga-hang-open-pic.png` **完全吻合**——魔鬼臉孔、
"DEMON'S WINTER" 標題字樣、"NOVOTRADE"／"STRATEGIC SIMULATIONS INC" 商標、
下方製作人員名單全部清楚對上。

**踩過的雷**：一開始比照 IBM CGA 硬體 0xB8000 framebuffer 的標準佈局（偶數掃描線
存前 8000B、奇數掃描線存後 8000B，這是 CGA 硬體因頻寬限制而做的交錯），寫出
`DecodeCGAPlanar320`，結果整張圖花掉、看不出圖案（見
`workplace/dump/gfx/open-pic-cga-interleaved-control.png` 對照組）。改成單純
線性由上到下排列（`DecodeCGALinear320`）才對上——**磁碟檔案格式不等於硬體
framebuffer 格式**，遊戲載入時才會做交錯（或者根本不需要，因為 CGA mode
4/5 也可以透過 BIOS/驅動把線性資料重排進顯存，檔案不必事先交錯）。這是本專案
第一個「數學算對但畫面不對，肉眼比對抓出來」的案例。

### 2.2 場景/人像框 `.PIC`（`PIC1~6.PIC`／`PRIEST.PIC`／`SHAMEN.PIC`／`THANATOS.PIC`，5,184B）

**已驗證**：144×144，同 §2.1 的線性排列、2bpp、CGA palette 1。
`5,184B = 144/4 bytes/row × 144 rows`，整除。

**肉眼比對**：`workplace/dump/gfx/cga-portrait-PIC1.PIC.png`、
`cga-portrait-THANATOS.PIC.png` 等都解出清楚的人形圖案（THANATOS 是披風骷髏
持鐮刀的形象），且跟同一角色的 EGA 版（見 §3）姿勢、輪廓完全一致——沒有 DOSBox
截圖直接對到這幾張單獨畫面，但**兩種獨立編碼(CGA/EGA)解出同一個形狀**是很強的
交叉驗證證據。

### 2.3 精靈圖 `.SHP`

**已驗證**：每個 sprite frame 是 **16 寬 × 16 高、64 bytes**，2bpp、
線性排列（同 §2.1），每列 `16/4 = 4` bytes。**六個檔一律如此，`CYPHER.SHP`
沒有特例。**

指令級證據：視訊模式初始化的 CGA 分支寫入

```
1d9f:018d  MOV word ptr [0x5226],0x40   ; 64 = 檔內 frame 大小
1d9f:01aa  MOV AX,[0x5226]
1d9f:01b5  MOV [0x521a],AX              ; 64（CGA 不加倍，見 §4）
```

同一段接著用 `[0x5226]` 直接乘出各素材檔的大小，等於遊戲親口說出檔案格式：

```
1d9f:01d0  [0x5226] × 0x66 (102) = 6,528  → DEMON.SHP / WINTER.SHP
1d9f:01ec  [0x5226] × 0x1b (27)  = 1,728  → CYPHER.SHP
```

檔案裡沒有 frame 數欄位，用「檔案長度 ÷ 64」反推：

| 檔案 | 大小(B) | frame 數 |
|---|---|---|
| `COMBAT.SHP` | 2,816 | 44 |
| `SHIP.SHP` | 2,048 | 32 |
| `DEMON.SHP` | 6,528 | 102 |
| `WINTER.SHP` | 6,528 | 102 |
| `MONSTER.SHP` | 15,360 | 240 |
| `CYPHER.SHP` | 1,728 | 27 |

**肉眼驗收**：依 16×16 解，每個 frame 都是一個完整自成一體的圖形——
`MONSTER.SHP` 是武士／骷髏／各種怪物，`CYPHER.SHP` 是一排幾何符文圖示
（對應 `DEMON.INT` 的字串 "God Runes / Fire Runes / Metal Runes..."）。
圖案、順序、空白格位置與 EGA 版逐格一致（見 §4）。

**踩過的雷（兩輪）**：

1. 第一輪猜 32 寬 × 16 高，byte 數學完全對得上（總 pixel 數相同），輸出全花。
2. 第二輪改成 16 寬 × 32 高，圖案看得出來了，於是被標成「已驗證」——
   但那其實是**把上下兩個 frame 疊在一格裡**。當時的觀察「每格裡有兩個
   上下堆疊的小武士」就是徵狀，卻被誤讀成美術打包慣例。

`128` 與 `64` 兩種 frame 大小都能整除全部六個檔（因為 frame 數都是偶數，
`CYPHER` 則被當成「較窄的特例」硬湊過去），**算術完全分不出來**。
定案靠的是遊戲自己宣告的 `[0x5226] = 0x40`。

## 3. EGA 全螢幕圖／人像框格式：已驗證

### 3.1 佈局

> ⚠ **2026-07-26 訂正兩點**：
> 1. **調色盤值是 6 bit，不是 4 bit。** 先前的解碼把值 `&0x0f` 之後拿去索引
>    16 色標準色盤，等於把高三位（次要色分量）整組丟掉。最好認的症狀是
>    **棕色變紅色**（EGA 棕色的暫存器值是 `0x14`，遮成 4 bit 變 `0x04` = 紅）。
>    所有 `.PIE` 美術的膚色與土色都因此整片偏成洋紅。
>    正解見 `gfx.EGAColor`：`R = 主R×170 + 次r×85`，GB 同理。
>    佐證：標準 EGA 預設調色盤的 16 個暫存器值換算後**恰好等於**標準 16 色表
>    （寫成 `TestEGAColor_MatchesStandardPalette`）。
>    ⚠ 連帶作廢下方「套用檔內調色盤後色調自然（紅棕色惡魔膚色）」那句 ——
>    那是**用錯誤解碼看到的顏色**。正確解出來 `PIC1.PIE` 是黃橘色調的火焰惡魔。
> 2. **同副檔名兩種 plane 佈局**：人像框是 plane-major（四個 plane 各自
>    連續一大塊），開場標題 `OPEN.PIE` 是每列 4 個 plane 各一小塊。
>    拿其中一種去解另一種會得到雜訊，而且看起來像「尺寸猜錯」。

**已驗證**：`.PIE` 檔開頭 **16 bytes 是調色盤索引表**（第 i byte = 邏輯色 i
對應到哪個實體 EGA 16 色代碼），之後是 **4-plane、sequential（plane 0 整塊
接著 plane 1 整塊...）、MSB-first** 的點陣資料。場景/人像框（`PIC1~6.PIE`／
`PRIEST.PIE`／`SHAMEN.PIE`／`THANATOS.PIE`，18,160B）解碼尺寸為
**144×252**（144×1.75，寬度不變、高度拉 1.75 倍）：

```
18,160 B = 16(調色盤) + 18,144(點陣資料)
18,144 = 144/8 bytes/row × 252 rows × 4 planes
       = 18 × 252 × 4
```

**但畫到畫面上是 288×252**（已驗證）：`FUN_217b_0884` 在 blit 時每列呼叫
`FUN_217b_0a95` 九次，每次吃 2 個來源 byte 吐出 4 個 byte，
18 bytes/列 → 36 bytes/列，等於水平像素加倍。
檔案裡存的是半寬圖，144 是**檔案解碼尺寸**，不是顯示尺寸。
這跟 `.SHE` 是同一條規則，只是加倍時機不同（見 §1、§4）。

### 3.2 調色盤

**已驗證是真的調色盤，不是佔位資料**：同一張圖分別用「內嵌 16 bytes 索引表」
與「標準 16 色盤（identity mapping）」解碼，兩者色彩明顯不同——內嵌調色盤版本
色調自然（如 `PIC1.PIE` 呈現正常的紅棕色惡魔膚色），標準色盤版本則偏向不自然
的高飽和撞色。詳見 `ParsePIEPalette`。

### 3.3 肉眼比對結果

| EGA 檔 | 輸出 | 比對結果 |
|---|---|---|
| `PIC1.PIE` | `workplace/dump/gfx/ega-portrait-PIC1.PIE-withpal.png` | 惡魔持鐮刀形象，姿勢與 `cga-portrait-PIC1.PIC.png`(CGA 版)一致，**清楚無雜訊** |
| `THANATOS.PIE` | `ega-portrait-THANATOS.PIE-withpal.png` | 披風骷髏、鐮刀、背景滿月，與 `cga-portrait-THANATOS.PIC.png` 輪廓一致，有少量垂直條紋殘留雜訊但主體清楚 |
| `PRIEST.PIE` | `ega-portrait-PRIEST.PIE-withpal.png` | 兜帽僧侶持蠟燭，**乾淨無雜訊，是目前最清楚的一張** |

沒有 DOSBox 截圖直接顯示這幾張單獨畫面（這些是劇情/道具彈出圖，目前擷取的截圖
只有開場、主選單、地城畫面），但**跨格式一致性**（CGA/EGA 兩份獨立編碼解出
同一主體、同一姿勢）加上**內嵌調色盤讓色彩變得合理**兩個獨立證據，足以判定
**已驗證**，不是巧合湊出來的雜訊圖案。

## 4. EGA 精靈圖 `.SHE`：**已解**（frame 尺寸於 2026-07-25 二度訂正）

> **這一節被改寫過兩次。**
> 第一版說「格式未解」（八種佈局假設全是雜訊）；
> 第二版說「32×28、448 B/frame，已驗證」——**plane 佈局對，frame 尺寸錯**。
> 現行結論是 **檔內 16×28、224 B/frame**，448 是**載入加倍後**記憶體裡的大小。
> 已推翻的舊敘述一律刪除，只保留 §4.3 的探索紀錄當方法論教材。

### 4.0 結論（已驗證）

| 項目 | 檔案內（磁碟） | 記憶體內（載入加倍後） |
|---|---|---|
| frame 尺寸 | **16 × 28** px | 32 × 28 px |
| frame 大小 | **224 bytes** | 448 bytes（`0x1c0`）|
| 每列 bytes | 8（4 個 plane 各 2 B）| 16（4 個 plane 各 4 B）|
| 位元佈局 | `offset = row × 8 + plane × 2 + col`，`col ∈ [0,2)` | `offset = row × 16 + plane × 4 + col`，`col ∈ [0,4)` |
| 色深 | 4-plane EGA，MSB-first | 同左 |
| 壓縮 | **無** | — |

**六個檔全部一致，`CYPHER.SHE` 沒有特例。**它先前之所以被當成「224 B 的特殊檔」，
只是因為它的 frame 數 27 是奇數、無法被（錯誤的）448 整除。

目標畫面是 EGA 640×350 十六色（`FUN_217b_0662` 清除恰好 28,000 B = 640×350÷8）。

### 4.1 指令級證據一：遊戲自己宣告 frame 大小

視訊模式初始化在 EGA 分支寫入：

```
1d9f:00bf  MOV word ptr [0x5226],0xe0   ; 224 = 檔案內 frame 大小
1d9f:00fa  MOV AX,[0x5226]
1d9f:0101  SHL AX,0x1
1d9f:0109  MOV [0x521a],AX              ; 448 = 0x1c0 = 記憶體內 frame 大小
```

CGA 分支寫的是 `0x40`(64)，且**不加倍**（`[0x521a]` 直接等於 64，見 §2.3）。
`[0x5226]`（檔內 frame 大小）與 `[0x521a]`（記憶體內 frame 大小）是兩個不同的量，
兩者在 EGA 下差兩倍——**先前的錯誤就是把後者當成檔案格式**。

同一段接著用 `[0x5226]` 乘出各素材檔的大小，兩種模式各自吻合磁碟上的實際檔案大小：

| 乘法 | EGA（`[0x5226]`=224）| CGA（`[0x5226]`=64）|
|---|---|---|
| `× 0x66` (102) | 22,848 = `DEMON.SHE`/`WINTER.SHE` | 6,528 = `DEMON.SHP`/`WINTER.SHP` |
| `× 0x1b` (27) | 6,048 = `CYPHER.SHE` | 1,728 = `CYPHER.SHP` |

（相關指令在 `workplace/ghidra/export/disassembly.asm` 約 19682–19775 行；
`1d9f:01d0` 起是 CGA 分支的乘法，`1d9f:01ec` 起是兩個分支共用的尾段。）

### 4.2 指令級證據二：載入時的水平像素加倍

`0x1c0` = 448 這個常數沒有錯，但它是**記憶體緩衝區**的 frame stride，不是磁碟格式。
載入鏈：

- **`FUN_1d9f_0a8b`**（素材載入器，`decompiled_all.c` 約 8644 行起）：
  EGA 模式下把副檔名末字元改掉（`.SHP`→`.SHE`、`.PIC`→`.PIE`、`.FNT`→`.FNE`）；
  讀檔後比對副檔名是不是 `shE`/`SHE`，是就呼叫 `FUN_217b_0adf(size)`
  就地把緩衝區加倍。比對用的字串常數在 `DEMON.INT` 檔案位移
  `0x27592`/`0x27596` = `"shE\0SHE\0"`。
- **`FUN_217b_0adf`**（`217b:0adf`）：由後往前就地展開 N bytes → 2N bytes，
  每 byte 呼叫 `FUN_217b_0b19`。`0b19`／`0a95` 的核心迴圈
  `SHL AX,1 / MOV DH,AH / AND DH,1 / SHL AH,1 / ADD AH,DH`
  是逐 bit 複製兩次，也就是水平像素加倍。
- **載入呼叫端**（`1990:2e3c`、`138d:3794`、`17c5:0581`）：讀取單位是
  `[0x5226] << 3` = 1,792 = **8 個 224-byte frame**（一隻怪物 8 個動作，
  240/8 = 30 隻），檔內 seek 是 `索引 × 1792`；目的位址是
  `[0x521e] + 槽位 × [0x521a]`（×448），正是 `FUN_217b_07cf` 定址的緩衝區。

**為什麼加倍後佈局公式不變**：檔案內每列 8 bytes（4 個 plane 各 2 B），
逐 byte 加倍後每列 16 bytes（4 個 plane 各 4 B）——結構同構，只有 rowBytes 從 2 變 4。
所以「把檔案當 16×28 的 row-blocks 解」與「把記憶體當 32×28 的 row-blocks 解」
是同一張圖。這也解釋了為什麼用 32×28 解檔案會看到「2×2 四個小圖」：
它把兩個相鄰 frame 的左右半邊錯位疊在一起。

**plane 佈局本身是對的**（`internal/assets/gfx` 的 `EGAPlanesRowBlocks`），
錯的只有 rowBytes。

### 4.3 frame 邊界與兩套素材的逐格對應（已驗證）

`.SHE` 與 `.SHP` 的 frame 數完全相同，同索引就是同一張圖：

| 檔案 | `.SHE` 大小(B) | ÷224 | `.SHP` 大小(B) | ÷64 |
|---|---|---|---|---|
| `COMBAT` | 9,856 | 44 | 2,816 | 44 |
| `SHIP` | 7,168 | 32 | 2,048 | 32 |
| `DEMON` | 22,848 | 102 | 6,528 | 102 |
| `WINTER` | 22,848 | 102 | 6,528 | 102 |
| `MONSTER` | 53,760 | 240 | 15,360 | 240 |
| `CYPHER` | 6,048 | 27 | 1,728 | 27 |

**肉眼驗收**：依 16×28 解，每個 frame 都是一個完整自成一體的圖形；
`MONSTER.SHE` frame 0–7 是同一個戰士的 8 個姿勢。
`DEMON`／`WINTER` 各 102 格逐格對應（`WINTER` 是雪地版）。
CGA 側依 16×16 解出的圖案、順序、空白格位置與 EGA 版一格不差。

### 4.4 `DEMON`／`WINTER` 的 102 格是地形圖塊集（已驗證）

這兩個檔不是角色 sprite，是**地形圖塊集**：102 個圖塊與 `FILES.DAT` offset
`0x040` 的可通行性表（tile 0–100，共 101 項，見 `docs/re/22`）對應，
最後一格（索引 101）未被該表涵蓋。`WINTER` 是 `DEMON` 的雪地版，同索引同地形。

### 4.5 歷史紀錄：解出前排除過的佈局假設

> **這節是探索紀錄，不是現況。**正確答案見 §4.0。保留的理由：一是讓後人知道
> 哪些方向已經走過；二是它示範了「猜佈局 → 輸出 → 看像不像」這條路的投報極限——
> 試掉十種假設都沒中，最後是**改從程式碼讀出常數**才解開的。
> 正確的 `row × 8 + plane × 2 + col` 這種粒度，不在下列任何一種假設裡。

當時用 `MONSTER.SHE` 逐一排除（尺寸一律假設 16×56 或 32×16 這類「448 B/frame」的切法）：

| 假設 | 說明 | 結果 |
|---|---|---|
| 逐-frame 4-plane sequential | 每個 frame 自己 plane0 整塊 + plane1…（跟人像框同邏輯） | 雜訊 |
| 整檔 4-plane sequential(global) | 把整份檔案當一張高圖解，4 個 plane 是檔案級分塊，再切 frame | 雜訊 |
| 逐-frame row-interleaved | 每列 4 個 plane byte 相鄰 | 雜訊 |
| 整檔 row-interleaved(global) | 整檔視為一張 16×6720 的圖，每列 4 plane byte 相鄰 | 雜訊 |
| 寬高對調(56×16 global) | 懷疑 1.75× 套在寬度而非高度 | 雜訊 |
| 不縮放(32×16 global) | 懷疑 sprite 不套用 1.75× 縮放 | 雜訊 |
| chunky 4bpp row-major(16×56) | 非 planar，每 byte 兩像素 | 雜訊 |
| chunky 4bpp column-major(16×56) | 同上但逐欄存放 | 雜訊 |

這八種**全都建立在「一個 frame 448 bytes」這個前提上**，而該前提本身就是錯的
（那是記憶體內的大小）。這是本節最重要的方法論教訓：
**當一整批佈局假設全數失敗時，要回頭懷疑的往往不是佈局，是切分單位。**

## 5. `OPEN.PIE`（102,160B）：**已解**（2026-07-26）—— 608×336 開場標題畫面

> 以下保留原本「未解」時的分析過程供追溯，結論在本節開頭。

**格式**：16 bytes 調色盤表頭 + **336 列 × 304 bytes**，
每列 4 個 plane 各 76 bytes（`EGAPlanesRowBlocks`），解出 **608×336**。
`16 + 76×4×336 = 102,160`，正好用光整個檔案。

**怎麼解出來的**：不是再猜一輪候選尺寸，而是**窮舉 16–320 的每一種列寬，
量測「相鄰列的位元組差異」**——正確的 stride 會讓相鄰列高度相似：

| 每列 bytes | 列間差異 |
|---|---|
| 303 | 72.8 |
| **304** | **43.2** ← 尖銳極小值 |
| 305 | 73.5 |

43.2 與兩個已知正確的對照組同級（`OPEN.PIC` 44.9、`PIC1.PIE` 55.6），
左右鄰居立刻跳到 73。先前「6 種候選尺寸全部雜訊」的問題在於**候選是猜的**，
而 304 不在任何一組猜測裡（它不符合 3.5× 規律，也不是常見螢幕寬）。

**⚠ 它不是半寬圖，這是 §1「EGA 素材一律檔案存半寬」的例外。**
608 × 2 = 1216 超過任何 EGA 模式；而且照 608 直接解出來的字母比例正常
（若真是半寬圖，字會橫向擠成一半）。全螢幕圖與人像框走的是不同的 blit 路徑。

**肉眼驗收**：解出「DEMON'S WINTER」標題、惡魔持鞭、
`Adapted for the IBM by Judit Burczolich and Laszlo Fazekas`、
SSI 與 NOVOTRADE 標誌。與 CGA 版 `OPEN.PIC`（320×200，16,000 B 線性 packed 2bpp）
是同一張美術，**兩版都有大量抖色雜點，那是美術本身不是解碼問題**——
拿 CGA 版當獨立對照才能確定這一點。

實作：`gfx.DecodeTitleScreen`。

### 5.0 另一個發現：`OPEN.*` 是孤兒檔，引擎不讀它

`OPEN.PIC` 與 `OPEN.PIE` 這兩個檔名**在 `DEMON.INT` 與 `DEMON.EXE` 裡都零命中**。
引擎的畫面檔名表（`0x277e7` 起）是：

```
THANATOS.PIC  PIC1.PIC … PIC6.PIC  PRIEST.PIC  SHAMEN.PIC  TITLE.PIC
```

—— 標題畫面叫 **`TITLE.PIC`**，而那個檔**不在這份 dump 裡**。
EGA 模式會把副檔名末字改成 `E`，所以它要找的是 `TITLE.PIE`，同樣不存在。

這解釋了 `workplace/dosbox/shots/05-cga-hang-open-pic.png` 為什麼是「開場卡住」：
**原版在這份 dump 上根本開不了場，因為標題檔名對不上。**

所以 `OPEN.PIC`/`OPEN.PIE` 很可能是改名前（或另一個發行版本）的檔案。
美術本身完整、解得開；**未解的是「原版怎麼載入標題畫面」**，
以及這份 dump 為什麼缺 `TITLE.PIC`。

---

### 5.1 原本的分析（未解時期，保留供追溯）

`(102,160 - 16) / 4 = 25,536 = 2^6 × 3 × 7 × 19`，**沒有因數 5**，代表無法
用任何「寬度是 320 或 640 的倍數（含因數 5）」的簡單全螢幕 4-plane 佈局整除。
試過的候選全部輸出雜訊：

| 候選 | 說明 | 結果 |
|---|---|---|
| 320×200 / 320×350 / 320×399 / 608×336 / 456×448（扣 16B 調色盤後） | 湊出能被 25,536 整除的尺寸組合 | 全部雜訊 |
| 640×350（4-plane 標準 EGA 高解析模式） | 尺寸不合，`102,144 < 112,000`，連 decode 都跑不完 | 資料不足，排除 |
| 5 幀動畫，每幀套用人像框公式(144×252，18,144B/幀) | `102,160/18,160=5.6`，非整數，仍探索性跑了 5 幀 | 全部雜訊 |

**結論**：`OPEN.PIE` 確認是 PLAN.md 標記的異常檔案，不符合本文件其他 EGA 素材
共通的「線性 frame × 4-plane sequential」模型。可能性(未驗證，留待下一輪)：

- 有某種未知的壓縮/編碼，且因為是開場全螢幕大圖，壓縮效果更明顯
  （惡魔插畫大面積同色，RLE 壓縮率會比小 sprite 高很多，與「檔案沒有依 3.5×
  等比放大」的觀察一致）。
- 是多幀動畫（開場可能有漸變/掃入效果），但幀之間可能有差分編碼而非各自獨立
  一張完整圖。
- 有目前未知的檔頭欄位（不只 16 bytes）標示實際尺寸/幀數。
- **候選尺寸表要照「檔案存半寬」重算**：`.PIE` 與 `.SHE` 都是檔案存半寬、
  顯示時寬度加倍（§1）。若 `OPEN.PIE` 也走這條規則，那麼一張 640 寬的
  開場畫面在檔案裡只佔 320 寬，先前用「顯示寬度」湊出來的候選尺寸全部偏了一倍。

## 6. 字型 `.FNT`/`.FNE`：**已解**（2026-07-25）

本節原記「未解」，並列出當時試過而失敗的佈局假設。
**已由 `docs/re/17-font-format.md` 解出並肉眼驗證**，結論：

| 項目 | CGA `.FNT` | EGA `.FNE` |
|---|---|---|
| 字元尺寸 | 8 × 8 | 16 × 14 |
| 色深／佈局 | packed 2bpp（每 byte 4 個像素，byte0 = 左 4px、byte1 = 右 4px）| 1bpp（前景色由呼叫端指定）|
| 每字 bytes | 16 | 28 |
| bit 順序 | MSB-first | MSB-first |
| 字表起點 | ASCII `0x20` | ASCII `0x20` |
| 字數 | 96 × **2 個 bank**（bank0 一般、bank1 反白）= 192 glyph | 96 |
| 檔頭 | **無**（3,073 B = 3,072 資料 + 結尾 `0x1A` DOS EOF）| 無 |

> 這張表以 `docs/re/17-font-format.md` 為準（該文有逐指令核對與逐字母 PNG 比對）。
> 本節先前寫的「1 byte 檔頭」「同列 2 bytes = 兩個 bit 平面」已被該文推翻。

原本的猜測「1-byte header + 256×8×12 1bpp」**尺寸、色深、bit 佈局全部錯**。
解法是先讀繪字函式的位址算式（`rulebook/62`），再拿字母形狀當 oracle 驗證
（`rulebook/64`），而不是純試佈局 —— 字型格式沒有「frame 邊界能被檔案大小整除」
這種錨點，純試很難收斂。

## 7. 總結表

| 項目 | 狀態 | 證據 |
|---|---|---|
| CGA `.PIC` 全螢幕(`OPEN.PIC`) | ✅ 已驗證 | 對上 DOSBox 截圖 05 |
| CGA `.PIC` 人像框(9 檔) | ✅ 已驗證 | 清楚圖案 + 與 EGA 版一致 |
| CGA `.SHP` 精靈圖(6 檔) | ✅ 已驗證 | frame 16×16、64 B;`1d9f:018d [0x5226]=0x40` + 檔案大小乘法 + 肉眼逐格比對 |
| EGA `.PIE` 人像框(9 檔) | ✅ 已驗證 | 清楚圖案 + 與 CGA 版一致 + 調色盤合理;檔內 144×252、顯示 288×252 |
| EGA `.SHE` 精靈圖(6 檔，含 `CYPHER`) | ✅ 已驗證 | 檔內 frame 16×28、224 B;`1d9f:00bf [0x5226]=0xe0` + 檔案大小乘法 + 載入鏈 + 肉眼逐格比對。記憶體內 32×28、448 B |
| `OPEN.PIE` | ✅ **已解**（2026-07-26）| 608×336，16B 調色盤 + 每列 4 plane×76B；窮舉 stride 找到尖銳極小值，肉眼與 CGA 版對照一致。**非半寬**，是 §1 規則的例外 |
| `.FNT`/`.FNE` 字型 | ✅ **已驗證**（2026-07-25，見 `docs/re/17`）| CGA 8×8 2bpp「同列 2 byte = 兩個 bit 平面」；EGA 16×14 1bpp。**不受載入加倍影響**——載入器只比對 `"SHE"` 字串 |

**3.5 倍假設的最終裁決**：作為「總位元數」的約束成立（色深 ×2 × 高度 ×1.75），
`.PIE` 人像框與 `.SHE` 精靈圖的檔案大小都符合；`OPEN.PIE` 不符。

但**它推不出佈局，也推不出 frame 尺寸**。sprite 這一項連續猜錯兩輪
（16×32 → 32×28 → 實際 16×28），每一輪的錯誤版本都整除、都能畫出「看起來像
那麼回事」的圖。定案靠的是遊戲自己在初始化時宣告的 `[0x5226]` 常數，
以及「每個 frame 必須是一個完整自成一體的圖形」這條肉眼判準。

## 8. 給引擎渲染層的建議

- **可以直接串進渲染管線**：
  - CGA 全部格式（全螢幕 `.PIC`、人像框、精靈圖 `.SHP` 16×16）
  - EGA 全螢幕圖／人像框 `.PIE`（解 144×252，畫的時候寬度 ×2 = 288×252）
  - **EGA 精靈圖 `.SHE`**（解 16×28、4-plane、列內 plane 分塊，
    畫的時候寬度 ×2 = 32×28，見 §4）
  - **字型 `.FNT`／`.FNE`**（見 `docs/re/17`）

- **不必複製原版的載入時加倍**：`FUN_217b_0adf` 那步是 8086 為了讓 blit
  變成單純的 `MOVSW` 而做的預處理。重寫版直接以 16×28 解檔、在繪製時
  用縮放或整數放大處理寬度即可。

- **仍不能用**：`OPEN.PIE`（見 §5）。
  開場畫面可先用 CGA 版 `OPEN.PIC` 頂著 —— 那個已完整驗證。

- **踩雷提醒**：任何「用檔案大小推 frame 尺寸」的推論都要當成假設。
  sprite 這一項本專案錯了兩輪才對，兩次的錯誤版本都整除、都畫得出圖案。
  可靠的判準有兩條：**遊戲初始化時自己宣告的常數**（`[0x5226]`），
  以及**每個 frame 必須自成一體**（一格裡出現 2 個或 4 個並排小圖 = 尺寸解錯）。
