# FILES.DAT / FILES.DTT / nSS.DAT / ALL_SS.DAT 格式分析

分析目標：`workplace/orig/demwin/DEM_DATA/` 底下的 `FILES.DAT`、`FILES.DTT`（原本懷疑是資源索引），
以及 `1SS.DAT`～`5SS.DAT`、`ALL_SS.DAT`（開場序列資料）。

可重跑的解析器：`tools/parse_files_index.py`（純標準庫，`python3 tools/parse_files_index.py` 即可重現本文所有數字）。

## 1. FILES.DTT — 已確認是遊戲主字串池

### 1.1 基本結構

`FILES.DTT`（5,829 bytes）是一串以 `\x00` 結尾的字串，共 **501 筆**（122 筆為空字串，379 筆非空）。
沒有任何長度前綴或位移表頭——純粹是字串一個接一個排列，用 NUL 分隔。

### 1.3 `[164:467]` 物件互動文字表的結構觀察（事實，語意部分為推測）

這段占了字串池將近六成的體積，是一連串「物件名 + 描述 + （選擇性）事件觸發文字」的記錄群，例如：

```
[164] Iron key
[170] Bed
[171] It is too heavy
[172] Just wood with a straw mattress
...
[188] Cage
[190] There are rats locked in it
[192] Iron key
[193] DOne of the rats runs out and through a secret door in the middle of the west wall
```

觀察到的規律（**事實**，已用 grep/hex 核對）：

- 大量空字串（122 個）穿插在有內容的字串之間，形成「固定欄位數、部分欄位留空」的記錄結構，而非隨機空洞。
- 部分字串開頭有單一字元前綴，且是**字面上的 ASCII 字元**（已用 hex dump 核對，例如 `DOne of the rats...` 的 `D` 就是 0x44，不是控制碼）：
  - `N` — 疑似「觸發後物件改名為」（如 `NBag/red dust` 之後接著出現獨立字串 `Bag/red dust`）
  - `D` — 疑似「觸發後才顯示的長描述／劇情文字」（每次出現都接著一段完整敘事句子）
  - `T` + 6 位數字（如 `T031704`）— 疑似觸發／座標編碼
  - `P` + 5 位數字（如 `P04480`）— 疑似圖片／座標編碼
  - `S` + 1 位數字（`S1` / `S2`）— 疑似音效或劇本編號
  - `*` 單獨出現 — 疑似「此欄位無內容」的顯式旗標（區別於純粹的空字串）
- 上述前綴代碼的**確切語意（是不是真的是 trigger/picture/sound）未證實**，只確認它們是穩定出現、格式一致的前綴模式，而非雜訊或誤判。

這個結構風格與 `DEMON.INT` 字串表中出現的 `itemlocb.dat` / `itemlocx.dat`（未出現在 `DEM_DATA/`，推測是執行期依角色存檔動態產生／複製的檔案）高度相似。**合理推測**（未證實）：`FILES.DTT` 是這些「物件位置事件」記錄所引用的共用字串池，執行期的 itemloc 檔案本身只存數值型的記錄結構（物件 ID、事件旗標、字串索引），實際顯示文字統一從 `FILES.DTT` 撈取，避免在每個城鎮/地城檔案裡重複儲存相同文字。

## 2. FILES.DAT — 否證「資源索引」假設；內部是多段小型數表

### 2.1 「檔名目錄」假設：已否證

`strings -n4 FILES.DAT` 與逐 byte 掃描皆未發現任何檔名字串（如 `1SS.DAT`、`PIC1.PIC`）。
唯一出現的可印字元片段都是數值 byte 剛好落在 ASCII 可印範圍的巧合（如 `$%&-.`、`NhNhNh...`），
不是真正的文字。**因此「FILES.DAT 記錄了哪個資源在哪個檔案」這個最初假設不成立**。

### 2.2 「FILES.DAT 是 FILES.DTT 的位移索引表」假設：證據不足

把 `FILES.DAT`（2,254 bytes）視為 uint16 LE 陣列（1,127 個數值），
與 `FILES.DTT` 501 個字串各自的起始位移做交集：

- 剛好命中 `FILES.DTT` 某字串位移的數值：**214 個**
- 同樣抽樣次數、在相同數值域內均勻隨機抽樣的期望命中數（基準線）：**約 84 個**
- 命中數/基準線 ≈ **2.55 倍**

倍率明顯高於隨機（説明兩者並非完全無關），但遠遠不到「真正索引表應有的高命中率」
（若 FILES.DAT 真的是一張完整的字串位移表，命中率應接近 100%，而非 2.5 倍基準線）。
**結論：現有證據不足以支持「FILES.DAT 直接索引 FILES.DTT」，判定不成立。**

較合理的解讀是：兩者只是**同一子系統會一起載入的兩個資源**（`DEMON.INT` 的內部檔名字串表中，
`files.dtt` 與 `files.dat` 確實緊鄰出現，和 `party.dat`／`itemlocb.dat`／`demon.shp`／`winter.shp` 排在一起），
但 FILES.DAT 本身另有其結構，不是專門對應 FILES.DTT 的索引。

### 2.3 FILES.DAT 內部分段（依 byte 值分布特徵辨識，已用程式驗證邊界）

| 位移範圍 | 特徵 | 判定 |
|---|---|---|
| `0x000–0x09F` | 大量 0–17 的小數值，夾雜少數 0xFF/0xFE | 疑似 signed 小整數表（-2~17），用途未定 |
| `0x0A0–0x14F` | 出現連續遞增的 marker byte `0x80,0x81,0x82,...,0xD0`（跨度 80 個 ID），每個 marker 後面跟著數個 0–25 範圍的小數值 | **已驗證**存在此結構（非隨機）；典型「遞增 ID + 變動長度子清單」編碼（類似鄰接表／群組表），語意未定 |
| `0x150–0x41F` | 大量 0–10 範圍小數值 | 另一張表格資料，未解 |
| `0x420–0x5FF` | uint16 LE 小數值，多在 0–100 範圍 | 未解 |
| `0x600–0x67F` | **8 筆固定 14-byte 記錄**，樣板 `[10, 8, 9, X, 1, 3, 0]`（7 個 uint16），僅第 4 欄變動：X = 6, 15, 13, 20, 30, 65, 100, 5 | **已驗證**（見 `tools/parse_files_index.py` 輸出，可重現）。8 筆記錄、6 個固定欄位＋1 個變動欄位，是全檔案中結構最乾淨的一段。**假設**：8 可能對應遊戲的 8 個吟唱類技能（Fire/Metal/Wind/Ice/Spirit runes + Illusion + Summoning + Possession），但變動值 X 與已知的法力/等級門檻對不上，未能確認 |
| `0x680–0x8CF` | 4~5-byte 週期的小數值表格 | 未解 |

**重要澄清**：FILES.DAT 明顯不是單一同構的資料表，而是**好幾張互不相關的小表格串接在一起**的
複合資料檔。這解釋了為什麼「offset/length 索引」假設測不出強相關——因為它本來就不是那種結構。

## 3. nSS.DAT / ALL_SS.DAT — 開場序列資料

### 3.1 ALL_SS.DAT = 5 個 512-byte 區塊：已驗證

`ALL_SS.DAT` 大小 2,560 = 5×512，符合任務假設的「5 個 512-byte 區塊」。
每個區塊的第 512 個 byte（index 511）都是 `0xFF`——五個區塊一致，判定為區塊填充／結束標記。

### 3.2 nSS.DAT 與 ALL_SS.DAT 對應區塊的逐位元組比對：部分成立

| 檔案 | 與對應 512-byte 區塊前 511 bytes 比對 |
|---|---|
| `1SS.DAT` | **不完全相同**，21 處差異 |
| `2SS.DAT` | **不完全相同**，8 處差異 |
| `3SS.DAT` | **完全相同** |
| `4SS.DAT` | **完全相同** |
| `5SS.DAT` | **完全相同** |

`1SS.DAT`／`2SS.DAT` 的差異**全部**發生在 `position % 3 == 2` 的位置（也就是每筆 3-byte 記錄的第 3 欄），
其餘欄位（第 1、2 欄）逐位元組相同。這與 3.3 節獨立分析出的「3-byte 記錄」結構完全吻合，
差異的性質是「同一組座標記錄，但屬性/類型欄位在個別檔案版本與合併版本之間不同」，
而不是資料錯位或損毀。**合理推測**：`nSS.DAT` 與 `ALL_SS.DAT` 是同一份開場序列資料的兩份建置產物，
1、2 號在某次修改後只更新了其中一份（個別檔或合併檔），3、4、5 號則兩邊保持同步。此推測未經進一步證據確認，
僅止於觀察到的差異型態與其位置規律。

### 3.3 nSS.DAT 內容判定：座標＋屬性的稀疏記錄清單（已驗證結構，語意未定）

**排除文字**：可印字元比例僅 5%–17%（1SS 最高，其餘更低），byte 值域 0–198，
不集中在 0x20–0x7E，不是文字。

**排除「均勻小數值 tile 地圖」**：每個檔案的實際資料只佔開頭一小段（60~204 bytes），
之後就是一大段連續 `0x00` 填充到檔尾（用 regex 找長度 ≥20 的連續零 byte 已驗證），
不是滿版的地圖網格。

**已驗證的 3-byte 記錄結構**：

1. 把 payload（去掉尾端填充零的部分）依 3 bytes 切開，`byte2`（記錄第 3 欄）出現 `0x40`／`0x41` 的比例
   明顯偏高（例如 3SS.DAT 68 筆記錄中 18 筆的第 3 欄是 0x40/0x41），且**所有** `0x40`/`0x41` 都精確落在
   `position % 3 == 2`，5 個檔案一致。這不是巧合，是 3-byte 記錄邊界的直接證據。
2. `byte2`（記錄第 3 欄）數值聚集在 `0x20`、`0x40`、`0x80` 及其加總／加 1 的組合（如 0x21, 0x62, 0xA2, 0xA9, 0xAF），
   即高位 bit（bit5/6/7）像是「模式／分類」選擇位，低位 bit（0–4）像是子參數（0–15 範圍），
   是典型的「屬性/分類 byte」編碼型態，不是像素資料也不是文字。
3. `byte0`、`byte1`（記錄第 1、2 欄）數值範圍集中在個位數到六十幾，符合小尺寸座標或索引值的合理範圍。

**綜合判定**：`nSS.DAT` 的內容是一份**稀疏的（座標, 座標, 屬性）三元組清單**，記錄筆數依檔案從 20 到 68 筆不等，
形態上最貼近「畫面繪製指令清單」（在哪個位置、用什麼顏色/模式畫一個點或圖塊），
但**沒有找到足夠證據確認具體用途**（例如是否為開場動畫的星點/雪花特效、還是別的東西）。
依專案硬規則，此處不對 `SS` 這個檔名縮寫做語意猜測——只能確認：它不是文字、不是檔名索引、
是規律的 3-byte 記錄型稀疏資料。

## 4. 未解問題與建議下一步

1. **FILES.DAT 各分段的精確語意未解**——尤其是 `0x0A0–0x14F` 的「遞增 ID + 子清單」結構、
   `0x600–0x67F` 的 8 筆固定記錄。建議下一步：在 Ghidra 反組譯結果中搜尋讀取 `FILES.DAT` 的函式，
   比對其解析迴圈的 stride（每筆記錄跨幾個 byte）與本文觀察到的分段邊界是否吻合，
   會比純資料面猜測可靠得多。
2. **`[164:467]` 物件互動文字表的 N/D/T/P/S 前綴確切語意未證實**——如果能在 Ghidra 裡找到
   顯示這段文字的函式，看它怎麼分支處理不同前綴字元，就能確認。
3. **`nSS.DAT` 的 3-byte 記錄用途未證實**——建議：用 DOSBox 實跑開場序列，逐格截圖，
   跟 `docs/re/` 或 `workplace/ghidra` 裡若有的畫面座標系統對照，看記錄裡的 (x, y) 是否對得上
   畫面上出現效果的位置。這是目前最有機會把「稀疏座標清單」進一步坐實成「具體視覺效果」的路徑。
4. **`FILES.DAT` 與 `FILES.DTT` 的載入關係**——兩者在 `DEMON.INT` 字串表中緊鄰出現，但數值上
   查無強索引關係；若要進一步確認，需要反組譯找到實際載入這兩個檔案的函式，看程式碼裡怎麼配對使用它們，
   純資料面分析已經到極限。
5. **`[467:489]` 的 22 個形容詞表是否為隨機物品命名詞庫**——僅為觀察形態後的假設，未證實；
   若能在其他檔案（如未列入本次分析範圍的 ITEM/MONSTER 相關檔）中找到直接引用此表的索引，
   即可確認或否證。
