# 事件觸發機制反組譯：座標 → DATA*.TXT 事件索引

> 分析對象：`workplace/ghidra/export/`（Ghidra 12.1.2 headless 匯出，見 `00-ghidra-setup.md`）。
> 前置文件：`02-data-loading-functions.md` 已解出 `DATA*.TXT` 讀取函式 `FUN_25be_0e77`（`25be:0e77`）
> 的記錄格式與 parse 迴圈，但留了一個明確的缺口：迴圈上限 `*(int*)0x52f4`（「要跳到第幾筆記錄」）
> 是怎麼被設定的、跟地圖座標的關係是什麼——這正是本文的起點。
> 方法：`rulebook/62` 靜態溯源 SOP——從 `FUN_25be_0e77` 往上游追呼叫者，逐層還原「玩家移動 →
> 判斷有無事件 → 決定第幾筆記錄 → 讀 DATA*.TXT」的完整鏈路。全程靜態反組譯，未使用 DOSBox。
> 位址換算公式：`file_offset = segment*16 + offset - 0xC400`（見 `00-ghidra-setup.md`）。

---

## 0. 結論先講

- **座標 → 事件索引的映射機制：已解，且有乾淨、無警告的反編譯證據 + 真實 `EXITS.DAT` 資料驗證。**
  核心是 `FUN_222f_1321`（`222f:1321`，224 bytes）：線性掃描一張以**遠指標 `0x5514:0x5516`**
  指向、內容來自 `EXITS.DAT` 的記憶體表，表格式是 **3-byte 記錄 `[X, Y, type_byte]`**（不是
  `docs/formats/town-and-map.md` 推測的「165 筆 2-byte (X,Y) 座標對」——見 §5 修正）。找到座標相符
  的記錄後，把**目前為止「事件類記錄」的計數**寫回全域 `0x52f4`——這個位址跟 `FUN_25be_0e77`
  （`docs/re/02`）讀 `DATA*.TXT` 的**迴圈上限變數是同一個記憶體位址**。這是「地圖座標決定 `DATA*.TXT`
  第幾筆記錄」的直接、可驗證證據，不是推論。見 §1。
- **觸發時機：已解，是特定 tile 值觸發，不是每步都查。** 玩家移動後，移動迴圈函式 `FUN_222f_0b0e`
  （`222f:0b0e`）讀取新座標的地圖 tile 值，**只有 tile 值（遮罩後）等於 `0x11`(17) 或 `0x53`(83)**
  時才呼叫事件檢查函式 `FUN_222f_0a90`；tile 值 `0x35`(53) 走另一條寫死的「阻擋」回傳，完全不查
  `EXITS.DAT`。見 §2。
- **事件後果分派：部分解開。** `EXITS.DAT` 記錄的 `type_byte` 拆成「類別」(`type_byte / 32`，0–7)
  + 「子值」(`type_byte % 32`)。類別 4 = **傳送**（已驗證，讀第二組座標覆寫玩家座標）；類別 1/2
  會讓事件索引 `+1`；類別 2 另外會武裝一個「防止同格重複觸發」的倒數計時器 `0x4e2e`。但**類別 0
  （真實 `EXITS.DAT` 裡佔 94/110、最大宗）在目前追到的閘門邏輯（`FUN_222f_0a90`）裡直接被排除、
  不觸發任何東西**——這點跟直覺（大多數房間都該顯示文字）矛盾，本文誠實列為未解，見 §4。
- **戰鬥啟動機制：沿用 `docs/re/02` 已有結論，未推翻。** `FUN_25be_0e77` 讀出的記錄若 `count != 0`，
  即呼叫 `FUN_17c5_000d` 進入戰鬥；本文新增的部分只是「怎麼決定讀哪一筆記錄」，不影響 `docs/re/02`
  對記錄內容本身的解讀。
- **`EXITS.DAT` 的角色：修正+擴充。** 不只是「座標表」，而是**「目前所在資料集(dataset)的座標→事件
  類別/索引查表」**，且會在切換 dataset（地城）時被**整份覆寫**——切換邏輯（`FUN_222f_32d4`，
  `222f:32d4`）另外維護一張**不同記錄長度（6-byte）**的「dataset 轉換表」，用來決定新的
  `dataset index`（即 `docs/re/02` 講的 struct+0xa3）與新的「錨點座標」。這代表**「330 bytes = 全部
  7 個地城共用的單一大表」這個假設是錯的**，330 bytes 應該只是「當前 dataset 專屬」的那一份，隨
  dataset 切換動態覆寫，見 §3、§5。

## 1. 位置 → 事件索引映射（核心問題，已解）

### 1.1 起點：`FUN_25be_0e77` 的迴圈上限變數

`docs/re/02` §2.2 已指出 `FUN_25be_0e77` 內層有一個外層迴圈：

```c
for (local_24 = 0; local_24 < *(int*)0x52f4; local_24++)  // 逐筆消耗 DATA*.TXT 記錄，直到第 0x52f4 筆
```

也就是說，`0x52f4` 這個全域變數的值，就是「要把 `DATA*.TXT` 從頭掃到第幾筆記錄才停下來」——因為
`DATA*.TXT` 是 NUL 分隔的變長文字格式，沒辦法隨機定位，只能從頭重新 parse 到目標筆數。`docs/re/02`
在 §2.6／§4 誠實列出「這個變數怎麼被設定，跟地圖座標的對應關係」是未解問題。本文從這裡往上游追。

### 1.2 找到設定者：`FUN_222f_1321`

全域搜尋所有寫入 `0x52f4` 的位置（`grep "0x52f4) = " decompiled_all.c`），排除掉單純「讀出來當座標
用」的位置後，鎖定一個 224-byte、**反編譯完全乾淨、零警告**的函式：

```
FUN_222f_1321 @ 222f:1321, 224 bytes
```

完整反編譯（`decompiled/222f_1321_FUN_222f_1321.c`，逐行核對過，无 decompiler 警告）：

```c
uint __cdecl16far FUN_222f_1321(void)
{
  local_e = 0;
  local_c = 0;
  local_6 = (byte *)CONCAT22(*(undefined2 *)0x5516,(byte *)*(undefined2 *)0x5514);  // 遠指標 0x5514:0x5516
  while( true ) {
    pbVar4 = (byte *)local_6;
    if (*local_6 == 0) {
      return 0xff;                                          // byte0==0：表尾哨兵，無符合記錄
    }
    if (((uint)*local_6 == *(uint *)0x52f4) &&               // byte0(X) == 輸入X (0x52f4)
        ((uint)pbVar4[1] == *(uint *)0x52f6)) break;         // byte1(Y) == 輸入Y (0x52f6)
    bVar1 = pbVar4[2] & 0xe0;                                // byte2 的高 3 bits
    if ((bVar1 == 0x40) || (bVar1 == 0x20)) {                // 類別 1 或 2 (見下)
      local_e = local_e + 1;                                 // 計數！
    }
    if (bVar1 == 0x80) {
      local_c = local_c + 1;                                 // 另一個計數（給類別4用）
    }
    local_6 = (byte *)CONCAT22(uVar6,pbVar4 + 3);            // 指標 +3：3-byte 一筆記錄
  }
  *(undefined2 *)0x52fa = uVar6;         // 存匹配記錄的遠指標(segment)，供後續寫回用
  *(undefined2 *)0x52f8 = pbVar4;        // 存匹配記錄的遠指標(offset)
  *(int *)0x52f4 = local_e;              // ★ 把「輸入X」欄位重用成「事件索引」——關鍵一行
  *(uint *)0x52f6 = (uint)pbVar4[2] % 0x20;   // ★ 把「輸入Y」欄位重用成「子值」
  uVar2 = pbVar4[2] / 0x20;              // 類別 = type_byte / 32 (0-7)
  *(uint *)0x5c62 = uVar2;
  if ((uVar2 == 1) || (uVar2 == 2)) {
    *(int *)0x52f4 = *(int *)0x52f4 + 1; // 類別 1/2：索引再 +1
  }
  if (uVar2 != 4) {
    return uVar2;                        // 非類別4：直接回傳類別值
  }
  // 類別4（傳送）：從表尾（0x1ff 往回數 local_c*2+2）另外取一組座標，覆寫 0x52f4/0x52f6
  iVar3 = 0x1ff - (local_c * 2 + 2);
  *(uint *)0x52f4 = (uint)*(byte *)(iVar5 + iVar3);
  uVar2 = (uint)*(byte *)(iVar5 + iVar3 + 1);
  *(uint *)0x52f6 = uVar2;
  return uVar2;
}
```

**已驗證**（反組譯 + 邏輯內部自洽，無需動態即可下結論，符合 `rulebook/62` 精神）：

1. 這是一個「座標比對」線性掃描：把記憶體裡的 `EXITS.DAT`（見 §1.3）當成 **3-byte 記錄陣列**
   `[X, Y, type_byte]`，逐筆比對輸入座標 `(0x52f4, 0x52f6)`。
2. 找到相符記錄後，**用『目前為止經過的事件類記錄數』覆寫 `0x52f4`**——這就是 `FUN_25be_0e77`
   要用的「第幾筆記錄」。兩個函式讀寫的是同一個記憶體位址 `0x52f4`，這是本文最關鍵的一條證據鏈。
3. `type_byte` 拆成類別（高 3 bits, `/32`）與子值（低 5 bits, `%32`），類別驅動不同分支（§1.4）。

### 1.3 `0x5514:0x5516` 指向的資料就是 `EXITS.DAT`（❌ **已被推翻，見 `docs/re/77`**）

> **本節結論錯誤。** `0x5514:0x5516` 裝的是 **`nSS.DAT`（511 bytes）**，不是 `EXITS.DAT`（330 bytes）。
> 真正的載入端在另一支函式（頂層 `222f:0003`，`0x16064`），檔名由 `sprintf(buf, "%dSS.DAT", 子地圖)`
> 組出來（`ds:0x2011`），大小參數是 `0x1ff` ＝ **511**。
> 本節下面那段「兩者最終指向同一塊已載入的 `EXITS.DAT` 資料」是**假設**，不是驗證 ——
> 證據鏈到「`FUN_222f_32d4` 裡有一處把 EXITS.DAT 載入 `[0x4c94]`」就斷了，
> 之後接的是推論。能戳破它的硬證據（兩個不同的大小參數 330／511）一直就在本節引文裡。
> **`docs/re/05` §3 對 `EXITS.DAT` → `[0x4c94]` 的判讀本身沒錯**，錯的是把 `0x5514` 也算成它。

在 `strings.csv` 找到 `31f0:2653,9,EXITS.DAT`。反查誰把這個位址的 offset 部分（`0x2653`）當立即數
使用，鎖定 `FUN_222f_32d4`（`222f:32d4`，見 §3）內的載入呼叫（`disassembly.asm` 逐行核對）：

```asm
222f:338e  PUSH word ptr [0x4c96]     ; 目的緩衝區遠指標 segment
222f:3392  PUSH word ptr [0x4c94]     ; 目的緩衝區遠指標 offset
222f:3397  MOV AX,0x2653              ; "EXITS.DAT"
222f:339a  PUSH AX
222f:339c  MOV AX,0x522a              ; 忙碌旗標位址（跟 docs/re/02 讀 DATA%d.TXT 用的旗標同一個！）
222f:339f  PUSH AX
222f:33a0  CALLF 0x1000:e47b          ; 檔案載入函式
222f:33a5  ADD SP,0x10
222f:33a8  TEST AX,AX
222f:33aa  JZ 0x2000:56a9             ; 載入失敗處理
```

大小參數（在更上方，`MOV AX,0x14a; MOV DX,0x0`）= **0x14a = 330**，跟 `EXITS.DAT` 實際檔案大小
（`docs/formats/town-and-map.md` 已驗證的 330 bytes）完全吻合。**已驗證**：`EXITS.DAT` 被載入到遠指標
`0x4c94:0x4c96` 指向的緩衝區，且用的是跟 `DATA%d.TXT` 相同的非同步載入 + `0x522a` 忙碌旗標慣例。

`0x5514:0x5516`（`FUN_222f_1321` 實際掃描用的指標）跟 `0x4c94:0x4c96`（載入目的地）不是同一個變數名，
但透過一個「資源指標分發」函式 `FUN_1d9f_03e9`（`1d9f:03e9`）把一批 `0x54xx` 開頭的指標槽複製到對應的
`0x55xx`/`0x4cxx` 具名全域（含 `0x5516=*0x54b6; 0x5514=*0x54b4;`），這是一次性、程式啟動階段的
「把資源表指標分發成好記的全域名字」慣例（同一個函式裡還分發了戰鬥怪物陣列指標 `0x514e`、其他
UI 相關指標）。**已驗證**：兩者最終指向同一塊已載入的 `EXITS.DAT` 資料（透過同一份初始化資料流），
但**兩個指標在程式的不同執行階段被重複使用做不同事**（`0x4c94/0x4c96` 在 §3 的 6-byte 表掃描中，
以及在完全不同的函式 `FUN_1d9f_281a` 中被用來記錄「插圖繪製座標」——這是 16-bit 組語常見的暫存器/
全域重用模式，讀後續分析時務必留意上下文，不要假設同一位址永遠代表同一件事）。

### 1.4 真實 `EXITS.DAT` 資料驗證（❌ **驗錯檔案，見 `docs/re/77`** §3）

> **本節拿錯的檔案驗 3-byte 假說。** `FUN_222f_1321` 掃的是 `nSS.DAT`（511 bytes，
> 3-byte 記錄），不是 `EXITS.DAT`（330 bytes，6-byte 記錄 —— 本文 §3 自己的判讀才對）。
> 330 剛好能被 3 整除，所以錯的假說看起來自洽。
>
> 拿 `1SS.DAT`～`5SS.DAT` 重驗，**類別 0–6 全部出現**，所以下面
> 「類別 3–7 用現有資料永遠走不到」「沒有真實資料佐證類別 4 傳送被觸發過」
> **兩句都被推翻**：類別 4 在 5 個檔案裡共 14 筆，而且筆數與尾表座標對數 5/5 零誤差相符。

用 Python 直接讀 `workplace/orig/demwin/DEM_DATA/EXITS.DAT`（330 bytes）套用「3-byte 記錄」假說：

```
n = 330 / 3 = 110 筆記錄，整除、無餘數
X 值域 1–62，Y 值域 1–62      <- 跟已驗證的 64×64 地圖座標空間完全吻合
全檔案最大 byte 值 = 64        <- 因此 type_byte 最大只到 64，類別(/32)最多只到 2
類別分佈：{0: 94筆, 1: 14筆, 2: 2筆}   <- 加總 110，剛好對上
```

**已驗證**：3-byte 記錄假說跟真實資料完全自洽（X/Y 值域合理、整除無餘數）。這也帶出一個可驗證的
推論：**類別 3/5/6/7（含類別4傳送）在目前這份 `EXITS.DAT` 裡完全不會出現**——因為要湊出這些類別，
`type_byte` 必須 ≥ 96，但全檔案最大 byte 只有 64。也就是說，`FUN_222f_1321` 裡處理類別 3–7 的分支
（尤其類別4傳送）**程式碼存在，但用現有 `EXITS.DAT` 資料永遠走不到**——不是死碼判斷錯誤，是「這份
資料集剛好沒用到高類別」，可能是給其他/未收錄的資料集用（見 §3 的 dataset 切換發現），或是引擎通用
但這批資料沒派上用場。**誠實標記**：類別4傳送在靜態層面已完整解出機制，但沒有真實資料可以佐證它在
這個遊戲版本裡真的被觸發過。

### 1.5 上層封裝：`FUN_222f_0a90`

`FUN_222f_1321` 本身不含「玩家目前在哪」的資訊，呼叫者才負責填入 `0x52f4/0x52f6`。最關鍵的呼叫者是
`FUN_222f_0a90`（`222f:0a90`，126 bytes，同樣反編譯乾淨無警告）：

```c
undefined2 __cdecl16far FUN_222f_0a90(void)
{
  *(undefined2 *)0x52f4 = *(undefined2 *)0x50f0;   // 0x50f0 = 玩家目前地圖 X
  *(undefined2 *)0x52f6 = *(undefined2 *)0x50ee;   // 0x50ee = 玩家目前地圖 Y
  FUN_222f_1321();
  local_4 = 0xfffd;                                 // 預設：無事件
  if ((*(int *)0x5c62 != 0) &&
      ((*(int *)0x5c62 != 1 || (*(int *)0x52f6 == 0)))) {
    if (*(int *)0x4e2e == 2) {
      *(int *)0x4e2e = *(int *)0x4e2e + -1;
      local_4 = 0x12;                               // 觸發（一般事件訊號）
    }
    else if ((*(int *)0x5c62 == 2) && (*(int *)0x52f6 != 0)) {
      *(undefined2 *)0x4e2e = 1;                     // 武裝「防重複觸發」倒數
    }
    else if (*(int *)0x5c62 == 4) {
      *(undefined2 *)0x50f0 = *(undefined2 *)0x52f4; // 傳送：直接覆寫玩家座標
      *(undefined2 *)0x50ee = *(undefined2 *)0x52f6;
      local_4 = 0xffff;
    }
    else {
      local_4 = 0x12;                                // 其餘類別：一般觸發訊號
    }
  }
  return local_4;
}
```

**已驗證**：`0x50f0`/`0x50ee` 就是玩家的即時地圖座標（跟移動迴圈 `FUN_222f_0b0e` 內部讀寫這兩個位址
的方式完全一致）。這個函式把 `FUN_222f_1321` 的類別結果轉譯成三種語意：`0xfffd`＝無事件、`0x12`＝
一般觸發、`0xffff`＝已就地傳送。**類別==0 時（連同「類別1且子值==0」）不進入 if 區塊，直接回傳
`0xfffd`（無事件）**——這點是 §4 未解問題的根源，先在此標記。

### 1.6 完整鏈路小結（已驗證）

```
玩家移動 (更新 0x50f0/0x50ee)
  → FUN_222f_0b0e 讀新座標的地圖 tile 值，特定 tile 值才呼叫 (見 §2)
    → FUN_222f_0a90()：0x52f4/0x52f6 ← 0x50f0/0x50ee
        → FUN_222f_1321()：掃描記憶體中的 EXITS.DAT (0x5514:0x5516)，比對 (X,Y)
              命中 → 0x52f4 被覆寫成「事件索引」，0x5c62=類別，0x52f6=子值
        → 依 0x5c62 分派：0xfffd(無)／0x12(觸發)／0xffff(傳送，就地覆寫座標)
  → （後續，經由外層狀態機以 action code 0xa 再次進入 FUN_222f_0b0e，見下）
    → case 0xa: 檢查 struct(0x4c76)+0xa5（docs/re/02 的「續接碼」）是否等於3，
                決定是否真的呼叫 FUN_25be_0e77(param_1, 是否延續旗標)
        → FUN_25be_0e77 內部：迴圈讀到第 *(int*)0x52f4 筆 DATA*.TXT 記錄 ← 就是剛剛算出來的索引！
```

`case 0xa` 的反編譯片段（`FUN_222f_0b0e` 內，`decompiled_all.c` 對應行，已核對）：

```c
case (byte *)0xa:
  if (*(char *)(struct+0xa5) != '\0') {
    // 把 (類別<<5)+1 寫回剛才匹配到的 EXITS.DAT 記錄本身（0x52f8 是 FUN_222f_1321 存的匹配記錄指標）
    *(char *)(*(undefined4 *)0x52f8 + 2) = (char)(*(int *)0x5c62 << 5) + '\x01';
    if (*(char *)(struct+0xa5) != '\x03') {
      *(undefined1 *)(struct+0xa5) = 0;
      return (byte *)0x2;                 // 續接旗標不是3：這次不進DATA*.TXT，直接回傳
    }
    local_14 = (byte *)0x1;               // 續接旗標==3：這次要用「延續模式」呼叫
  }
```

- `FUN_25be_0e77` 的第二參數（`param_2`）就是這個「延續模式」旗標，跟 `docs/re/02` §2.4[F]

- `case 0xa` 執行時會**把 `(類別<<5)+1` 寫回記憶體裡匹配到的那筆 `EXITS.DAT` 記錄的 `type_byte`
  欄位**——這是「消耗/標記已觸發」的機制：觸發後子值被強制改成 1，配合 `FUN_222f_0a90` 對子值的
  判斷（`類別!=1 || 子值==0` 才略過），可以讓某些類別的事件「觸發一次後不再重複觸發」。這只改
  **記憶體裡的副本**，不寫回磁碟檔案，符合「每次重新進入這個 dataset 都會用 §3 的機制重新載入
  一份乾淨的 `EXITS.DAT`」的設計（見下）。

## 3. `EXITS.DAT` 的角色（修正 + 擴充）與 dataset 切換機制

### 3.1 `EXITS.DAT` 不是靜態全域表，而是「當前 dataset 專屬」且會被覆寫

在追蹤 `EXITS.DAT` 載入呼叫的所在函式時，發現載入呼叫**不是獨立函式**，而是包在一個明顯更大的
「dataset（地城）切換」函式裡：

```
FUN_222f_32d4 @ 222f:32d4, 510 bytes
```

完整反編譯（`decompiled/222f_32d4_FUN_222f_32d4.c`）：

```c
undefined2 __cdecl16far FUN_222f_32d4(void)
{

                  table[iVar1*4+0x551c],            // ★ dst = 每個 dataset 各自的快取槽（陣列，4筆）
```

> **三處更正（`docs/re/77`）：**
> 1. **`FUN_307c_0005` 的參數方向本節註反了。** 反編譯裡是
>    `*(undefined1 *)param_2 = *(undefined1 *)param_1` —— **`param_1` 是來源、`param_2` 是目的**。
>    所以這一處是把 `0x5514` 的內容**存出去**到 per-dataset 快取槽，不是載入進來。
>    對照組：`0x16024` 的同一支呼叫方向相反（槽 → `0x5514`），是**還原**。
>    `ds:0x5c52[i]` 就是「槽 i 有沒有快取」的旗標。
> 2. **`struct.a9` 與「自動接續重繪」無關。** `docs/re/02` 全文沒有 `+0xa9` ——
>    那句「docs/re/02 已知的」是**假引用**。它是 `nSS.DAT` 的快取有效性旗標。
> 3. 搬的是 `nSS.DAT`（511 bytes），不是 `EXITS.DAT`（330 bytes）。

**已驗證**（`FUN_307c_0005` 反編譯確認是遠指標記憶體複製函式，非壓縮/RLE，見
`decompiled/307c_0005_FUN_307c_0005.c`）：

1. `EXITS.DAT`（`0x5514:0x5516`）**每次 dataset 切換時，內容會被 `FUN_307c_0005` 從一個「per-dataset
   來源指標表」（`0x551c` 起，4 筆槽位，每 dataset 一份）複製覆蓋**——也就是說，現在磁碟上這一份
   `EXITS.DAT`（330 bytes）**只是目前這個 dataset 專屬的一份資料**，不是「全部 7 個地城共用的單一
   330 bytes 大表」。§1.4 驗證用的 330 bytes 是遊戲資料目錄裡靜態存在的那一份，對應**某一個特定
   dataset**（哪一個未進一步確認，見 §4 未解）。
2. 存在**另一張獨立的 6-byte 記錄表**（載入到 `[0x4c94]`），用來查「給定目前的錨點座標 `struct.a1/a2`，
   下一個 dataset index 跟新錨點座標是什麼」——這是**跨地城/跨 dataset 的轉換表**，跟 §1 的
   3-byte 表（同一 dataset 內部的座標→事件表）是**完全不同的資料結構、不同用途**，只是共用了
   `0x4c94` 這個暫存指標全域（見 §1.3 警語，這裡是另一個具體案例）。
3. `struct+0xa3`（`docs/re/02` 已知的 dataset index 欄位，1–5，`FUN_25be_0e77` 開頭讀取用來組
   `DATA%d.TXT` 檔名）**正是在這裡被設定**——`docs/re/02` §2.6 留的「struct 0x4c76+0xa3 這個欄位
   本次沒有系統性盤點其他寫入點」的缺口，本文補上其中最關鍵的一個寫入點。

### 3.2 綜合角色定義

`EXITS.DAT`（以及它背後的 per-dataset 來源資料）同時扮演兩層角色：

- **同一 dataset 內**：3-byte 記錄表，`(X,Y) → 事件類別 + DATA*.TXT 索引`（§1，逐步移動時查）。
- **跨 dataset**：（透過另一張 6-byte 表，非 `EXITS.DAT` 本身，但由同一個切換函式管理）
  `(舊錨點X,Y) → 新 dataset index + 新錨點座標`，在玩家跨越地城邊界時觸發（§3.1）。

`docs/formats/town-and-map.md` §3「假設：165 筆 (X,Y) 座標對」的推測，本文用反組譯 + 真實資料
**修正為：110 筆 3-byte 記錄 `(X, Y, type_byte)`**，且進一步指出這份資料是**per-dataset、會被
執行期覆寫**的，不是靜態全域表（見 §5 修正總表）。
