# 34 — 3×3 陣型格

存檔 trailer 開頭那九個 byte，`docs/formats` 一直標著「**假設**是隊形/順序表，
排列方式的實際意義未解」，長度還猜成 10。這一篇把它釘死。

**它是一張 3×3 的陣型圖**，九個格子各存一名成員的編號，`0xFF` 是空格：

```
Positions:
   A B C      格號 0 1 2
   D E F      格號 3 4 5
   G H I      格號 6 7 8
```

| 存檔 | 內容 | 陣型 |
|---|---|---|
| `PARTY.DAT` | `00 ff 01 ff 02 ff 03 ff 04` | 五人散在 A C E G I，隔一格站一個 |
| `PARTY.BAK` | `00 01 02 03 04 ff ff ff ff` | 擠在前五格 |

---

## 1. 四個呼叫端

長度是 9 不是 10 —— 四處的迴圈上界都是 `cmp ax,9 / jl`。第 10 個 byte
（trailer `+0x09`）是另一回事；後續全檔 consumer 稽核確認這份 DOS
執行檔不使用它，列為保留 byte（`docs/re/112`）。

| 位址 | 做什麼 |
|---|---|
| `1000:0379` | **Reorder**：清空九格，再逐一問每個人站哪裡 |
| `0x14af2` | **離隊**：清掉該員的格子，並把編號比他大的往前挪 |
| `0x15089` | **入隊**：找第一個空格塞進去 |
| `0xc615` | **佈陣**：把格號換算成相對座標 |

四個湊在一起才是完整的證據鏈。單看 Reorder 只知道「有人在編這張表」，
看到離隊那一段**把大於離開者的編號整批減一**，才確定格子裡存的是
「成員在隊伍陣列裡的索引」而不是別的識別碼 —— 索引會因為別人離隊而位移，
其他任何識別碼都不會。

---

## 2. Reorder（`1000:0379`）

```
0380  清畫面
0385  印 "   Reorder" / "Positions:" / "   A B C" / "   D E F" / "   G H I"
03c6  for i := 0; i < 9; i++ { party[i] = 0xff }        ; ★ 整張表清掉
03e1  for member := 0; member < party[+0x9a]; member++ {
03e9    把名字複製到 buffer，補空白到第 11 格，接上 "at "
0479    [0x4c7c] = member + 0x14                        ; 游標列
0488    印 "名字        at ?"
0495    ch = getkey() − 10                              ; 10='A' … 18='I'
04a5    ch < 0 或 > 8 → 重問
04b4    party[ch] != 0xff → 重問                        ; 那一格有人了
04c2    回顯字母
04e0    party[ch] = member                              ; ★ 寫進去
04ed    row = ch / 3, col = ch % 3
04f6    [0x4c7c] = row + 0x16、[0x4c82] = col×2 + 3      ; 網格上的位置
0506    在網格印 member + '0'
      }
0532  清畫面，結束
```

**Reorder 不是「交換兩個人」，是整張表重填。** 先把九格清光，再照隊伍順序
一個一個問。中途沒有確認步驟，也不能跳過某個人 —— 問完最後一個人就結束。

`getkey() − 10` 那一手值得記：`0xd9f:2231` 回傳的是**36 進位的字元值**
（`0`–`9` → 0–9，`A`–`Z` → 10–35），減 10 正好把 `A`–`I` 換成格號 0–8。
不是 ASCII，所以別拿 `− 'A'` 去對。

---

## 3. 離隊與入隊

```
14ae4  party[+0x9a]--                       ; 人數減一
14af2  for i := 0; i < 9; i++ {
14af9    if party[i] == 離開者 → party[i] = 0xff
14b0e    if party[i] != 0xff && party[i] > 離開者 → party[i]--
       }
```

```
15089  for i := 0; i < 9; i++ {
15090    if party[i] == 0xff { party[i] = party[+0x9a]; break }   ; 新人的編號就是舊人數
       }
```

入隊那一段順帶確認了 **`party+0x9a` 是隊伍人數**，而且新成員的索引就是
加入前的人數 —— 隊伍陣列是緊密排列的，沒有空洞。

---

## 4. 佈陣（`0xc615`）—— 讀出來了，但還沒接

```
c5fa  格號 = 0
c600  for row := −1; row <= 1; row++ {
c608    for col := −1; col <= 1; col++ {
c615      成員 = party[格號++]
c621      == 0xff → 跳過
c634      char[+0x102] >= 5（死亡）→ 跳過
c643      圖塊 = 0x14 + 面向×2（依 char[+0xf6] 再 +8 或 +0x10）
c68f      地圖緩衝[row×64 + col + 0x34d] = 圖塊
c6b0      單位[成員].圖塊 = ...
c6ba      單位[成員].X = col + 0x0d
c6c4      單位[成員].Y = row + 0x0d
       }
```

**`0x34d` = 845 = 13×64 + 13** —— 就是 64 寬緩衝裡的座標 (13, 13)。
所以佈陣是「以 (13,13) 為中心，把 3×3 陣型原樣攤開」。

**本專案沒有接這一段。** 理由是中心點對不上：這裡的戰場是一個 64 寬的緩衝、
中心在 (13,13)，而本專案的戰場網格是 9×9（`docs/re/06` 由視線遮蔽表推出，
證據獨立且紮實）。兩者要嘛是不同的東西，要嘛 9×9 是 64 寬緩衝裡的一塊視窗
—— 沒查清楚之前，硬把 `(13+col, 13+row)` 塞進 9×9 只會得到一組看起來
能跑、其實沒有依據的座標。目前戰鬥仍照 `PlayerSlotStart + i` 排成一直行。

**這是下一輪該追的事**：`0x4fbe`／`0x4fc0`／`0x4fd4` 這組 38 bytes 一筆的
結構，與 `docs/re/20` 記載的 `0x4eb4`（戰場 X）平行陣列是什麼關係。

## 5. 本專案的實作範圍

- `internal/assets/scenario`：`SaveGame.Formation [9]byte`（原 `FormationOrder [10]`）
  ＋新分出來並原樣 round-trip 的 `Reserved09`
- `internal/game/formation.go`：`Formation`、`CellLabel`／`ParseCellLabel`、
  `Clear`／`Place`／`Occupied`／`CellOf`、`RemoveMember`／`AddMember`、
  `FormationOffset`
- `cmd/demonwinter/campreorder.go`：紮營選單按 `R` 排陣型

介面上有一處刻意的偏離：**格子裡印名字，不印成員編號**。原版印的是
`成員編號 + '1'`，那要對照隊伍名冊才知道是誰；中文介面沒有理由保留那層抽象。

實機驗收（`workplace/dump/persist/47`–`49`）：把五個人依序放進 A–E 再存檔，
trailer 前九個 byte 變成 `00 01 02 03 04 ff ff ff ff` —— 與 `PARTY.BAK`
的排法完全一致（那份存檔顯然就是這樣排出來的），其餘 byte 沒有被動到。

**沒實作**：把陣型接到戰鬥擺位（見 §4）、離隊／入隊的入口（規則層已備妥，
但本專案還沒有隊伍增減的流程）。
