# 77 — `nSS.DAT` 是子地圖的特殊格清單，`+0xa9` 是它的快取旗標

`CONTEXT.md` §7 的 B8 剩一項：`party+0xa9` 的第二個設值點。
把 16 處存取全掃出來之後，答案連帶推翻了兩份文件的判讀 ——
`FUN_222f_1321` 掃的那塊緩衝區**不是 `EXITS.DAT`**，
而 `nSS.DAT` 也不是「開場序列資料」。

---

## 1. `+0xa9` 的完整普查（16 處）

掃法：ModRM `mod=10`（disp16）＋ 目標位移 `0x00a9`，
不靠線性反組譯對齊（線性掃描會在資料段錯位，漏掉大半）。

| 動作 | 處數 | 位址 |
|---|---|---|
| 寫 `0` | **12** | `0x053bf` `0x0b129` `0x1441d` `0x15184` `0x1702c` `0x17077` `0x170c2` `0x1710c` `0x18492` `0x19333` `0x1bea8` `0x1c0a0` |
| 寫 `1` | **2** | `0x160a4`、`0x19361` |
| `cmp 0` | 1 | `0x15f88` |
| 讀進區域變數 | 1 | `0x0e20c`（**死碼**，讀進 `[bp-0xc]` 之後沒人用）|

> `CONTEXT.md` §7 原本記「14 處清 0」是**多算了兩處** ——
> 把 `cmp 0` 與那個死讀也算成清 0 了。實際是 12。

---

## 2. 唯一有作用的判斷：`0x15f88`

在頂層函式 `222f:0003`（`0x15ef3`，`docs/re/51` 說的外層主迴圈那一支）裡：

```
15f88  cmp party[+0xa9], 0
15f8e  je  15f93                       ; == 0 → 走載入
15f90  jmp 160be                       ; != 0 → 跳過載入

; ---- +0xa9 == 0：這一格的資料還沒進記憶體 ----
15fc3  ax = FUN_222f_28d0(子地圖, 0)
15fd4  if (ax != 0) {                   ; 海圖：不讀檔，現場生成
15fd6      [0x4c90][0] = [0x4c90][1] = 5
15fe7      memset([0x4c94], 0x14, 0x1000)     ; 4096 格全鋪 tile 0x14
15fff      call 25be:17c0                     ; 隨機把其中一半換成 0x62
16004      call 25be:1782                     ; 存地圖（0x4c94 → 0x4c8c）
       }
16009  if (子地圖 >= 10) goto 1609f     ; 大地圖／城鎮：沒有特殊格清單
16012  i = 子地圖 − 1
1601d  if (ds:[0x5c52 + i*2] != 0) {
16024      FUN_307c_0005(src = [0x551c + i*4], dst = [0x5514], 0x1ff)
1604d      goto 1609f                   ; 快取槽有 → 從記憶體還原
       } else {
1604f      sprintf(&local_2c, ds:0x2011, 子地圖)     ; "%dSS.DAT"
16064      do {                                      ; 從磁碟載入
               r = FUN_1d9f_0a8b(0x522a, &local_2c, [0x5514], 511L)
               if (r != 0) FUN_1d9f_19fe(0)
           } while (r != 0)
       }
1609f  les bx, [0x4c76]
160a3  party[+0xa9] = 1                 ; ★ 設值點一
160a9  if (子地圖 > 9) ds:0x5c60 = [0x4c90][1]
160bc  goto 160c3

; ---- +0xa9 != 0：資料已經在記憶體 ----
160be  call 25be:1765                   ; 還原地圖（0x4c8c → 0x4c94）
160c3  （繼續）
```

**`+0xa9` ＝「當前子地圖的特殊格清單已經在 `0x5514` 緩衝區裡」。**

12 處清 0 的時機全部是「位置變了」（跨子地圖、傳送、神殿樓梯、
`docs/re/08` §460 的進新樓層、`docs/re/15` §290 的法術傳送）——
清掉就是**強迫下一輪重新載入**。這不是遊戲狀態，是**快取有效性旗標**。

> 對引擎的意涵：`+0xa9` 存在 `PARTY.DAT` 裡，但**沒有遊戲語意**。
> Go 引擎不需要模擬它 —— 除了 §4 那個例外。

### 兩支互為鏡像的地圖備份函式

`FUN_307c_0005` 的反編譯（`workplace/ghidra/export/decompiled/307c_0005_FUN_307c_0005.c`）
裡是 `*(undefined1 *)param_2 = *(undefined1 *)param_1`：
**`param_1` 是來源、`param_2` 是目的**。照這個方向讀：

| 位址 | 呼叫 | 方向 | 語意 |
|---|---|---|---|
| `25be:1765`（`0x1af45`）| `FUN_307c_0005([0x4c8c], [0x4c94], 0x1000)` | 備份 → 現用 | **還原**地圖 |
| `25be:1782`（`0x1af62`）| `FUN_307c_0005([0x4c94], [0x4c8c], 0x1000)` | 現用 → 備份 | **存**地圖 |

`0x4c94` 是現用的 64×64 tile 陣列（`docs/spec/04-movement.md` 已驗證），
`0x4c8c` 是它的備份。4096 ＝ 64×64，數字自己對上。

## 3. `0x5514` 裝的是 `nSS.DAT`，不是 `EXITS.DAT`

這是本篇最關鍵的一條，因為它推翻 `docs/re/05` §1.3／§1.4 的結論。

| | `EXITS.DAT` | `nSS.DAT`（1–5）|
|---|---|---|
| 檔案大小 | 330 | **511** |
| 載入目的 | `[0x4c94]`（`docs/re/05` §1.3 逐行核對過）| **`[0x5514]`** |
| 載入處 | `222f:338e`，大小參數 `0x14a` = 330 | `0x16064`，大小參數 `0x1ff` = **511** |
| 記錄長度 | 6 bytes（330 = 55×6）| 3 bytes |

`FUN_222f_1321`（`0x17211`）掃的是 `[0x5514]`，stride 是 `addw $0x3,-0x4(%bp)`
（`0x172ea`）—— **3 bytes**。而 `FUN_222f_32d4` 在 dataset 切換時
用 `FUN_307c_0005` 搬的也是 `0x1ff` ＝ 511 bytes。

**511 這個數字只有 `nSS.DAT` 對得上。** 兩邊都是 511，不是巧合。

`docs/re/05` §1.3 之所以誤判，是因為它從 `"EXITS.DAT"` 字串反查到
`FUN_222f_32d4` 裡的載入呼叫（那一處確實是 EXITS.DAT → `[0x4c94]`），
然後假設同一支函式裡的 `0x5514` 也指向同一份資料。
但那支函式對 `0x5514` 做的是**搬進搬出**，不是載入 ——
真正的載入端在**另一支函式**（`222f:0003`），檔名是 `"%dSS.DAT"`（`ds:0x2011`）。

### 連帶推翻：「類別 3–7 永遠走不到」

`docs/re/05` §1.4 拿 330 bytes 的 `EXITS.DAT` 驗 3-byte 假說，得到
「全檔最大 byte ＝ 64，所以類別最多到 2，類別 3–7 的分支程式碼存在但走不到」。

**拿對的檔案重驗，類別 0–6 全都出現：**

| 檔案 | 記錄數 | 類別分布 |
|---|---|---|
| `1SS.DAT` | 68 | `{0:4, 1:17, 2:18, 3:5, 4:2, 5:21, 6:1}` |
| `2SS.DAT` | 32 | `{1:6, 2:6, 3:8, 5:12}` |
| `3SS.DAT` | 38 | `{1:8, 2:18, 3:1, 4:7, 5:4}` |
| `4SS.DAT` | 28 | `{1:8, 2:13, 3:1, 4:3, 5:3}` |
| `5SS.DAT` | 20 | `{1:2, 2:9, 3:2, 4:2, 5:5}` |

那份 330 bytes 的 `EXITS.DAT` 本來就不該用 3-byte 去讀 ——
它是 6-byte 表（55 筆），`docs/re/05` §3 自己的 6-byte 判讀才是對的那一份。
**同一篇文件用兩種 stride 讀同一個檔案，其中一種必然錯。**

## 4. `nSS.DAT` 格式（本篇新增）

```
偏移 0 起，往後長：3-byte 記錄  (X, Y, attr)      X == 0 表示結束
偏移 510 起，往前長：2-byte 座標對  (X, Y)        供類別 4 使用
attr = (類別 << 5) | 值            類別 = attr >> 5，值 = attr & 0x1f
```

`FUN_222f_1321(X in ds:0x52f4, Y in ds:0x52f6)` 線性掃描：

- 沒命中：類別 1／2 → `local_c++`；類別 4 → `local_a++`；指標 +3 繼續
- 表尾（`X == 0`）→ 回 `0xff`
- 命中：`ds:0x52f8/0x52fa` ← 記錄指標、`ds:0x52f4` ← `local_c`、
  `ds:0x52f6` ← `attr & 0x1f`、`ds:0x5c62` ← 類別
  - 類別 1／2：`ds:0x52f4++`（序號變 1-based）
  - 類別 4：`k = local_a`，從 `[0x5514][0x1ff − (k*2 + 2)]` 取兩個 byte
    覆寫 `ds:0x52f4/0x52f6` —— **傳送目的座標**

### 反向尾表的可驗證推論

類別 4 的第 `k` 筆用尾表第 `k` 對（`k` 從檔尾往前數）。
所以**類別 4 的筆數必須等於尾表非零對的個數**。五個檔案全對：

| 檔案 | 類別 4 筆數 | 尾端非零 pair | |
|---|---|---|---|
| `1SS.DAT` | 2 | 2 | ✓ |
| `2SS.DAT` | 0 | 0 | ✓ |
| `3SS.DAT` | 7 | 7 | ✓ |
| `4SS.DAT` | 3 | 3 | ✓ |
| `5SS.DAT` | 2 | 2 | ✓ |

可重跑：`python3 tools/parse_nssdat.py`。

**5/5 零誤差。** 這比「反組譯讀起來合理」強一個等級 ——
它是一個會被資料打死的預測。

`5SS.DAT` 還給了語意上的旁證：兩筆類別 4 互為往返，
而且目的地都**差一格**（踩上去不會立刻被彈回來）：

```
(28,59) → (11,5)        (11,4) → (28,58)
```

`1SS.DAT` 的兩筆不對稱（`(18,39)→(21,38)`、`(36,8)→(30,49)`），
所以**不是每筆都是雙向樓梯**，有單向長距離跳躍。

### ⚠ 實作警告：配對規則是序號，不是「就近」

`3SS.DAT` 看起來很像在暗示另一種讀法：

```
 觸發              序號配到的目的      而「看起來該配」的
 [0] ( 8,23)  →  (10,23)   ✓ 相鄰
 [1] (57, 4)  →  (39,28)               (56, 4) ← 在 [3]
 [2] (40,28)  →  (55,19)               (39,28) ← 在 [1]
 [3] (56,19)  →  (56, 4)               (55,19) ← 在 [2]
```

**七個目的座標各自都跟某個觸發格相鄰**，但序號把它們配得交叉。
很容易因此推論「配對其實是找最近的那一個」——**不要**。
指令讀得很明確（`0x1729a`–`0x172b0`）：偏移 ＝ `0x1ff − (k*2 + 2)`，
`k` ＝ 掃到這一筆之前經過的類別 4 筆數（`0x172e7` 的 `inc`）。
就是**序號配序號**。

那 3SS 的交叉是什麼？是**原版的資料就長這樣** ——
當年填目的表的人順序跟觸發表不一致。照序號實作會複製這個行為，
照「就近」實作會**修掉原版的怪異之處**，那就不是還原了。
（`rulebook/82`：移植的正確性是對齊原版，不是對齊常理。）

### 類別的語意（部分）

類別 1／2 回一個 1-based 序號，而 `docs/re/05` §1.2 已經追到
`FUN_25be_0e77` 用同一個 `ds:0x52f4` 當「第幾筆記錄」——
那就是事件文字的索引。類別 4 是傳送。
**類別 0／3／5／6 尚未追**（`5` 在 `1SS.DAT` 裡有 21 筆，最常見的一類）。

## 5. `+0xa9` 的第二個設值點：`0x19361`

`FUN_222f_32d4`（dataset 切換）的尾巴。這一段 `docs/re/05` §3
**已經有完整反編譯**，本篇只補一句它沒說的：

```c
struct.a9 = 0;                                  // 位置變了 → 快取失效
if (struct.a3 != 5 || struct.a1 < 0x24) return 1;
struct.a9 = 1;                                  // ★ 設值點二
local_6 = struct.a1 - 0x1b;
if (local_6 == 0x21) { FUN_222f_1404(0x38,0x11); local_6 = 0xc; }
if (local_6 == 0xf)  local_6 = 10;
if (local_6 == 0x16) local_6 = 0xd;
FUN_25be_1694(local_6);
if (local_6 == 0xc) return FUN_25be_000c();
```

進 dataset 5 且 X ≥ 0x24(36) 時把 `+0xa9` 設成 1，是**刻意讓
`222f:0003` 跳過 `%dSS.DAT` 的載入** —— 這一塊寫死的場景自己
用 `FUN_25be_1694(X − 27)` 決定要畫什麼，不走特殊格清單。

所以「`+0xa9` 沒有遊戲語意」有一個例外：**這個旗標是那段場景
用來關掉一般機制的開關**。Go 引擎照抄行為的話，這一格不能省。

## 5.5 為什麼要有快取：這張表會被**改寫**

到這裡還缺一塊 —— 純唯讀的表根本不需要 per-dataset 快取，重讀檔就好。
答案在 `ds:0x52f8`（`FUN_222f_1321` 命中時存下的**記錄遠指標**）：

| 位址 | 動作 | 意思 |
|---|---|---|
| `0x178a6` | `記錄[2] = 0` | **屬性清零 → 這一格再也不會命中**（一次性事件用掉了）|
| `0x1788e` | `if (記錄[2] < 0xc1) 記錄[2] += 0x60` | `0x60 = 3 << 5` → **類別 +3**，狀態推進 |
| `0x1a623` | `記錄[2] = al` | 直接改寫屬性 |

**特殊格清單是可變的。** 事件觸發後就地改掉自己那一筆。
於是整條因果鏈閉合：

```
進子地圖 n → +0xa9 == 0 → 載入 nSS.DAT（或從快取槽還原）→ +0xa9 = 1
    ↓
玩家踩到特殊格 → FUN_222f_1321 命中 → ds:0x52f8 存下記錄位址
    ↓
事件執行完 → 透過 ds:0x52f8 改寫該筆（清零／類別 +3）
    ↓
離開 → 存回快取槽 [0x551c + i*4]，ds:0x5c52[i] = 1
    ↓
回來 → +0xa9 已清 0 → 從快取槽還原（不是重讀磁碟）→ 改過的狀態留著
```

`+0xa9` 不是可有可無的最佳化：**少了它，回頭走一趟就會把已觸發的事件復活。**

## 6. 順帶收掉 B8 的另外兩欄：`+0xbe` 與 `+0x99`

同一支掃描器換個位移就能跑，所以順手把 B8 剩下的兩欄一起做了。

### `+0xbe` ＝ 一次性劇情的完成閂鎖

11 處存取，**兩處寫 `1`，沒有任何一處寫 `0`**：

| 動作 | 處數 | 位址 |
|---|---|---|
| `cmp` | 8 | `0x053c9` `0x11f8d` `0x15f7c` `0x15fb7` `0x163bb` `0x18a97` `0x19136` `0x1a550` |
| 讀 | 1 | `0x18a49` |
| 寫 `1` | **2** | `0x1b2ef`、`0x1b459` |

**沒有清除端 → 設下去就永遠是 1。** 這一句本身就定案了語意：
它是「這件事做過了」的**單向閂鎖**，不是狀態機也不是計數器。

`docs/re/65` 的地點劇情跳表 case 14（`0x1a54b`）：
`+0xbe != 0` 就回 3（這一步什麼都不做），否則呼叫 `25be:1ae2`。
而 `25be:1ae2` ＝ **`0x1b2c2`**，正好是包住那兩個設值點的函式
（下一個函式開頭在 `0x1b4dc`，所以兩處都在同一支裡）。

閉環：**case 14 → 沒做過就跑 `25be:1ae2` → 該函式兩個出口都把 `+0xbe` 鎖上 → 之後永遠回 3。**

> 這支函式**沒有任何字串引用**，所以「是哪一段劇情」還沒有名字。
> 要追 `1d9f:1846`／`1cdc:20b7`／`25be:19d1` 才知道它演什麼。

### `+0x99` ＝ 同一件事的第一趟旗標

3 處存取，**全部在 `25be:1ae2` 這一支函式裡**：

```
0x1b4ca  party[+0x99] = 1        ; 第一趟：武裝
0x1b2dd  if (party[+0x99] == 1)  ; 第二趟：認出來了
0x1b2e5      party[+0x99] = 0    ;   用掉
0x1b2ef      party[+0xbe] = 1    ;   鎖上，不再發生
```

**這是一件兩趟才完成的劇情**：第一次踩上去把 `+0x99` 立起來，
第二次踩上去才真的結束並上鎖。因為 `+0x99` 在 `PARTY.DAT` 裡，
中間可以存檔離開再回來。

> `+0x99` 緊貼在符印旗標 `+0x96`／`+0x97`／`+0x98` 後面，**但不是第四個符印**。
> 掃描順帶佐證了符印那三格的結構：寫入是 `[bx+si+0x0096]`（`0x6bb9`，索引式），
> 讀取是三個獨立位移（`0x16b64/6e/78` 與 `0x1a56a/72/7a` ＝ 光之環的門），
> 跟 `docs/re/59` 一致。**相鄰的欄位不代表同類**（`docs/re/76` §4 同一條）。
