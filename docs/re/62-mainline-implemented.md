## 2. 第四方驗證：地圖資料

`tools/glyphscan` 解壓 `SUM.MAP` 掃 tile `0x63`：

```
子地圖 55 (0x37)  X=47 Y=22
子地圖 56 (0x38)  X=20 Y=45
子地圖 66 (0x42)  X=50 Y=47
```

**整個世界只有這三格**，而且正好落在反組譯讀出的那三張子地圖。

到目前為止指向同一組座標的獨立來源有四個：

1. `222f:0b0e` 的劇情檢查（子地圖 `0x37`／`0x38`／`0x42`）
2. `0x6b35` 的索引映射（`− 55`，66 特判成 2）
3. 攻略「東南角火山，三塊狹長陸地各有一個符印」
4. **地圖資料本身**

順帶對上 `docs/re/58` §3 的分段：子地圖 56 的符印在 `Y=45`，
落在那裡三段判定的**南段**（`Y > 0x16` ＝ 22）。

## 3. 四處刻意的差異

### 3.1 切換條件是本專案的決定

原版把 UNCURSE／IMPRISON 換進施法選單的**條件還沒反組譯出來**
（`docs/re/61` §5：掃過 `0x6300`–`0x6a14` 的近跳全部沒命中）。

本專案的條件是依機制推導的：

- 腳下是 tile `0x63` 且在三張符印子地圖之一 → 給 UNCURSE
- 子地圖 `5` 或 `Y ≤ 6`（＝禁錮判定過得了的地方）→ 給 IMPRISON

**這是設計決定，不是反組譯結論。** 等切換條件解出來要換掉。

### 3.2 光之環的門在移動前擋，原版在移動後推開

原版是走進去之後才判定，擋下時把玩家推回：
`if (party[+0xa1] == 0x0b) party[+0xa2] = 0x36 − (面向×2 + 2)`。

本專案在 `Walk` 之前擋。**玩家看到的結果一樣**（進不去、收到同一句提示），
省掉「推開」那段。差異記在這裡，不是漏做。

### 3.3 兩個門檻刻意不統一

```go
CircleOfLightOpen  → flags[i] != 0      // 擋門（0x1a569）
GlyphActive        → flags[i] < 0x80    // 傷害（222f:0b0e）
```

原版這兩處判斷本來就不一樣。中間值（1–0x7f）在原版資料裡不存在，
所以實務上等價 —— **但不要為了「看起來一致」把它們合併**，
那會把原版的兩個獨立判斷變成一個推論。

### 3.4 IMPRISON 的「先扣費再檢查地點」照抄

在錯的地方施放，100 點法力照樣沒了（`0x6bfb` 扣費、`0x6c07` 才檢查）。
這看起來像 bug，但攻略叮嚀「先備份 `PARTY.DAT`」正是為此 ——
**它是原版行為的一部分，刻意保留**。測試釘住了這一點。

UNCURSE 相反：法力檢查在扣費之前（`0x6aef` 早於 `0x6b8e`），不會白扣。
兩個動作不一致也照抄。

## 4. 實機驗到哪

`workplace/dump/persist/74-glyph-uncurse.png`

```bash
tools/screenshot.sh out.png KEYS=Return,r,c,Return,Down×11,Return \
  -map=55 -x=47 -y=22 -sp=120
```

| 驗到的 | 畫面 |
|---|---|
| 「解咒」**只在符印上出現** | 不在符印時施法選單沒有這一項 |
| 花費顯示 50 | 「解咒　最低 50 點」 |
| 法力不足正確拒絕 | 「那需要 50 點法力」（起始隊伍最高 29）|
| **解除成功** | 「力量閃現，符印的魔法被摧毀了」 |

`-sp` 這個偵錯旗標是為了這次驗收才加的 —— 起始隊伍最高 29 點法力，
連第一個符印都解不掉，沒有它就驗不到成功路徑。

**還沒實機驗到**：光之環的門、IMPRISON 的三種結果。
那需要先把三個符印都解掉再走到子地圖 5，下一輪做。
