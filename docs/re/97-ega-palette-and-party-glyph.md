# 97 — 原版自己換掉了 EGA 調色盤；以及隊伍圖示是一個地形圖塊

使用者看 README 的截圖說「tileset 或 sprite 沒有解析正確，部分對部分怪」。
查下來**解碼從頭到尾都是對的**，錯的有兩層，都在呈現側：

1. 引擎載入的是 **CGA** 素材（`DEMON.SHP`，16×16 四色），
   EGA 的 `DEMON.SHE` 解碼器早在 `docs/formats/graphics.md` §4 寫好卻沒接上。
2. 就算接上，**也不能用標準 EGA 16 色表** —— 原版開機時把 16 個調色盤暫存器整組換掉了。

第 2 點是這一篇的主題。它讓一整批**正確解出來的地形圖塊看起來像雜訊**，
因此連帶造成 §4.4 那條「102 格全是地形圖塊集」的錯誤斷言。

---

## 1. 調色盤：`ds:0x14b7`

**表本體**（`DEMON.INT` 檔位移 `0x26fb7`，16 bytes，全部 ≤ `0x3f`）：

```
00 3c 02 26 0b 0a 01 07 30 1b 27 04 30 36 2c 3f
```

**設定常式**（`2cdc:16b7` ＝ 檔位移 `0x22077`，手動反組譯 ——
Ghidra 這一段沒建函式邊界）：

```asm
2cdc:16b7  55              PUSH BP
           8b ec           MOV BP,SP
           83 c4 fe        ADD SP,-2
           56              PUSH SI
           83 3e fb 19 00  CMP word ptr [0x19fb],0    ; ← EGA 模式旗標
           74 26           JZ 收尾                     ; CGA 就整段跳過
           c6 46 ff 00     MOV byte ptr [BP-1],0      ; i = 0
           eb 1a           JMP 迴圈條件
迴圈本體:  c4 5e 06        LES BX,[BP+6]              ; 遠指標參數 ＝ 調色盤表
           8a 46 ff        MOV AL,[BP-1]
           98 8b f0        CBW / MOV SI,AX
           26 8a 00        MOV AL,ES:[BX+SI]          ; 表[i]
           98 50 56        CBW / PUSH AX / PUSH SI    ; (顏色值, 暫存器編號)
           9a 81 0a 7b 11  CALLF 217b:0a81            ; INT 10h trampoline
           83 c4 04        ADD SP,4
           fe 46 ff        INC byte ptr [BP-1]
迴圈條件:  80 7e ff 10     CMP byte ptr [BP-1],0x10   ; i < 16
           7c e0           JL 迴圈本體
```

**呼叫端**（`1d9f:1ac1`，緊接在 `INT 10h` 設完視訊模式之後）：

```asm
1d9f:1ac1  PUSH DS
1d9f:1ac2  MOV AX,0x14b7
1d9f:1ac5  PUSH AX
1d9f:1ac6  CALLF 2cdc:16b7
```

也就是 `INT 10h AH=10h AL=00h`（設單一調色盤暫存器）跑十六次。
`ds:0x19fb` 是 EGA 模式旗標 —— **CGA 模式不設**，那邊的四色是硬體固定組。

### 換算與驗收

EGA 6-bit 是 `r'g'b'RGB`（每通道 ＝ 主 `0xAA` ＋ 次 `0x55`）：

| idx | 6-bit | RGB | 畫面上是什麼 |
|---|---|---|---|
| 0 | `0x00` | `#000000` | 黑（未照明的地板、空格）|
| 1 | `0x3c` | `#FF5555` | 淺紅 |
| 2 | `0x02` | `#00AA00` | 綠（樹葉）|
| 3 | `0x26` | **`#FFAA00`** | 沙／平原（戶外畫面占比 51%）|
| 4 | `0x0b` | **`#00AAFF`** | 水 |
| 5 | `0x0a` | **`#00AA55`** | 深綠 |
| 6 | `0x01` | `#0000AA` | 藍 |
| 7 | `0x07` | `#AAAAAA` | 淺灰（石、泥縫）|
| 8 | `0x30` | **`#555500`** | 暗橄欖 |
| 9 | `0x1b` | **`#00FFFF`** | 亮青 |
| 10 | `0x27` | `#FFAAAA` | 膚色 |
| 11 | `0x04` | `#AA0000` | 紅 |
| 12 | `0x30` | `#555500` | 暗橄欖（**與 8 重複**，原版就是這樣）|
| 13 | `0x36` | **`#FFFF00`** | 黃 |
| 14 | `0x2c` | **`#FF0055`** | 深紅（磚）|
| 15 | `0x3f` | `#FFFFFF` | 白 |

粗體那七個**不在標準 EGA 16 色裡**（標準表對應位置是 `#AA5500`、`#FFFF55`、
`#55FFFF` 之類）。這是為什麼用標準表解出來會「沙地變黃、水變紅、樹幹變青」。

**驗收方法**（`rulebook/64` 的截圖 oracle）：用 DOSBox 抓原版 **原生 640×350**
截圖（`shot:` 用的 `import -window root` 抓到的是 1024×768 縮放，顏色不可信；
要送 `key:ctrl+F5` 讓 DOSBox 自己寫 `captures=` 目錄），把畫面上出現的顏色逐一取出來：

| 場景 | 取到的顏色 | 對上本表 |
|---|---|---|
| 戶外（地圖 34 的 (31,44)）| `#FFAA00 #00AAFF #00AA55 #00AA00 #000000 #555500 #AA0000 #FFFFFF #FFFF00 #AAAAAA #00FFFF #FF5555` | **12/12** |
| 地城（地圖 1 的 (9,32)）| 另加 `#FF0055`、`#FFAAAA` | 索引 14、10 |

**兩個互不相干的場景、14 種顏色，全部落在這 16 格裡，沒有一個落在外面。**

## 2. 怎麼找到它的（方法）

`0x3c0`（attribute controller）在反組譯裡**零命中**，`INT 10h` 的呼叫點也只看到
get/set mode。照舊會下「原版沒有換調色盤」的錯誤結論。

改成**掃資料而不是掃程式碼**（`rulebook/62`／記憶 `grep-constants-not-results`）：

1. 從原生截圖取出實際顏色，換算成 EGA 6-bit 值。
2. 掃全部檔案，找「16 個 byte 全部 ≤ `0x3f`，且同時含那幾個特徵值」的視窗。
   隨機資料命中機率約 `0.25^16 ≈ 2e-10`，所以命中就是它。
   → `DEMON.INT @ 0x26fb7`，唯一一處。
3. `grep "0x14b7"` 在反組譯裡**零命中** —— 這是記憶
   `search-before-digging` 那條「grep 落空永遠先懷疑查法」。改掃**機器碼位元組**
   （`b8 b7 14` ＝ `MOV AX,0x14b7` 等各種載入形式），四處命中，其中三處在
   `1d9f` 段、緊接在視訊模式初始化後面。

**先取輸出、再回推資料、最後才找程式碼**，比從程式碼正面追快得多。

### 一個先被自己否證的假設

一開始看到「海面解出來是紅色、樹幹解出來是青色」，推測是 **plane 順序反了**
（B,G,R,I vs I,R,G,B —— bit0↔bit2 對調正好把紅藍互換）。
兩個獨立現象指向同一個解釋，看起來很強。

**實測不成立**：反過來之後海變綠、森林變粉紅，比原本更糟。
真正的原因是調色盤而不是 plane 順序。教訓與記憶
`corrections-need-more-proof-than-claims` 同源 —— **兩個現象都能被同一個假設解釋，
不等於那個假設是對的**；跑一次比想三輪便宜。

## 3. 隊伍圖示是一個地形圖塊，不是疊在上面的裝飾

`CONTEXT.md` 記著「原版的隊伍 glyph 動畫表（`0x210f`）尚未解讀」。
它就在主迴圈開頭，`docs/re/96` 讀 `FUN_222f_0b0e` 時經過的那一段：

```asm
222f:0b85  CMP word ptr [0x52d4],0    ; 在船上？
222f:0b8a  JNZ 0x0bc1
222f:0b8c  MOV AX,[0x4e32] / AND AX,1 / CMP AX,1
222f:0b95  JNZ 0x0b9f
222f:0b97  MOV AX,[0x50f0] / MOV [BP-2],AX   ; 面向東西 → 取 X
222f:0b9d  JMP 0x0ba5
222f:0b9f  MOV AX,[0x50ee] / MOV [BP-2],AX   ; 面向南北 → 取 Y
222f:0ba5  MOV BX,[0x4e32]                   ; 面向
222f:0ba9  MOV AL,byte ptr [BX + 0x210f]     ; ← 走路 glyph 基底
222f:0baf  MOV CX,[BP-2] / AND CX,1
222f:0bb6  ADD AX,CX                         ; ＋ 座標奇偶 ＝ 兩格動畫
222f:0bb8  LES BX,[0x4c94]
222f:0bbc  MOV byte ptr ES:[BX + SI],AL      ; ← 寫進地圖繪製緩衝區
; 在船上那一支：
222f:0bc1  MOV AX,[0x4e32] / ADD AX,0x3f     ; 船 glyph ＝ 63 ＋ 面向
```

`ds:0x210f` 的原始位元組（檔位移 `0x26c0f`）是 **`1e 1b 18 21`**：

| 面向 | 基底 | 兩格動畫 |
|---|---|---|
| 0 北 | `0x1e` = 30 | 30、31 |
| 1 東 | `0x1b` = 27 | 27、28 |
| 2 南 | `0x18` = 24 | 24、25 |
| 3 西 | `0x21` = 33 | 33、34 |

搭船時是 `0x3f + 面向` ＝ **63–66**。

三件事跟著落定：

- **動畫用的是「行進軸上的座標奇偶」**，不是計時器：東西向看 X、南北向看 Y。
  走一步座標變一格，glyph 就換一次。若寫成「一律看 X」，南北向走動時
  畫面上會是滑行而不是走路。
- **glyph 走的是地形圖塊的同一條繪製路徑** —— 原版把索引寫進繪製緩衝區
  （`222f:0bbc`），所以隊伍那一格的地圖原始值（出貨存檔那格是 tile 17 ＝ 純黑）
  會被蓋掉。重製版照同一個分工：`drawWorld` 在中央那一格換 tile，不另外疊圖。
- **這推翻了 `docs/formats/graphics.md` §4.4** 的「`DEMON`／`WINTER` 的 102 格
  是地形圖塊集（已驗證）」。那 102 格**混著地形與 glyph**：
  24–34 是隊伍、63–66 是船。§4.4 的「與可通行性表 101 項對應」仍然成立
  （表對每個索引都有一格），但「每一格都是地形」不成立。

**版面沒有衝突**：EGA 一格顯示 32×28，CGA 是 16×16 放大兩倍 ＝ 32×32 ——
**格寬都是 32**，所以地圖視窗寬仍是 288，右側狀態欄那 21 個中文格不受影響。
只有地圖高從 288 變 252（下方多出 36 px 空白）。

CGA 保留而不是換掉，是完整性原則（`rulebook/83`）：那是原版的另一個發行版本，
不是畫質選項。

## 5. 照明：視窗固定 9×9，畫出來的範圍會往內縮

比對時發現原版只畫**一小塊**：同一個位置（地圖 1 的 (9,32)）原版只畫出隊伍
上方那一排，重製版卻畫滿 9×9。差的不是資料，是裁切。

繪圖常式 `FUN_222f_1404` 一開頭就用 `ds:0x4c86` 把四邊各縮掉那麼多格：

```asm
222f:1425  繪製緩衝區（ds:0x514e）整片清 0        ; tile 0 是純黑
222f:1440  Y 上界 = [BP+8] + 9 − [0x4c86]
222f:1450  [BP+8] += [0x4c86]                    ; Y 起點往內移
222f:1453  X 上界 = [BP+6] + 9 − [0x4c86]
222f:1463  [BP+6] += [0x4c86]                    ; X 起點往內移
222f:1466  起始緩衝位移 = ds:0x2208[[0x4c86]]      ; {0, 10, 20, 30, 40, 50}
```

所以「內縮 3」看到的是中央 3×3，其餘八成畫面是黑的 —— **那不是缺圖，是照明**。

`ds:0x2208` 那張 `{0,10,20,30,40,50}` 順帶證明緩衝區的 row stride 是 9：
內縮 i 要跳 i 列再跳 i 欄 ＝ `i×9 + i` ＝ `i×10`。

內縮量由**兩條互斥的規則**寫同一個 `ds:0x4c86`，分界是子地圖編號 10：

### 5.1 戶外（子地圖 ≥ 10）：查時辰表

```asm
222f:07bc  CMP byte ES:[BX+0xa3],0x0a / JC 跳過   ; 地城不走這條
222f:07c4  MOV AL,ES:[BX+0x9f]                    ; +0x9f ＝ 小時
222f:07cd  MOV AL,[BX + 0x209c]                   ; 查表
222f:07d3  MOV [0x4c86],AX
```

`ds:0x209c`（檔位移 `0x27b9c`）：
`02 02 02 01 01 00 00 00 00 00 00 00 00 00 01 01 02 02 03 03 …`

| 時 | 內縮 | 視野 | |
|---|---|---|---|
| 0–2 | 2 | 5×5 | 深夜將盡 |
| 3–4 | 1 | 7×7 | 黎明 |
| 5–13 | 0 | **9×9** | 白天 |
| 14–15 | 1 | 7×7 | 午後 |
| 16–17 | 2 | 5×5 | 黃昏 |
| 18 起 | 3 | 3×3 | 入夜 |

**戶外不看光源** —— 火把在白天沒有用，這是原版的分工。

### 5.2 地城（子地圖 < 10）：光源，而矮人 +1

```asm
222f:02a9  MOV word ptr [0x5c64],4
222f:02b3  CMP byte ES:[BX+0xa3],0x0a / JNC 跳過  ; 戶外不走這條
222f:02bb  MOV AL,ES:[BX+0xa7]                    ; +0xa7 ＝ 光源強度
222f:02c2  MOV [0x5c64],AX
222f:02c5  CMP word ptr [0x4e32],0 / JZ 0x02d5    ; ← 這個旗標是什麼？
222f:02cc  CMP AX,4 / JGE 0x02d5
222f:02d1  INC word ptr [0x5c64]                  ; 光源 +1
222f:02d5  MOV AX,4 / SUB AX,[0x5c64]
222f:02dc  MOV [0x4c86],AX                        ; 內縮 = 4 − 光源
```

**`ds:0x4e32` 在這支函式裡不是面向。** 那是它在移動程式碼（`222f:0b34`
從 `+0xa4` 載入）裡的用途；這個位址全檔有 **40 個寫入點**，橫跨戰鬥 `138d`、
`1990`、`17c5` 各段，是典型的共用暫存字。在 `FUN_222f_0003` 裡它是這樣算的：

```asm
222f:002c  MOV word ptr [0x4e32],0
222f:0032  for i := 0; i < 5; i++ {                ; 掃五個隊員（記錄 0x104 bytes）
222f:0043    CMP byte ES:[BX+SI+0xf5],0x2 / JNZ 下一個   ; +0xf5 種族，2 ＝ 矮人
222f:004b    CMP byte ES:[BX+SI+0x102],0x1 / JA 下一個   ; 戰鬥狀態 > 1 不算
222f:0053    MOV word ptr [0x4e32],1               ; ← 有活著的矮人
           }
```

**所以「黑暗視覺」這個矮人天生能力的實際效果就是「地城視野半徑 +1」**，
不是另一套照明機制。門檻是戰鬥狀態 `> 1` 不算 —— **束縛與死亡都不算，中毒還算**。

> 差點在這裡下錯結論：Ghidra 顯示 `CMP word ptr [0x4e32],0`，而 `0x4e32`
> 在 `docs/re/08` 是**已驗證的面向欄位**，於是差點寫下「面向北會讓視野變差」
> 這種讀起來很怪的結論。位元組核對（`83 3e 32 4e 00`）證實位址沒讀錯 ——
> 錯的是「同一個位址在不同函式裡語意相同」這個假設。
> `CONTEXT.md` §5 早就記著這個坑（`0x52f4` 是到處被重用的暫存字），
> 而**判別法就是數寫入點**：40 個寫入點、跨五個段，就不可能是專用欄位。

### 5.3 驗收

| 場景 | 光源／時辰 | 算出的內縮 | 原版畫面 |
|---|---|---|---|
| 地城，地圖 1 的 (9,32) | **光源 1、隊伍沒有矮人** | 3 → **3×3** | 只畫出上方 `(8,31)(9,31)(10,31)` ＝ 磚／暗橄欖／磚，其餘全黑 —— **逐格相符** |
| 戶外，地圖 34 的 (31,44) | 13 時 | 0 → **9×9** | 整個視窗都畫，與重製版相符 |

> ⚠ **這張表的第一列原本寫「光照 0，隊伍有三個矮人 → 光源 1」—— 兩個數字都錯**
> （2026-07-27 訂正）。出貨存檔用驗過的 `scenario.LoadSaveGame` 讀出來是
> **光源 1、五個人是精靈＋四個人類、沒有矮人**。錯誤來源是為了「看一眼」
> 手寫的 `PARTY.DAT` 解析 —— 步長與偏移漂掉，同 `one-implementation-per-rule`。
> **結論（內縮 3）不變，但當初推導的理由是錯的**：3 來自光源 1，不是矮人加成。
>
> 另一個誤導來源是狀態列：它印的「光照」是 `clock.Light()`，那只是**戶外**的
> 時辰值，在地城裡與實際生效的內縮量無關（畫面顯示 0 而視野其實縮到 3）。
> 已改成兩邊共用 `app.viewInset()`。

### 5.4 ⚠ 這條規則**早就實作了**，第一版是重造

`internal/game/clock.go` 從一開始就有 `LightLevel`、`lightByHour`（同一張
`ds:0x209c` 表）與 `DungeonLight(torch) = 4 − 光源`，連「原版還有一個 +1 的加成
沒有實作，那個旗標是什麼還沒追出來」都寫在註解裡。而 `DungeonLight` **一個呼叫端
都沒有** —— 機制寫好了但從沒接進畫面。

第一版的 `vision.go` 把時辰表與 `4 − 光源` 又抄了一遍，是
`one-implementation-per-rule` 的典型漂移（形狀是「寫新功能時沒發現舊的已經有了」）。
已合併：

| 在哪 | 負責什麼 |
|---|---|
| `clock.go` | 光照等級：`LightAtHour`（戶外時辰表）、`DungeonLight(torch, darkVision)` |
| `vision.go` | 等級 → 哪幾格看得見：`ViewSpan`／`ViewInset`／`ViewVisible`／`PartyHasDarkVision` |

**這一輪真正的新發現只有一個**：那個 `+1` 加成的旗標 ＝ 隊伍裡有活著的矮人。
其餘都是把既有的東西接起來。
