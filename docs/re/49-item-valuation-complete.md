# 49 — 估價的最後三項，與一個不能用的整數捷徑

`docs/re/46` §3 停在「第四項的 dump 對齊有問題，沒讀乾淨」，
`ItemValue` 因此要回報一個 `exact`，商隊介面上會出現「說不出價」。

`docs/re/48` 把那兩個 byte 的來歷讀出來之後（`+0x0a`／`+0x0c` 是掉寶生成器
寫的特效級數），回頭再看那一段就通了 —— 而且發現後面還有兩項。

---

## 1. 第四、五項：兩組特效值

```
1e13  if 槽[+0x0a] == 0 → 跳過
1e1d  n = 槽[+0x0a] − 10
1e29  push double 1.4；push n
1e3c  call 206a:000a          → |n|
1e45  call 278d:000c          → A = 1.4 × |n|
1e4d  bx = CS:0x35fa (250.0)；0196 / 0588   → A = A × 250
1e62  call 206a:0020          → sign(n)
1e76  07e2                    → trunc(A)
1e83  總額 += trunc(A) × sign(n)
```

`+0x0c` 那一組（`1e97`）一模一樣。

卡了兩輪的 `206a:000a` 與 `206a:0020` 一讀就完：

| entry | 內容 | 是什麼 |
|---|---|---|
| `000a` | `if ax <= 0 → neg ax` | **絕對值** |
| `0020` | `0 → 0；> 0 → 1；否則 −1` | **正負號** |

先取絕對值算完再乘回正負號 —— 那是為了讓截斷**朝零**而不是朝負無窮。

**所以詛咒品會扣分。** 特效級數在掉寶時被取負（`docs/re/48` §6.1），
到估價這裡就是負的加價。

---

## 2. 第六項：附魔

```
1eeb  if 槽[+0x00] >= 13 → 跳過        ; 只有武器與護甲
1ef1  n = 槽[+0x0e] − 10               ; 附魔
1efd  係數 = 槽[+0x00] > 7 ? 700 : 350 ; 護甲加倍
1f0f  A = 1.7 × |n|  →  × 係數  →  trunc
1f5f  總額 += trunc(A)
```

兩件事值得記：

**這裡的型別比較是 0-based 的。** 估價常式直接讀槽 `+0x00`，
沒有 `docs/re/48` §2 那個 `+1`。`>= 13` 與 `> 7` 兩道分界正好把
「武器 0–7、護甲 8–12、其餘 13 以上」切出來 —— 與掉寶生成器
「飾品以上不長附魔」是同一條線，兩支常式各自寫了一遍。

**取絕對值之後沒有補回正負號。** 第四項有 `206a:0020`，這裡沒有 ——
負附魔（詛咒品）在這一項照樣加分。看起來像疏漏，但沒有旁證說它是 bug，
照抄。

---

## 3. 最後兩道鉗制

```
1f68  if 槽[+0x0d] != 0 → 總額 = 0     ; 有驅邪成功率 = 詛咒品
1f7c  if 總額 < 0       → 總額 = 0
```

**掉落生的詛咒品一文不值。** `+0x0d` 只有模式 0 的詛咒品才寫
（`docs/re/48` §7），所以這一鉗剛好只打中它們。
商隊的貨不會有 `+0x0d`，市集的平凡裝備也不會。

第二道鉗制不是多餘的：兩組特效值都是負的時候，前面幾項不見得補得回來。

---

## 4. 「小數乘出整數」這次不能用

`docs/re/44` 把 `225 × 1.2` 寫成 270、`docs/re/46` 把 `1.07 × 200` 寫成 214，
理由是「浮點常數乘出整數，直接用整數值完全相同」。
第四項看起來是同一個樣子（`1.4 × 250 = 350`），**但它不成立**：

| n | `trunc(1.4 × n × 250)` | `350 × n` |
|---|---|---|
| 1 | 350 | 350 |
| 2 | 700 | 700 |
| **3** | **1049** | 1050 |
| 4 | 1400 | 1400 |
| **6** | **2099** | 2100 |
| **7** | **2449** | 2450 |

差別在**乘法順序**：

```
第二項：(a+b) × 225   先乘整數 → 再 × 1.2   → 落在整數上方，截斷不掉
第四項：1.4 × |n|     先乘小數 → 再 × 250   → 誤差被放大 250 倍，掉一格
```

`1.4` 的 IEEE double 是 `1.39999999999999991…`（比 1.4 小一點點）。
先乘 250 的話這點誤差會被吸收進捨入；先乘 `n` 再乘 250，
誤差跟著放大，`n = 3` 時剛好跨過整數邊界。

第六項（`1.7 × |n| × 350`）是同一個結構，同樣不能簡化。

> 教訓：**「這個小數乘出整數」是關於算式的斷言，不是關於常數的。**
> 同樣兩個數，換個順序結論就不一樣。想用捷徑就要對值域跑一遍比對 ——
> 這一輪是跑了 `n = 1..600` 的窮舉才敢在第二、三項留整數。

## 5. 完整的估價公式

```
價值 = 底價 × 材質倍率                                    (docs/re/44 §1)
     + 已鑑定 ? (槽[+0x02] + 槽[+0x04]) × 270 : 0         (docs/re/44 §3)
     + 強度 != 0 ? 強度加價（三條分支）: 0                 (docs/re/46 §1)
     + 槽[+0x0a] != 0 ? trunc(1.4×|a|×250) × sign(a) : 0   a = 槽[+0x0a] − 10
     + 槽[+0x0c] != 0 ? trunc(1.4×|b|×250) × sign(b) : 0   b = 槽[+0x0c] − 10
     + 型別 <= 12 ? trunc(1.7×|附魔|×(型別<=7 ? 350 : 700)) : 0

if 槽[+0x0d] != 0 → 0
if 價值 < 0       → 0
```

六項全解，**`exact` 這個回傳值可以拿掉了**。它是公式缺一項時的自保 ——
與其標一個算不準的數字，不如在介面上說「說不出價」也不賣。
補齊之後那個狀態就沒有存在的理由。
