
# 44 — 道具估價，以及那段軟浮點的真相

商隊售價是本專案最老的一筆未解帳（`docs/re/32` §4，2026-07-26 早些時候）。
這一篇沒有把它全部解完，但**解掉了卡住它的那個誤解**，並讀出了公式的第一項。

---

## 1. 軟浮點的常數在**程式段**，不是資料段

追這條線時撞過兩次牆，都是同一個誤判 —— 而且**第一次的「訂正」也是錯的**，
所以這一節記兩層。

看到 `mov bx, 立即值` 接 `lcall 210e:0196`，我先假設 `bx` 指向資料段的浮點常數，
去 `ds:0x40e0` 一看是 ASCII `"tistics"`、`ds:0x35f2` 是 `"Dormant: "`。
於是下了第一個結論：「`bx` 不是運算元指標，常數是 `push` 推上堆疊的」。

**那個結論只對了一半。** `push` 推常數確實存在（見 §3 的 1.2 與 0.9），
但 `210e:0196` 真的是「把 `[bx]` 的常數載入暫存器 B」——
**只是那個 `bx` 相對的是 `CS`，不是 `DS`**。

這件事 `docs/re/14` §1 早就寫過了：

> `CALLF 0x3000:1276 ; = FUN_310e_0196：把 **30c2:0092** 的常數推入暫存器 B`
> …「常數放在程式段、由 `FUN_310e_0196` 這類函式讀取」是這個編譯器的通用手法。

照著改用呼叫端自己的段基底去讀，三個位址立刻乾淨：

| 位址（CS 相對）| 檔位移 | double |
|---|---|---|
| `278d:35ea` | `0x1eaba` | **0.6** |
| `278d:35f2` | `0x1eac2` | **0.8** |
| `1990:40e0` | `0x115e0` | **2.6** |

三個都是漂亮的十進位小數，不是巧合。

> **兩層教訓。** 第一層：段暫存器要跟對 —— 同一個 `bx` 值配 `DS` 是字串、
> 配 `CS` 是浮點常數。第二層更要緊：**答案早就寫在我們自己的文件裡**
> （`docs/re/14` §1，連「放在程式段」這句話都有）。
> 撞牆時先翻自己的筆記，比再讀一次反組譯便宜得多。
> 這是 `rulebook/63` 的鄰居 —— 不是標記過期，是**根本沒去查**。

順帶：這也把 `docs/re/30` §2.0 那個「`f(等級)` 沒解碼」的缺口鬆開了 ——
那段用的常數就是 **2.6**。

## 2. 估價常式在哪

商隊列貨的迴圈（`0x1d66e`–`0x1d74a`）對每一件貨做：

```
1d6c8  槽[+0x10] = 1                  ; ★ 標成已鑑定
1d6d6  lcall 278d:1c1b(槽)            ; ★ 估價
1d6e1  一段軟浮點（換算成顯示用的售價）
1d737  價格表[i] = dx:ax              ; 32-bit
```

`278d:1c1b` = 檔位移 **0x1D0EB**，就是估價常式。

> 順帶訂正 `docs/re/32` §3 的表：那裡寫「商隊的貨**未鑑定**」。
> 列貨的時候 `槽[+0x10]` 被寫成 1 —— **擺出來給你看的時候是已鑑定的**。
> 生成當下確實沒鑑定（`GenerateLoot` 不設那個 byte），
> 但玩家看到的清單是鑑定過的。

## 3. 公式讀到哪裡

```
1c22  型別  = 槽[+0x00]
1c3c  底價  = [0x5300][型別 × 14]          ; ITEMS.DAT 記錄的 word 0
1c4f  倍率  = [0x18b3 + 槽[+0x0f]]
1c58  價    = 底價 × 倍率                   ; ★ 第一項

1c64  if 槽[+0x10]（已鑑定）== 0 → 跳過以下
1c6e  價 += (槽[+0x02] + 槽[+0x04]) × 225 × 1.2     ; ★ 第二項 = ×270

1cc4  if 槽[+0x08]（強度）== 0 → 結束
1cd1  if 槽[+0x06] == 0xff（無限次數）:
1cdf     一段以 5 × 強度² 與 0.9 為材料的軟浮點      ; ★ 第三項
      否則（有限次數）:
1d5d     另一條，還有 `槽[+0x05] > 100` 的分支
```

**第一項已經解乾淨**，倍率表 `ds:0x18b3` 是九個 byte：

```
00 01 02 05 14 23 32 3c 4b
 0  1  2  5 20 35 50 60 75
```

`+0x0f` 因此有了名字：**材質／品質類別**。它同時決定名稱前綴
（`docs/re/30` 的名稱表）與價格倍率 —— 同一把匕首，類別 8 就是 **75 倍**價。
兩份原版存檔裡每一件實物都是類別 1（×1），與「起始裝備都是平凡貨」一致。

**第二項也解乾淨了。** 那一段的常數是 `push` 上去的 double 1.2，
呼叫 Turbo C 的 `long × double` 輔助函式 `278d:000c`，中間沒有其他運算 ——
所以就是 `(a + b) × 225 × 1.2`，而 **225 × 1.2 = 270 剛好是整數**。
一個沒有小數的常數用浮點繞一圈，是編譯器把 `* 1.2` 直譯的結果，不是設計。

**第三項還沒解。** 它有兩條分支（無限次數／有限次數），
中間夾著 `210e:0x21e`／`0x242`／`0x02e4`／`0x0732` 幾個還沒對上名字的
entry point。`docs/re/14` §1 已經釘住 `0196`（常數→B）、`07a4`（整數→A）、
`0588`（A×B）、`045e`（A÷B）、`07e2`（float→int）、`0127`/`01b2`（載入／存回），
剩下那幾個照同樣的方式讀出來就行 —— 是工作量，不是難題。

## 4. 本專案的實作範圍

- `internal/assets/scenario`：`InventorySlot.MaterialClass`（`+0x0f`）雙向；
  常數從 `slotUnknown0F` 改名為 `slotMaterialClass`
- `internal/game/price.go`：`MaterialMultiplier`／`ItemValueBase`／`ItemValue`

`ItemValue` 算前兩項並回報 `exact`：**強度為 0 的道具算得出確切售價**，
強度不為 0 的還缺第三項，`exact = false`。起始存檔那十件裝備
（`+0x02`／`+0x04`／強度全是 0）算出來就等於底價，測試釘住。

**商隊購買介面還是沒做**，理由變得很具體：商隊的貨是掉寶生成器生的，
多數帶強度 —— 也就是多數落在 `exact = false` 那一邊。
與其標一個算不準的價錢賣給玩家，不如等第三項讀完。
