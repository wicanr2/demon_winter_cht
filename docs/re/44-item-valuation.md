
# 44 — 道具估價，以及那段軟浮點的真相

商隊售價是本專案最老的一筆未解帳（`docs/re/32` §4，2026-07-26 早些時候）。
這一篇沒有把它全部解完，但**解掉了卡住它的那個誤解**，並讀出了公式的第一項。

---

## 1. 先訂正：軟浮點的常數不在資料段

追這條線時撞過兩次牆，都是同一個誤判：

| 位址 | 我當時的判讀 | 實際是 |
|---|---|---|
| `ds:0x40e0`（`docs/re/30`）| 浮點常數 | ASCII `"tistics"` |
| `ds:0x35f2`（本次）| 浮點常數 | ASCII `"Dormant: "` |

兩次都是看到 `mov bx, 立即值` 接著 `lcall 210e:xxxx` 就假設「bx 指向一個浮點常數」。

**真相是常數用 `push` 直接推上堆疊。** 估價常式裡看得一清二楚：

```
1c8b  mov ax,0x3ff3 / push
1c8f  mov ax,0x3333 / push
1c93  mov ax,0x3333 / push
1c97  mov ax,0x3333 / push        ; → 記憶體 33 33 33 33 33 33 f3 3f = double 1.2
1c9b  push 32-bit 運算元
1ca1  lcall 278d:000c             ; long → double、相乘
```

`3ff3 3333 3333 3333` 是 IEEE-754 double **1.2**；後面另一處
`3fec cccc cccc cccd` 是 **0.9**。兩個都是漂亮的十進位小數，
不可能是巧合湊出來的字串。

> **教訓**：`mov bx, imm` 之後接浮點呼叫，`bx` 未必是運算元指標。
> 驗證只要一步 —— 去那個位址看一眼。看到 ASCII 就該停下來重想，
> 而不是換一種方式把它讀成浮點數（我第一次就是那樣，
> 把 `"tistics"` 當 double 印出 `1.7e-306` 還繼續往下推）。

---

## 2. 估價常式在哪

商隊列貨的迴圈（`0x1d66e`–`0x1d74a`）對每一件貨做：

```
1d6c8  槽[+0x10] = 1                  ; ★ 標成已鑑定
1d6d6  lcall 278d:1c1b(槽)            ; ★ 估價
1d6e1  一段軟浮點（換算成顯示用的售價）
1d737  價格表[i] = dx:ax              ; 32-bit
```

`278d:1c1b` = 檔位移 **0x1D0EB**，就是估價常式。

> 順帶訂正 `docs/re/32` §3 的表：那裡寫「商隊的貨**未鑑定**」。
> 列貨的時候 `槽[+0x10]` 被寫成 1 —— **擺出來給你看的時候是已鑑定的**。
> 生成當下確實沒鑑定（`GenerateLoot` 不設那個 byte），
> 但玩家看到的清單是鑑定過的。

## 3. 公式讀到哪裡

```
1c22  型別  = 槽[+0x00]
1c3c  底價  = [0x5300][型別 × 14]          ; ITEMS.DAT 記錄的 word 0
1c4f  倍率  = [0x18b3 + 槽[+0x0f]]
1c58  價    = 底價 × 倍率                   ; ★ 第一項

1c64  if 槽[+0x10]（已鑑定）== 0 → 跳過以下
1c6e  價 += (槽[+0x02] + 槽[+0x04]) × 225 × 1.2     ; ★ 第二項

1cc4  if 槽[+0x08]（強度）== 0 → 結束
1cd1  if 槽[+0x06] == 0xff（無限次數）:
1cdf     一段以 5 × 強度² 與 0.9 為材料的軟浮點      ; ★ 第三項
      否則（有限次數）:
1d5d     另一條，還有 `槽[+0x05] > 100` 的分支
```

**第一項已經解乾淨**，倍率表 `ds:0x18b3` 是九個 byte：

```
00 01 02 05 14 23 32 3c 4b
 0  1  2  5 20 35 50 60 75
```

`+0x0f` 因此有了名字：**材質／品質類別**。它同時決定名稱前綴
（`docs/re/30` 的名稱表）與價格倍率 —— 同一把匕首，類別 8 就是 **75 倍**價。
兩份原版存檔裡每一件實物都是類別 1（×1），與「起始裝備都是平凡貨」一致。

第二、三項的浮點運算**順序**還沒讀（`210e` 那些 entry point 沒有一一對名），
所以本專案只實作第一項。

---

## 4. 本專案的實作範圍

- `internal/assets/scenario`：`InventorySlot.MaterialClass`（`+0x0f`）雙向；
  常數從 `slotUnknown0F` 改名為 `slotMaterialClass`
- `internal/game/price.go`：`MaterialMultiplier`／`ItemValueBase`

`ItemValueBase = 底價 × 材質倍率`。對起始存檔那十件裝備來說這就是完整售價
（`+0x02`／`+0x04`／強度全是 0），測試釘住「原版存檔每一件都是類別 1」。

**商隊購買介面還是沒做。** 缺的不再是「不知道從哪查」，而是
第二、三項的浮點順序 —— 位址、常數、輸入欄位都在 §3 了，
剩下的是把 `210e:0x21e`／`0x242`／`0x7a4`／`0x588`／`0x7e2` 這幾個
entry point 對上名字。那是下一輪的事。
