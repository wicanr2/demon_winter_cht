# 102 — 附魔費用定案：那個 `1.7` 是指數，而且執行檔裡真的有一支手寫的 pow

`docs/re/55` 從攻略的 80 個點反推出

	累積附魔費用  F(n, c) = 35 × (20 − c) × n^1.7

誤差全部 ≤6，但那一篇留了兩條保留意見：

> **(1)** 找不到原版哪裡提供這個服務（城鎮八設施與市集 12 選項都沒有）。
> **(2)** `n^1.7` 對 1988 年的 16-bit 遊戲來說是可疑的東西。非整數次方要
> `log`／`exp`，而我們目前在這個執行檔裡看到的只有整數次方。
> 同樣能吻合 80 個點的還有「存一張十格的表，再乘材質係數」——
> 那在 1988 年合理得多。**光靠攻略分不出這兩者。**

**兩條都解除了。** 服務在地圖 2 的一格劇情事件裡（A7 case 6），
而執行檔裡有一支**手寫的 pow**。

---

## 0. 結論先講

| | |
|---|---|
| 入口 | 地點劇情 case 6 ＝ **矮人大師的附魔工坊**，地圖 2 的 (28,5)（`docs/re/101` §1）|
| 費用 | `(ItemValue(新附魔) − ItemValue(舊附魔)) × (20 − 材質類別) ÷ 10` |
| 估價的附魔項 | **`trunc(|n|^1.7 × 350)`**（護甲 700）—— `1.7` 是**指數** |
| `2000:78dc` | **手寫的 `pow`**：`log` → 乘 → `exp`，開頭一道 `n == 0 → 0.0` 的守衛 |
| 連帶訂正 | 估價第四／五項（特效值）也是 `|n|^1.4 × 250`，不是 `1.4 × |n| × 250` |
| `docs/re/55` | **反推對了**，而且它反推的是可觀察行為；這一篇補上機制 |

## 1. 費用是「附魔漲的估價」乘材質折扣（`0x0feb1`–`0x0ff4b`）

工坊選完人、選完道具、選完要附魔到 +幾之後呼叫 `1000:c2ad` ＝ `0x0fead`：

```
0fee1  新價 = 2000:94eb(改成新附魔的那一格)      ; ＝ ItemValue，32 位元
0fef5  舊價 = 2000:94eb(現在的那一格)
0ff09  差   = 新價 − 舊價                        ; 32 位元減法
0ff17  AX = 0x14                                 ; 20
0ff1b  材質 = 那一格的 +0x0f
0ff27  AX = 20 − 材質                            ; ← 材質折扣
0ff32  32 位元乘：差 × (20 − 材質)
0ff40  CX = 0xa;  BX = 0
0ff46  call 3000:016a                            ; 32 位元除法 ÷ 10
0ff4b  費用 = 商
0ff78  金幣 = party[+0x0a]（32 位元）
0ff84  if (金幣 < 費用) → 印 ds:0x12cc（付不起）
```

所以

	費用 = (ItemValue(新) − ItemValue(舊)) × (20 − 材質類別) ÷ 10

`docs/re/55` 的 `35 × (20−c)` 就是這條式子的展開：估價的附魔項係數是 350，
`350 ÷ 10 = 35`。**折扣不是「大約每級 5%」而是精確的 1/19**
（材質 1 是 19/10，每高一級少 1/10 個係數）。

這也解釋了設計意圖：**附魔會漲估價，工坊收的就是那個差額打折**。
不是查表，是照著同一套估價收費。

## 2. `2000:78dc` 是 pow，不是乘法（`0x1b4dc`）

估價的附魔項（`0x1d3eb`）：

```
1d3ee  if (槽[+0x00] >= 0x0d) 跳過                ; 只有武器與護甲
1d3f4  n = 槽[+0x0e] − 10
1d400  係數 = 槽[+0x00] > 7 ? 0x2bc(700) : 0x15e(350)
1d412  push double 0x3FFB333333333333             ; ＝ 1.7
1d422  push |n|                                   ; 2000:06aa ＝ abs
1d42e  call 2000:78dc                             ; ← 這一支
       …乘上係數，trunc，加進總額
```

而 `2000:78dc` ＝ `0x1b4dc`：

```
1b4df  if (參數 == 0) return 3000:1884(0)         ; ← long → double(0.0)
1b4fa  3000:1884(long)                            ; long → double
1b505  3000:12fe
1b50a  3000:094c                                  ; ← log
1b512  LEA BX,[BP+0xa]                            ; 那個 double（1.7）
1b515  3000:126f / 3000:1668                      ; 載入 / 乘
1b524  3000:0cba                                  ; ← exp
```

**`exp(y · ln x)` 就是 `pow(x, y)`。** 那道 `x == 0 → 0.0` 的守衛
正是手寫 pow 必須有的（`ln 0` 沒有定義）——
一個乘法函式不會需要那道守衛。

> `docs/re/55` §2(2) 的疑慮到此解除：**這個引擎算得出非整數次方**，
> 而且是自己用 log／exp 拼的。

## 3. 80 個點的裁決

`docs/walkthrough/part-5.md` §4.1 是「一把武器從 +0 附魔到 +10、
八種材質」的逐級費用 —— 80 個點。

| 讀法 | 一般材質 +0→+1 | 攻略 |
|---|---|---|
| **指數**：`trunc(1^1.7 × 350) × 19 ÷ 10` | **665** | **665** |
| 係數：`trunc(1.7 × 1 × 350) × 19 ÷ 10` | 1130 | ✗ 差七成 |

不是捨入問題，是**差一個量級的問題**。

全部 80 個點跑下來（照反組譯的捨入順序：兩次估價各自 `trunc` →
乘 `(20−c)` → 整數 `÷10`）：

	完全相同 69 個、差 1 的 11 個（**全部同一個方向**）、沒有差 2 以上的

差 1 全同向是「同一條式子、末位捨入不同」的指紋。兩個來源：

- 攻略那張表**自己就不自洽** —— 原文的「總計」（逐段加總）與「0→10」
  （整體算）差 2～3，作者自己標成捨入誤差。
- 原版的 pow 是 1988 年手寫的 `exp(y·ln x)`，末位不會和 Go 的
  `math.Pow` 逐位相同。

材質那一維反而是**完全精確的**：八種材質的 +0→+1 全部等於
`350 × (20−c) ÷ 10`，8/8 零誤差。

## 4. 連帶訂正估價的第四、五項

`docs/re/49` §4 花了一整節論證「第四項不能用 `1.4 × 250 = 350` 的整數捷徑」，
理由是浮點誤差的乘法順序。**那一節的推理沒錯，前提錯了** ——
它假設 `2000:78dc` 是乘法。同一支函式、同一個呼叫形狀，所以第四／五項是

	trunc(|n|^1.4 × 250) × sign(n)

`internal/game/price.go` 兩處都改了（`effectValueExp`／`enchantValueExp`），
`price_test.go` 那幾個預期值一併更新 —— 那些值是從錯的讀法算出來的，
不是從遊戲觀察來的，所以更新它們不需要另外的證據。

> **教訓：「這個浮點常數是係數」是一個假設，不是讀出來的事實。**
> 判斷它要看那支函式做什麼，而不是看常數長什麼樣子。
> 這一輪能裁決是因為**附魔費用把估價的附魔項乘上 19/10 放大了** ——
> 差七成藏不住。單看估價本身，1.7 是係數還是指數在小 n 時差得不多，
> 而本專案沒有任何估價的外部對照數字（`docs/re/54` §7 就卡在這裡）。
