# 50 — 商隊是事件動作，不是隨機遭遇

`docs/re/32` §4 唯一還掛著的缺口：「什麼情況下會遇到商隊、規模與等級怎麼來」。
`M` 鍵一直是偵錯用的替身。這一篇把規模那一半解完，並釘住觸發的性質。

---

## 1. 找呼叫端：從函式位址回推

商隊常式的進入點在檔位移 `0x1d4a1`（緊接在估價常式的 `retf` 之後），
換算成 `278d:1fd1`。遠呼叫的機器碼就是 `9a d1 1f 8d 17`（段值存的是編碼過的
`178d`），全檔掃一遍只有兩個：

```
0x1b0cc  push 1 ; call 278d:1fd1 ; pop cx ; ax = 0 ; retf
0x1bc91  push 0 ; call 278d:1fd1 ; ...    ; [bp-0x8a] = 0xb
```

**參數是 0 或 1，函式開頭就分岔**（`1d4c8  cmp [bp+6],1 / jne`）——
所以這支常式其實服務兩個畫面，商隊只是 `mode == 1` 那一半。

`0x1b0cc` 那段只有五行：推 1、呼叫、回傳 0。那是**包裝函式**的形狀。
再掃一次誰指到它（`15be:18ec`，同樣用位址回推），也只有一個地方：
`0x163d1`，而它前後長這樣：

```
163b6  les bx, ds:0x4c76               ; 隊伍記錄
163ba  if 隊伍[+0xbe] != 0 → 結果 = 3   ; ★ 閘門
163c9  隊伍[+0xa8] = ds:0x5c60          ; 把規模基準塞進參數欄
163d1  call 商隊
163d6  結果 = 回傳值
163d9  重畫地圖(隊伍[+0xa1] − 4, 隊伍[+0xa2] − 4)
```

這一段落在一整排 `call FUN_222f_xxxx ; [bp-0x14] = ax ; jmp 結束` 中間 ——
**是事件動作分派表的一個 case**（同一個 switch 裡有 `FUN_222f_32d4`、
`FUN_222f_1404`，都是 `docs/re/05` 認得的事件常式）。

所以商隊**不是每走一步擲一次的隨機遭遇，是事件表寫死的動作**。
`M` 鍵不是「暫時替代隨機遭遇」，是「暫時替代事件」。

**商隊是動作碼 `0x17`**，見下一節。

---

## 1.1 分派表：21 個事件動作

Turbo C 把 switch 的分派放在**函式最後面**，所以往前找沒有用。
掃 `jmp word ptr cs:[bx+d16]` 這個指令碼（`2e ff a7`）直接命中 `0x16488`：

```
1647d  sub ax,6
16480  cmp ax,0x15
16483  jae  預設                      ; 0x15 = 21 個 case
16485  xchg bx,ax ; shl bx,1
16488  jmp  cs:[bx + 0x563]           ; 跳表在 cs:0x563 = 檔位移 0x16453
```

`sub ax,6` 是關鍵：**動作碼的值域是 6–26（`0x06`–`0x1A`）**，case 0 對應 6。
21 個 word 解出來：

| 動作碼 | case | 呼叫 | 認出來的部分 |
|---|---|---|---|
| 0x06 | 0 | `222f:1606` | |
| 0x07 | 1 | `222f:1882` | |
| 0x08 | 2 | `222f:1a94` | **載入地城探索地圖**（511 bytes ≈ 64×64 bits）|
| 0x09 | 3 | `25be:0077` | |
| 0x0a | 4 | `222f:1c74` | **Examine**，轉呼叫 `222f:2088(3)` |
| 0x0b | 5 | `222f:3621` | |
| 0x0c | 6 | `222f:2088(0)` | **Use（使用道具）**，參數選提示詞（`docs/re/69` §1）。~~與 0x12 成對~~ —— 那是誤判，`0x12` 是另一支函式 |
| 0x0d | 7 | `222f:2da5` | 回傳 9 時印 **"It's too crowded here"** |
| 0x0e | 8 | 重定位補的遠呼叫 | 目標由載入器填，靜態看不到 |
| 0x0f | 9 | `222f:30dc` | **觀室**（技能 27）|
| 0x10 | 10 | `222f:34d2` | **鑑物**（技能 28）|
| 0x11 | 11 | `222f:37c4` | |
| 0x12 | 12 | `25be:0263(0)` | **地點劇情事件**的內層分派（16 格，`docs/re/65`）|
| 0x13 | 13 | `222f:3233` | |
| 0x14 | 14 | `222f:32d4` | `docs/re/05` §4 提過的那一支 |
| 0x15 | 15 | （直接回 1）| 什麼都不做 |
| 0x16 | 16 | `222f:2a5b` | |
| **0x17** | **17** | **商隊** | 本文 §1 |
| 0x18 | 18 | `25be:000c` | |
| 0x19 | 19 | 印字串 | **"Your crew refuses to sail any further…"**（航到世界邊緣）|
| 0x1a | 20 | 印字串 | **"The sun is rising"**（天亮）|

選擇子本身是區域變數 `[bp-0x16]`，**誰填它還沒追**。
但光是這張表就把「事件動作」從一團未知變成 21 個有位址的格子 ——
`docs/re/05` 卡住的「誰在什麼時候用什麼參數重新呼叫」有了對照的骨架。

## 2. 規模＝等級，而且同一個變數

```
1d4e6  [bp-0x12] = 隊伍[+0xa8]          ; 呼叫端剛塞進來的基準
1d555  ax = rnd(3)
1d55f  ax += [bp-0x12] ; dec ; dec      ; 基準 + rnd(3) − 2
1d564  [bp-0x12] = ax
1d567  if > 9 → 9
...
1d6ad  push [bp-0x12]                   ; ← 傳給掉寶生成器當「等級」
```

**規模與等級是同一個區域變數。** 算完規模之後原封不動當等級傳下去。
所以「衣衫襤褸的商隊」賣的東西一定也差 —— 那不是兩個獨立的設定，
是同一個數字的兩種呈現。

上限 9 這件事順帶解掉一個隱憂：`docs/re/48` §1 說材質類別公式在等級 10
以上會讀出表外的 bytes，**商隊永遠碰不到那條線**。

## 3. 基準值從哪來

`ds:0x5c60` 是 BSS（超出執行檔映像），執行期才有值。掃寫入端有兩處，
都在「進入地圖」的初始化裡：

```
15f64  ds:0x5c60 = 隊伍[+0xaf]                  ; 預設
160b9  if 子地圖編號 > 9 → ds:0x5c60 = [0x4c90][+1]   ; 戶外改用地圖記錄自帶的參數
```

（旁證：同一段稍後把地城光源寫進 `ds:0x5c64` —— 兩個全域挨在一起，
是同一批「進地圖時填好的常數」。）

所以存檔 `+0xaf` 是**地城**的基準，戶外另有來源。
兩份原版存檔的 `+0xaf` 是 1 與 4。

後續已確認 `[0x4c90]` 是 6-byte `EXITS.DAT` 記錄表，命中出口後第六欄
寫回 `+0xaf`（`docs/re/107` §3）。`+0xbe` 的語意仍另列為證據缺口。

## 4. 基準 1 會擲出等級 0，而等級 0 在原版會轉不完

基準 1 → 規模 ∈ {−1, 0, 1}，有三分之一以上落在 0 或負數。
而 `LootPriceCap(0) = 2.6^0 + 25×0 = 1`（`docs/re/48` §3），
`ITEMS.DAT` 最便宜的匕首要 2 —— **一件都選不出來，型別重擲迴圈不會結束**。

這不是我們算錯的旁證，是一個實實在在的矛盾。三種可能：

1. 商隊事件只發生在戶外，那裡的基準來自地圖記錄，實際值夠大；
2. `+0xbe` 那道閘門擋掉了低等的情況；
3. 原版真的會在這裡卡死（只是玩家很難走到）。

沒有證據能在三者之間裁決，所以**不猜**。本專案的做法是
`LootItemTypeFor` 用光重擲次數就退回匕首 —— 不會卡死，也不會憑空發財。
症狀在畫面上看得見：基準 1 的商隊會列出清一色的匕首。

驗收用的偵錯旗標 `-merchant-base N` 就是為此加的：
不改基準看不到大商隊，而大商隊才驗得到材質、附魔與價格的分布。

## 5. 本專案的實作範圍

- `internal/assets/scenario`：`SaveGame.MerchantBase`（trailer `+0xaf`）。
- `internal/game/merchant.go`：`MerchantSize(r, base)`；
  `RollMerchant` 的 `size, level` 兩個參數收成一個 —— 它們本來就是同一個數。
- `cmd/demonwinter`：`openMerchant` 照存檔的基準擲，
  換圖時以 `EXITS.DAT` 第六欄更新基準，並保留偵錯旗標 `-merchant-base`。

測試釘住：基準 4 擲出 3–5 且三種都出現、上限鉗在 9、下限不為負、
`RollMerchant` 的 `Level == Size`。

畫面實測 `workplace/dump/persist/65-merchant-real-size.png`
（基準 8 → 「豪富的商人」，貨從釘頭鎚 23 到晨星鎚 +6 的 4861）。
