# 30 — 掉寶生成：`ITEMS.DAT` 四個欄位的完整答案

`docs/re/25` §3 把掉寶生成解到剩一角：

> 第一個欄位為 0 時走「從四個欄位挑一個」那條路，而武器的四個欄位是
> `0, 10, 8, 9` —— 挑到 0 之後 `−1` 會得到類別 `−1`，索引到表外。
> **這一步還沒解釋清楚**……本作目前不實作掉寶生成。

**那是把 `jne` 讀成了 `je`。** 分支方向反過來，整件事就自洽了。

---

## 1. 反過來的那一行

```
13bc  cmpw $0x0, -0x1a(%bp)      ; f[0] == 0 ?
13c0  jne  0x13e3                ; ★ 不等於 0 才跳到「挑一個」
13c2  （f[0] == 0 的路徑）：rnd(17)，撞到 f[1..3] 就重擲
13e1  jmp  0x13fa
13e3  （f[0] != 0 的路徑）：i = rnd(4)；cls = f[i−1]
13fa  cls −= 1
```

所以四個欄位是**兩種用法**，由第一個欄位是不是 0 決定：

| f[0] | 意思 | 例子 |
|---|---|---|
| `!= 0` | **候選清單**：四個裡隨機挑一個 | 護甲 `12,7,7,7` → 12 或 7；雕像 `15,15,15,15` → 一定 15；勳章 `1,5,3,1` → 1 的機率加倍 |
| `== 0` | **排除清單**：`rnd(17)` 撞到 f[1..3] 就重擲 | 武器 `0,10,8,9` → 除了 10、8、9 都行；火把 `0,0,0,0` → 17 種都行 |

`rnd()` 回傳 1..n，所以排除路徑得到 1–17、候選路徑得到的都是非零值
（30 件真貨裡，`f[0] != 0` 的那些四個欄位都沒有 0）。減一之後**永遠落在 0–16**，
不會索引到表外。疑點結案。

---

## 2. 完整流程（`1990:1107`–`1990:1522`）

參數：`[bp+6]` 等級、`[bp+8]` 道具槽的遠指標、`[bp-4]` 道具型別。

### 2.0 先擲道具型別，再用價格門檻篩掉（`1128`–`1193`）

```
1128  型別 = rnd(26) − 1                     ; 0–25
1136  門檻 = f(等級) + 25×等級                ; f 是一段 310e 軟浮點運算
117b  價格 = ITEMS.DAT[型別] 的第 0 個 word
1189  if 價格 < 門檻 → 回 0x1128 重擲型別      ; ★ 這是**最低**價格門檻
1195  [0x4cc8] = [0x4e38 + 型別×4]            ; 這件道具的名字（要印出來用）
11b0  道具[+0x00] = 型別
```

**價格門檻是「最低」不是「最高」**（`cmp / jl → 重擲`）—— 等級越高，
掉出來的東西越貴。這解釋了為什麼高等怪不會掉匕首。

⚠ **`f(等級)` 那一段軟浮點沒解碼。** 當時卡在「`bx` 指向 `ds:0x40e0`，
但那裡是字串」——**那個困惑解開了**：`bx` 要配 **CS** 不是 DS，
`1990:40e0` 讀出來是 double **2.6**（`docs/re/44` §1）。
知道常數之後這一段應該重讀，只是還沒動手。
只知道整體形狀是 `f(等級) + 25×等級`。**本專案沒有實作這道門檻** ——
用 `f = 0` 去湊等於自己發明分布，不如先誠實缺著（見 §6）。

順帶兩個確認：

- `[0x4e38]` 是**道具型別名的遠指標表**，30 條 —— 正是 `docs/re/27` §2
  切表常式填的第 4 張表（FILES.DTT `[123:153]`）。
- `[0x4cc8]` **不是神祇專用**。`docs/re/29` 是在神殿的脈絡下看到它，
  這裡掉寶也拿它存「目前要印的名字」—— 它是個通用的暫存指標。

### 2.1 附魔（`1296`–`12e7`）

```
n = max(1, 等級)
附魔 = 0
for i := 1; i <= n; i++ {
    if rnd(125) < 12 − i { 附魔 = i; break }
}
if 道具型別 > 8 { 附魔 = (附魔 + 1) / 2 }      ; 護甲與飾品減半
if 被詛咒        { 附魔 = −附魔 }
道具[+0x0e] = 附魔 + 10                        ; 儲存偏移 10
```

等級越高擲的次數越多，但每一級的門檻遞減（i=1 時 10/125，i=2 時 9/125…）。
附魔上限就是等級。

### 2.2 兩道效果門檻（`1308`／`134c`／`1363`）

```
if rnd(100) > 等級×2 + 6  → 結束（平凡裝備）
if rnd(100) > 等級 + 16   → 結束
if 被詛咒                 → 結束（**詛咒的道具一定沒有效果**）
```

低等級掉的東西幾乎都是平凡裝備 —— 原版起始存檔那 11 件全部 `+0x05`–`+0x08` 為 0，
正是這個結果。

### 2.3 效果與強度（`13ab`／`13fd`–`1484`）

```
重擲點:
  強度 = rnd(等級×2) + 2
  類別 = §1 的兩層規則            ; 1–17
  r    = rnd([0x1941 + (類別−1)×6])   ; 該列的候選數
  效果 = [0x1941 + (類別−1)×6 + r]
  if 最低法力(效果) > 強度 → 回重擲點      ; ★
道具[+0x08] = 強度
道具[+0x07] = 效果
```

**「最低法力 > 強度就整組重擲」是關鍵**：沒有這一步會生出「有效果卻付不起」的
道具。最低法力讀的是法術記錄的第 4 個 word（`[0x4e28]` 表，`效果×5 + 3`），
也就是 `gamedata.Spell.M` —— 又一次印證道具效果與法術共用同一個索引空間。

候選表 `DS:0x1941`（檔位移 `0x27441`）17 列 × 6 bytes，格式 `[候選數, e1 … e5]`，
內容見 `docs/re/25` §3 的表格（本文不重複）。

### 2.4 使用次數（`14a0`–`1522`）

分支值是 `ITEMS.DAT` 的**第三個數字欄**（本專案的 `CategoryIndex`，
讀取端 `1990:1334`）。那個欄位原本標「語意未確認」，這裡就是它的用途：

| 種類 | 次數上限 | 已用次數 | 哪些道具 |
|---|---|---|---|
| 1 | `rnd(等級×2) + 1` | **0xFF** | 魔杖、法杖、權杖、護符、藥膏 |
| 2 | `121 − rnd(等級+5)`（戒指與火把固定 200）| 0 | 兩件藥水瓶 |
| 3 | `3 − 強度/8`，`rnd(5) == 1` 再 +1 | 0 | 武器、護甲、冠冕、勳章 |
| 0 | 現場擲 `rnd(3)` 決定用上面哪一種 | — | 戒指、寶石、護身符、雕像、火把、提燈、劇情物 |

**兩個「過夜不充能」的例外因此有了解釋。** `docs/re/26` §3.3 記睡覺常式跳過
`+0x05 >= 100` 與 `+0x06 == 0xff` 兩種道具 —— 正好就是種類 2（上限一定 >= 100）
與種類 1（已用次數 0xFF）。**兩邊各自從不同的程式碼解出來，卻剛好互相解釋。**

種類 3 的次數會**減成負的**：強度 24 就是 0、強度 40 是 −2。原版用 `mov al`
存進一個 byte，所以 −2 變成 254 —— 高強度的裝備反而幾乎用不完。
那是原版的溢位行為，本專案照著取低位元組（不取的話記憶體是 −2、
存檔讀回來是 254，同一件道具在存檔前後行為不一樣）。

種類 3 是武器與護甲：次數 0 很合理 —— **那類道具的效果是裝備著被動生效的**，
本來就不走 Use 選單（`docs/re/16` §4.3 的「必須是已裝備的那一件」）。

## 5. 誰呼叫：戰鬥勝利與商隊遭遇

生成器的進入點是 `1990:1107`（**不是** §2 引用的 `1250`，那是函式中段），
全檔只有兩個呼叫端：

| 檔位移 | 附近的字串 | 是什麼 |
|---|---|---|
| `0xe3fc` | `"Exp per chr: %ld    Gold: %ld"`、`"Give to character ?"`、`"No more room!"` | **戰鬥勝利的結算** |
| `0x1d6b0` | `"You see a group of"` `" merchants"`、`"They show you"` `"their wares..."` | **商隊遭遇**（未讀）|

參數：`gen(等級, 道具槽遠指標, 詛咒機率, 模式)`。戰鬥那邊詛咒機率傳 0、模式傳 0；
商隊那邊傳 `[bp-0x16]` 與 1 —— 模式 1 才會用那個機率擲詛咒（`1990:122d`）。
模式 0 走另一條：`rnd(10) == 10` 且道具型別 < 14 才詛咒（`1990:124a`）。

### 5.1 戰鬥勝利（`0xe376`–`0xe451`）

```
e376  隊伍金幣 += 這場的獎金（32-bit ADD/ADC），封頂 0x00FFFFFF
e3ab  for slot := 0; …            ; 逐一掃戰鬥槽位
e3b3    r = rnd(100)
e3be    等級 = [0x4ece + 38×slot]  ; 那一隻的等級
        門檻 = 等級×6 + 5
e3e5    if r > 門檻 → 跳過這一隻
e3ec    gen(等級, …, 0, 0)         ; ★ 掉一件
e404    印出來、問要給誰、放不下就 "No more room!"
```

**掉落是逐隻獨立判定的**：`rnd(100) <= 等級×6 + 5`。1 級怪 11%、
10 級怪 65%、16 級以上必掉。打贏一群低等怪很可能一件都沒有。

道具型別在生成器開頭擲：`rnd(26) − 1` → **0–25**。
26–29（火把、提燈、惡魔水晶、恆世寶珠）永遠不會掉 ——
前兩件是雜貨、後兩件是劇情物。

### 5.2 順帶：`+0x0f` 是名稱類別索引

結算印道具名時（`0xe421`）拿的是 `item[+0x0f]`，乘 4 去查 `ds:0x1852`
的遠指標表。所以那個一直標「語意未解、原版實物都是 1」的 byte
（`docs/re/26` §4 的觀察）是**名稱類別**。生成器在 `1990:1264` 依道具型別
分組寫入（`1990:11b9`–`1228` 那串比較）。**分組規則本文沒讀完**，
本專案造新道具時仍照原版實物填 1。

## 6. 本專案的實作範圍

`internal/game/loot.go`：`LootEffectClass`／`LootEnchant`／`LootCharges`／
`GenerateLoot`，候選表內嵌（與 `weaponDamageDice`、`lightByHour` 同樣的處理）。

測試把三件事釘住：30 件真貨的類別欄位全部算得出合法類別、
生成的道具**強度一定付得起效果的最低法力**、充能種類 1／2 對得上睡覺常式的
兩個例外。

**戰鬥勝利的掉落已接上**（`game.RollBattleDrops` → `app.awardDrops`）：
每隻死掉的怪物各自擲一次，中的那隻掉一件，撿到的東西進第一個有空格的隊員身上，
全隊都滿了就照原版印「沒有人放得下了」。實機：打倒五隻高等怪 →
「Wopple 撿到戒指」「Wopple 撿到戰斧 +2」。

**沒實作的規則**：§2.0 的價格門檻（`f(等級)` 未解碼）。缺這一條的後果是
**各型別的掉落機率一律均等**，原版則是等級越高越不會掉便宜貨。
這是已知的偏離，不是漏看。

**沒接上的**：商隊遭遇的購買介面（`docs/re/32`）。另外偵錯旗標 `-loot` 可以直接發指定
型別與等級的道具，`-battle-win` 可以直接進勝利流程 —— 用 xdotool 打完一整場
戰鬥不切實際，但「打贏之後會怎樣」得看得到。
