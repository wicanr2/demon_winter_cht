# 78 — `nSS.DAT` 是存檔的一部分，`ALL_SS.DAT` 是母本

`docs/re/77` 收掉 `+0xa9` 之後留了兩個問號：那張特殊格清單被誰改寫、
以及 B8 剩下的兩處 `+0x9c` 重置。兩條線在這裡合起來 ——
**`nSS.DAT` 不是唯讀資料，是遊戲會寫回磁碟的存檔**。

---

## 1. 新遊戲會用 `ALL_SS.DAT` 重建五個 `nSS.DAT`

`Character Utilities`（建角選單，函式 `0x14567` ＝ `206a:02c7`）裡：

```
14812  FUN_1d9f_0a8b(0x522a, "all_ss.dat", [0x4c94], 0xa00L)
                                        ; 讀 0xa00 = 2560 bytes 進地圖緩衝區
14845  for (i = 0; i < 5; i++) {
1484a      al = i + 0x31                ; '1' + i  → '1'…'5'
14850      *(char*)[0x1587] = al        ; 塞進檔名樣板的數字位
14857      長度 = 0x1ff                 ; 511
1485f      來源 = [0x4c94] + (i << 9)    ; i × 512
14874      檔名 = [0x1587]
           → 寫檔
       }
```

四個常數自己把結論釘死：`0xa00` ＝ 2560 ＝ `ALL_SS.DAT` 大小、
`i << 9` ＝ 512（區塊大小）、`0x1ff` ＝ 511（`nSS.DAT` 大小）、
`i + 0x31` ＝ ASCII `'1'`–`'5'`。

**`ALL_SS.DAT` ＝ 母本（唯讀），`nSS.DAT` ＝ 工作副本（會被改寫）。**
開新遊戲就是把母本切五塊蓋回去。

> `[0x1587]` 是檔名樣板裡數字那一格的遠指標。`docs/re/05` §3 在
> `FUN_222f_32d4` 看到 `*(char *)(*(undefined4 *)0x1587) = struct.a3 + '0'`
> 時標「疑似組動態檔名的一個字元」—— 兩個獨立位置用同一個槽做同一件事，
> 現在可以去掉「疑似」。

## 2. 出廠的 `1SS`／`2SS` 差異是玩過的痕跡

`docs/formats/resource-index.md` §3.2 觀察到：`3SS`／`4SS`／`5SS` 與
`ALL_SS.DAT` 對應區塊**逐位元組相同**，而 `1SS`（21 處）／`2SS`（8 處）
不同，**差異全部落在第 3 欄**（屬性）。當時的解釋是
「同一份資料的兩份建置產物，1、2 號只更新了其中一份」。

**那個解釋錯了。** 差異的型態只有三種，而且三種都對得上程式碼裡的改寫指令：

| 型態 | 筆數 | 例 | 對應的改寫端 |
|---|---|---|---|
| 值 `0` → `1`（類別不變）| **25** | `0x40`→`0x41`、`0x20`→`0x21` | `0x1a623`、`0x1a9b6` |
| 屬性清零 | **4** | `0x61`→`0x00`、`0x64`→`0x00`、`0x68`→`0x00` | `0x0e1f8`、`0x0f6a7`、`0x178a6`、`0x19ef6` |
| `+0x60`（類別 +3）| **1** | `0x66`→`0xc6` | `0x1788e` |

29 處差異、三種型態、零例外。**出廠的 `1SS`／`2SS` 是某次玩到一半的狀態**
（壓片前有人在地圖 1 和 2 走過一段），不是建置產物不同步。

而且第三種正好解釋 `0x1788e` 那個看起來很怪的守衛：

```
1788e  if (記錄[2] < 0xc1) 記錄[2] += 0x60
```

`0x66 + 0x60 = 0xc6`，已經 **≥ `0xc1`** → 第二次來就不會再加。
**`< 0xc1` 就是「只推進一次」**。守衛的數字是從結果反推出來的，不是隨手挑的。

## 3. 三種改寫的語意

全部經由 `ds:0x52f8`（`FUN_222f_1321` 命中時存下的記錄遠指標）：

### 清零（4 處）— 這一格用掉了

`記錄[2] = 0`。屬性 0 的記錄類別是 0，**永遠不會再命中任何分支**。
一次性事件消耗掉自己。

### `+0x60` ＝ 類別 +3（1 處）— 狀態推進一格

`0x60 = 3 << 5`。所以類別 1→4、2→5、3→6 —— 這解釋了為什麼
`1SS.DAT` 的類別分布會同時出現 `{1,2,3}` 與 `{4,5,6}`：
**它們是同一批東西的前後兩態**，不是六種互不相干的類別。

（⚠ 但類別 4 同時也是傳送，而傳送顯然不是「類別 1 的後續態」。
所以「+3 是前後態」對某些類別成立、對類別 4 不見得 ——
`docs/re/77` §4 列的類別 0／3／5／6 語意仍未解，這條線索不夠定案。）

### `(類別 << 5) | 1`（2 處）— 標記看過了

兩處寫的都是同一個算式：

```
1a616  ax = ds:0x5c62        ; 類別（命中時存下的）
1a619  ax <<= 5
1a61e  ax++
1a61f  記錄[2] = al          ; = (類別 << 5) | 1
```

**類別留著、低 5 bit 設 1。** 記錄照樣命中、照樣分派，只是值從 0 變 1 ——
所以這是「已造訪」標記，不是消耗。25 筆差異全是這一種，
也就是出廠存檔裡走過最多的就是這類格子。

`0x1a61f` 那處外面還有閘門：`if (ds:0x5c62 == 1 && party[+0xa5] != 0)`。
`+0xa5` 是續接碼那個欄位（`docs/re/02` §2.4，`docs/re/77` 的 C5 用的同一個）。

## 4. B8 的 `+0x9c` 兩處收束

### `0x14933` ＝ 新遊戲初始化 —— **`docs/re/51` 早就解了**

`docs/re/75` 寫「所屬函式無字串，範圍很短，像是某個小事件之後的短暫喘息。**未追。**」

`docs/re/51` §那張表寫：
`| 0x14933 | rnd(5) + 14 | 15–19 | **新遊戲初始化**（同一段還寫 +0x9f = 5、+0xa0 = 1、起始金幣 75）|`

重讀指令，`docs/re/51` 完全正確：

```
148f4  +0xa4 = 1      148fe  +0xa7 = 1
14908  +0x9e = 8      ; 日 = 8
14912  +0x9f = 5      ; 時 = 5
1491c  +0xa0 = 1
14922  ax = Roll(5) + 14
14933  +0x9c = ax     ; 15–19
1493c  +0x0c = 0      14942  +0x0a = 0x4b   ; 起始金幣 75（32-bit）
```

`+0x9e = 8`／`+0x9f = 5` 正是 `CONTEXT.md` 記的
「新遊戲初始化只寫日 8、時 5，月完全沒寫」—— 獨立事實對上，位置無疑。

> **這是回歸，不是漏查。** 較新的 `docs/re/75` 把較舊的 `docs/re/51`
> 已經解掉的項目重新標成「未追」，於是它又被排進 worklist、又被追了一次。
> `rulebook/63` 講的是「別信陳舊的完成標記」；這裡是**反向**的同一個病 ——
> **別信陳舊的未解標記**。掃描器重跑一次很便宜（`docs/re/75` 的教訓），
> 但重跑之後要拿結果跟既有筆記對，不是直接覆寫。

### `0x106ff` ＝ 海上遇到船的選單，離開後給長安全期

函式 `0x10027` ＝ `1990:2b27`，唯一呼叫端 `0xbe33`。裡面有 `SHIP.SHP`、
`You:`、`%s:`，而選單描述子 `ds:0x1334` 是熟悉的那個形狀
（三個遠指標 + 熱鍵字串，同 `docs/re/67` 的 `1cdc:033d` 慣例）：

```
ds:0x1379 'Attack'   ds:0x1380 'Examine'   ds:0x1388 'Quit'   熱鍵 "AEQ"
```

分派與那處寫入：

```
10745  if (ax == 0xffff) → 106df  離開
1074a  if (ax == 0)      → 106ee  ★
1074f  if (ax == 1)      → 106ee  ★

106ee  +0x9c = Roll(50) + 150            ; 151–200 步不觸發遭遇
10704  al = ds:0x5314[[bp-0x20] << 4]     ; 16-byte stride 表
10713  si = ds:0x52d4 * 6                 ; 6-byte stride
10725  隊伍[+0x25 + si] = al              ; ★ 寫進船隻陣列
1072d  if (隊伍[+0xb9] == 3) 隊伍[+0xb9] = 2
```

`docs/re/28` 已驗證船隻陣列在 **trailer `+0x22`，10 格 × 6 bytes**。
`+0x25` ＝ `+0x22 + 3`，所以這是寫**某艘船記錄的第 4 個 byte**。

**判讀**：海上遇到一艘船 → Attack／Examine／Quit；選了前兩項之一
就給 151–200 步的安全期，並更新那艘船的記錄。安全期這麼長是合理的 ——
`docs/re/24` §58 說船上本來就不擲遭遇，這一處是額外保證離開後不會立刻再撞上同一艘。

> 標**判讀**不是結論：沒追 `0xbe33` 的呼叫脈絡，也沒解 `ds:0x5314`
> 那張 16-byte 表。依 `docs/re/51` 的原則（值套錯地方會直接改掉遭遇節奏），
> **這一處先不實作**。

## 5. ⚠ 重新打開 `docs/re/76`：`ds:0x52d4` 拿來當船隻索引

上面 `0x10713` 用 **`ds:0x52d4 × 6`** 去索引 6-byte 的船隻陣列。

`docs/re/76` 的結論是「`ds:0x52d4` ＝ 子地圖巢狀深度」，並把
`docs/re/04` §103 的「未定案」結案。**用巢狀深度去索引船隻陣列講不通。**

三份筆記的說法現在攤開來是：

| 出處 | 說法 | 支持證據 |
|---|---|---|
| `docs/re/24` §58 | **在船上**（`cmp 0 / jnz 跳過擲遭遇`）| 語意合理，但 `cmp 0` 兩種讀法都成立 |
| `docs/re/76` | **子地圖巢狀深度** | `inc`／`dec` 成對（`0x0c611`／`0x0fb58`／`0x16d4e`）|
| 本篇 `0x10713` | **船隻索引** | `× 6` 對上 `docs/re/28` 已驗證的 stride |

`inc`／`dec` 成對確實排除了「二元開關」，但**沒有排除「船隻索引」** ——
上船 `inc`、下船 `dec` 也是成對的。而 `× 6` 是三者裡最硬的一條：
stride 是 `docs/re/28` 獨立驗證過的數字，不是推測。

**所以 `docs/re/76` §2「深度計數器結案」下得太早**，改標**未定案**。
下一步該做的是逐一讀那三處 `inc`／`dec` 的上下文（是進子地圖還是上船），
而不是再從 `cmp 0` 的用法去猜。

> 這是 `docs/re/76` 自己那條教訓的鏡像。它說「相鄰的位址不代表同類」
> （`0x52d4` vs `0x52f4`），而這次踩的是**「一種存取形狀不代表全部用途」**：
> 30 處存取裡挑出 3 處 `inc`／`dec` 就結案，漏掉了那一處 `× 6`。
> 掃描要掃全部，**下結論也要用全部** —— 定案前先問「有沒有哪一處我解釋不了」。

### 對引擎的意涵（重要）

`nSS.DAT` 會被寫回磁碟，所以它跟 `PARTY.DAT` 一樣受
**「不得覆寫玩家原始存檔」** 這條硬規則管。
本專案的存檔路徑必須把這五個檔一起納進去，而且
**不能直接寫 `workplace/orig/`**（唯讀）。
出廠的 `1SS`／`2SS` 已經是髒的，開新遊戲時要照原版從 `ALL_SS.DAT` 重建。
