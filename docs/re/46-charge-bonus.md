# 46 — 估價的第三項：強度加價

`docs/re/44` 讀出估價公式的前兩項，`docs/re/45` 讀出商隊的開價係數。
剩下的第三項（`1cc4`–`1e10`）在這裡讀完 —— 三條分支，全部是整數。

---

## 1. 三條分支

```
1cc4  if 槽[+0x08]（強度）== 0 → 沒有這一項
1cd1  if 槽[+0x06]（已用次數）== 0xff:          ; 無限次數
1cdf     加價 = trunc(5 × 強度² × 上限 × 0.9)
      else if 槽[+0x05]（上限）> 100:
1d67     加價 = (500 × 強度²) ÷ (上限 − 100)     ; 有號 32-bit 整數除法
      else:
1daa     加價 = trunc(上限 × 強度 × 1.07 × 200)
```

三個常數又是同一個套路：**浮點常數乘出整數**。

> ⚠ **這個套路不是每次都能用。** 第四、六項長得一樣卻不成立 ——
> 差別在乘法順序（`docs/re/49` §4）。這裡能用整數是因為**先乘整數再乘小數**，
> 而且跑過窮舉比對。

| 常數 | 出處 | 相乘 |
|---|---|---|
| `0.9` | `push` 上堆疊（`1d01`）| — |
| `1.07` | `push` 上堆疊（`1daa`）| **1.07 × 200 = 214** |
| `200.0` | `CS:0x3602`（`docs/re/44` §1 的程式段常數）| |

`225 × 1.2 = 270`（第二項）、`1.07 × 200 = 214`（這裡）—— 兩處都是
「原始碼裡寫了個小數，編譯器老實地叫浮點庫去乘」。實作直接用整數，值相同。

---

## 2. `> 100` 那條分界不是隨便切的

`上限 > 100` 那條要除以 `上限 − 100`。**分界正好把除數 0 與負數擋在外面** ——
守衛 (`cmpb $0x64 / jbe`) 與除數 (`add $0xff9c` = −100) 一組一組對得起來。

這是判讀正確的旁證之一：如果我把 `1d5d` 那個比較讀成 `>= 100` 或
把 `0xff9c` 讀成別的偏移，這個關係立刻崩掉。

`3016:000a` 是有號 32-bit 除法（先算兩個運算元的符號、再呼叫
`3016:0068` 的無號除法核心、最後補號）—— 這一步查 Ghidra 反編就看得出來，
不必猜 `lmul` 還是 `ldiv`。

---

## 3. 還缺第四項（已在 `docs/re/49` 補完）

`1e13` 起還有一段：`槽[+0x0a]`（特效值 A 的**原始 byte**）不為 0 時，
拿 `槽[+0x0a] − 10` 去做一段以 **1.4** 為底的運算（`206a:000a`）。
那一段的 dump 對齊有問題，這一輪沒讀乾淨。

> **後來讀完了**（`docs/re/49`），而且後面還有第五、第六項。
> `206a:000a` 是絕對值、`206a:0020` 是正負號，第四項 =
> `trunc(1.4 × |n| × 250) × sign(n)`。`ItemValue` 的 `exact` 已經拿掉。

用原始 byte 而不是 `WeaponEffect`：後者是「兩組類型 15h 的效果值」相加出來的
衍生值，拆不回去（`docs/re/25`），而估價要的就是那個原始 byte。

## 4. 本專案的實作範圍

`internal/game/price.go` 的 `chargeBonus` 與 `ItemValue`；
`internal/assets/scenario` 的現名是 `InventorySlot.EffectValueAByte`
（`+0x0a` 原始值；類型分派後續見 `docs/re/109`）。

測試釘住三條分支各自的算式、`上限 = 100 / 101` 的分界（除數剛好是 1），
以及「`+0x0a` 不為 0 就回報 `exact = false`」。

搭配 `docs/re/45` 的 `MerchantPrice`，**`+0x0a` 為 0 的道具現在算得出
完整的商隊開價**：

```
開價 = trunc( ItemValue(底價, 槽) × (uniform() × 0.8 + 0.6) )
```

購買介面在 `docs/re/47` —— 接上去之後才發現掉寶生成器沒填材質類別，
估價的第一個乘數一直是 0。
