# 主迴圈與頂層狀態機（DEMON.INT 反組譯）

> 分析對象：進入點 `3037:0009` 往下追、主畫面指令分派、時間推進、勝利條件。
> 全部證據來自 `workplace/ghidra/export/`（`disassembly.asm`、`decompiled_all.c`、
> `decompiled/*.c`、`strings.csv`、`functions.csv`），以及對
> `workplace/orig/demwin/DEMON.INT` 原始位元組的直接讀取核對。
> 位址換算一律套用 `docs/re/00-ghidra-setup.md` 的公式：
> `file_offset = segment*16 + offset - 0xC400`。字串位址皆屬 `31f0` 段（DS=SS=`31f0`）。
> 本文與 `docs/re/05-event-triggering.md`（座標→事件、dataset 切換）、
> `docs/re/06-combat-system.md`（戰鬥回合、RNG）互補，三份文件出自同一批並行分析，
> 已交叉核對過共用的函式/欄位（`FUN_222f_0b0e`、`struct+0xa3`、`FUN_1d9f_0dda`），
> 未發現矛盾，僅在需要處引用對方結論，不重複展開。

## 0. 結論先講

- **主畫面指令分派表：已完全解開，含 15 個指令的字串表、按鍵表、指令碼轉換表三張表的
  精確位址與內容，以及泛用選單元件 `FUN_2cdc_033d` 的呼叫慣例。**（§3）

  跟任務單給的「一天 26 小時」說法對不上，本文誠實列出矛盾、不強行套解釋。**（§4）

- **頂層狀態機（overworld / town / dungeon / combat / camp 之間的切換）：只完成部分。**

## 1. 進入點到主迴圈的路徑（部分已驗證）

### 1.1 `entry`（`3037:0009`，277 bytes）—— 標準 C 執行期啟動碼 `[已驗證]`

反編譯內容是教科書式的 16-bit real mode C 執行期 `crt0`：算可用記憶體大小
（`DAT_31f0_47e4` 相關運算）、解析命令列（掃描 `=` 字元、複製 PSP 的 command tail）、
最後透過建構一個假的堆疊框架（把 `0x3000:047a` 之類的值塞進堆疊）呼叫
`FUN_304b_014d`（2 bytes，幾乎必是單一 `RETF`）達成「遠跳轉到 main」的效果。
這一段跟遊戲邏輯無關，純粹是編譯器/連結器產生的樣板碼，**不需要逐行反組譯**。

### 1.2 `FUN_1000_003b`（`1000:003b`）——遊戲啟動後第一個互動畫面 `[已驗證]`

```c
FUN_222f_0832();                 // 未展開（畫面初始化？）
*(undefined2*)0x4c7a = 0x1d;
FUN_2cdc_1727();
FUN_2cdc_033d(0x94);             // 呼叫泛用選單元件（見 §3.2），但參數被 decompiler 弄丟
FUN_1d9f_1361(0x153);            // 印字串 "      Camp"
do {
    uVar1 = FUN_2cdc_033d(0x94);
} while (uVar1 == -1);           // 等待有效輸入
FUN_1000_01e3();                 // 交給下一層 dispatcher
```

字串 `0x153` = `"      Camp"`（原始位元組核對過）。`FUN_1000_01e3`（`1000:01e3`）是一個
以某個未命名狀態變數（`unaff_BP-6`，decompiler 標成未綁定，真實來源待查）分派的
`switch`，其中 `default` 分支與 `case 3` 都會呼叫回 `FUN_1000_003b`，形成
`FUN_1000_003b ⇄ FUN_1000_01e3` 互相呼叫的小迴圈。**這極可能是遊戲啟動後的
「開場/紮營」畫面迴圈**，但本次沒有查出是哪個外部事件（讀檔完成？玩家選了
New/Continue？）讓它跳出並轉進真正的遊戲世界迴圈——**誠實列為未解**（見 §6 建議）。

### 1.3 主畫面指令迴圈 `FUN_222f_0b0e`（`222f:0b0e`，1827 bytes）—— 核心已驗證 `[已驗證]`

這是本文最主要的成果，見 §3。它被 8 個地方呼叫（含自身遞迴一次），呼叫端全是
「完成某個子畫面後，回到主選單讓玩家下指令」的收尾動作：

| 呼叫端函式 | 位址 | 內容線索（字串錨定） | 對應遊戲行為（推測） |
|---|---|---|---|
| `FUN_222f_0b0e`（自身） | `222f:0b0e` | — | 處理完某些指令碼後遞迴呼叫自己，重新進入選單 |
| `FUN_25be_0263` | `25be:0263` | "You carefully avoid the trap" 等 | **Look 指令**的搜查陷阱處理（見 §3.3） |
| `FUN_278d_0932` | `278d:0932` | "Before you is an oddly shaped temple" | 城鎮**教堂/神殿**設施 |
| `FUN_2aed_07be` | `2aed:07be` | "Welcome to the / Guild." | 城鎮**公會**設施（升級/購買糧食） |
| `FUN_2aed_14c2` | `2aed:14c2` | "Level: %d  Experience:" "Skills:" | **角色能力值/技能**檢視畫面 |
| `FUN_206a_02c7` | `206a:02c7` | "Character Utilities" | **角色工具**選單 |
| `FUN_222f_0003` | `222f:0003` | "%dSS.DAT" | 存讀檔（`SS.DAT` = save state）相關 |
| `FUN_1d9f_2a95` | `1d9f:2a95` | 無直接字串 | 未定性（見下） |

`FUN_1d9f_2a95` 同時也被 `docs/re/06-combat-system.md` 提到的戰鬥相關函式
（`FUN_138d_065e`、`FUN_138d_2e63`）呼叫——**它很可能是一個被多處共用的底層工具
函式（畫面/輸入相關），不是獨立的「模式」**，本文不強行替它定性。

這張表本身已經是很強的證據：`FUN_222f_0b0e` 是玩家「站在原地、可以選擇下一步做什麼」
時的中樞——不管是逛街逛到一半查了角色能力值、去神殿捐了錢、還是搜查完陷阱，
最後都會呼叫回這個函式，等待下一次輸入。**這正是任務要找的「讀鍵盤 → 分派」核心迴圈本體**
（至少是它在「非戰鬥、非移動瞬間」狀態下的樣子）。

## 2. 頂層狀態機（部分已驗證，部分未解）

### 2.1 模式判別欄位 `[已驗證，跨三份文件交叉確認]`

- **`struct(0x4c76)+0xa3`（dataset index）**：`docs/re/02` 已知欄位，`docs/re/05` §3.1
  進一步找到寫入點 `FUN_222f_32d4`（跨地城/跨 dataset 切換時設定）。本文在
  `FUN_222f_0763`（見 §4）裡發現一個新的用法：`if (*(byte*)(struct+0xa3) > 9)` 時，
  才會額外做「亂數遭遇檢定」與「查月份對照表」。這跟 `docs/re/05` §3.1 的
  `if (*(byte*)(struct+0xa3) < 10)` 是同一條邊界線的兩面，兩份文件互相印證。
  **注意**：`docs/re/02` 原本把這個欄位理解為「1–5，對應 `DATA1~5.TXT`」，但
  `FUN_222f_32d4` 允許切換到的 dataset 顯然不只 5 個（`< 10` 這個邊界本身就暗示
  最多可能有 9 個），因此「`>9` = 一定在地城」這個推論**只到「假設」層級**，
  比較確定的是「這個欄位控制某個和地城/特殊區域有關的行為開關」。
- **`struct(0x4c76)+0x52d4`（更正：全域變數 `0x52d4`，非 struct 成員）**：在
  `FUN_25be_0e77`（`docs/re/02`）與 `FUN_222f_0763`（本文 §4）都被當作二元開關檢查
  （`==0` 才繼續某條路徑）。兩處用法都指向「目前是否處於某種會暫停一般規則的畫面/
  狀態（例如查看角色詳細資料）」，但**確切語意仍未定案**，本文與 `docs/re/02` 一樣
  列為未解。

### 2.2 戰鬥的觸發與收尾 `[已驗證，含新發現的隨機遭遇路徑]`

已知路徑（`docs/re/02`、`docs/re/05`、`docs/re/06` 已驗證）：

```
FUN_25be_0e77（DATA*.TXT 事件讀取，見 docs/re/02）
  └─ count != 0 時 → FUN_17c5_000d（戰鬥初始化，17c5:000d）
       └─ FUN_17c5_05f8
            └─ FUN_138d_0002（戰鬥主迴圈，見 docs/re/06 §1.1）
```

**本文新發現的第二條戰鬥觸發路徑**（`FUN_222f_0763`，見 §4）：每輪主迴圈呼叫時，
若 `dataset(0xa3) > 9` 且 `mode(0x52d4) == 0` 且 `(FUN_1d9f_0dda() & 0x3f) == 0x34`
（1/64 機率，`FUN_1d9f_0dda` 已由 `docs/re/06` §3-4 確認是 RNG 呼叫鏈的一環），
則回傳特殊碼 `0x17`（23）。這條路徑**沒有經過 `EXITS.DAT` 或 `DATA*.TXT` 事件表**，
是純粹的「地城裡每次行動都有 1/64 機率隨機遭遇」機制——**這是本文對
`docs/re/06-combat-system.md` 沒有涵蓋的「戰鬥從哪裡被觸發」問題的補充**，
但**回傳碼 `0x17` 之後具體怎麼接到 `FUN_17c5_000d` 沒有追完整**（只確認這個訊號
存在、RNG 機率、閘門條件三者，接續的分派邏輯落在 `FUN_222f_0b0e` 內被
decompiler 弄壞的那段 switch 裡，見 §3.4 的誠實列表）。

戰鬥結束後怎麼「回到」`FUN_222f_0b0e`：本次沒有直接追出 `FUN_138d_0002` 的
`return` 值如何一路傳回 `FUN_222f_0b0e` 觸發它重新進入選單迴圈——推測（**未驗證**）
是透過 `FUN_25be_0e77` 的回傳值往上層層傳遞，最終被 `FUN_222f_0b0e` 自身的某條
分支接住後遞迴呼叫自己，但這條路徑上的中介函式（`FUN_25be_0e77` 的呼叫端）
本次沒有查。

### 2.3 城鎮（town）已知機制 `[已驗證，引用既有文件]`

### 2.4 未解：overworld 移動迴圈、town↔overworld 切換 `[誠實列為未解]`

Ghidra 對這幾個候選函式的反編譯品質很差（大量 `Removing unreachable block` 警告，
反編譯輸出動輒數千行，明顯是把跳表/switch 誤判成一般程式碼流程，跟
`docs/re/00-ghidra-setup.md` 事先警告的最壞情況一致）：

| 函式 | 位址 | 宣告大小 | decompiled .c 行數（膨脹倍率反映跳表誤判程度） |
|---|---|---|---|
| `FUN_1d9f_2a95` | `1d9f:2a95` | 1410 bytes | 5283 行 |
| `FUN_206a_02c7` | `206a:02c7` | 802 bytes | 4242 行 |
| `FUN_222f_0003` | `222f:0003` | 1076 bytes | 4744 行 |
| `FUN_25be_0263` | `25be:0263` | 721 bytes | 7443 行 |
| `FUN_278d_0932` | `278d:0932` | 1050 bytes | 6598 行 |
| `FUN_2aed_07be` | `2aed:07be` | 1622 bytes | 4180 行 |
| `FUN_2aed_14c2` | `2aed:14c2` | 2563 bytes | 5695 行 |

宣告大小都只有幾百到兩千多 bytes（合理的函式規模），但反編譯輸出卻是數千行，
差距達 4~10 倍，這是 decompiler 對間接跳轉/switch 分析失敗、把資料誤判成
控制流、又不斷產生「unreachable block」重複展開的典型癥狀。這代表：

- 這些函式**本身不是「巨大到不可能是單一模式函式」**——大小上完全合理，
  很可能就是「你在城鎮設施 X／你在角色工具選單」這種單一畫面的完整邏輯。
- 但要從裡面**逐行核對**找出「進入 town 模式」「離開 town 模式」這種轉移條件，
  需要照 `docs/re/00-ghidra-setup.md` 建議的方式繞開 decompiler、直接讀
  `disassembly.asm`（本文 §3、§4、§5 都是用這個方法成功解開的），但這幾個函式
  單獨要花的時間超出本次任務的時間預算，**誠實列為下一步**（見 §6）。

## 3. 主畫面指令分派表 `[已完全驗證]`

### 3.1 三張表的精確位址與內容

用字串錨定法在 `FUN_222f_0b0e` 內找到三張平行表，全部位於 `31f0` 段，緊接在一起：

**表一：指令標籤字串（15 個遠指標，每筆 4 bytes：offset word + segment word）**
位址 `31f0:2113`，segment word 固定是連結期值 `0x21f0`（= 執行期 `0x31f0`，跟
`docs/re/00` 驗證過的 base segment 換算一致）：

| # | offset | 字串 | # | offset | 字串 |
|---|---|---|---|---|---|
| 0 | `219a` | `Walk` | 8 | `21cd` | `Examine` |
| 1 | `219f` | `Party info` | 9 | `21d5` | `Use` |
| 2 | `21aa` | `Save Game` | 10 | `21d9` | `Inspect` |
| 3 | `21b4` | `Camp` | 11 | `21e1` | `View room` |
| 4 | `21b9` | `Look` | 12 | `21eb` | `X)View item` |
| 5 | `21be` | `Take` | 13 | `21f7` | `Read descr.` |
| 6 | `21c3` | `Drop` | 14 | `2203` | `Quit` |
| 7 | `21c8` | `Move` |  |  |  |

（原始位元組核對：檔案位移 `0x27c13`起，直接讀 `DEMON.INT` 逐筆比對過，內容吻合。）

**表二：按鍵表（15 bytes，緊接在 `31f0:216d`）**：

```
216d: W P S C L T D M E U I V X R Q
```

逐一對應表一同一順序：Walk=`W`、Party info=`P`、Save Game=`S`、Camp=`C`、Look=`L`、
Take=`T`、Drop=`D`、Move=`M`、Examine=`E`、Use=`U`、Inspect=`I`、View room=`V`、
X)View item=`X`、Read descr.=`R`、Quit=`Q`。**這就是任務單要找的「按鍵→指令」
分派表本體**（原始位元組核對過）。

**表三：指令碼轉換表（11 words，緊接在按鍵表後方 `31f0:217c`，只涵蓋選項 4–14）**：

```
217c: 0004 0007 0009 000f 0008 000a 000e 000c 000b 000d 0005
      Look Take Drop Move Exam Use  Insp View XView Read Quit
```

即：選項 index（4–14）先乘 2 當位移加到 base `0x2174`（注意這個 base **落在按鍵表
尾端 7 個字元「MEUIVXRQ」中間**，只是巧合地重疊——因為選項 0–3 永遠不會走到這條
查表路徑，所以重疊的位元組沒有被誤用）取出對應的「內部指令碼」，這個碼才是後續
`switch` 真正判斷的值。

### 3.2 泛用選單元件 `FUN_2cdc_033d`（`2cdc:033d`）與呼叫慣例 `[已驗證]`

`FUN_222f_0b0e` 對這三張表的呼叫方式（`disassembly.asm` 222f:0d50–0d9c 逐行核對）：

```asm
; 第一次呼叫：flag=0（只畫面，不等輸入）
MOV AX,0x0        / PUSH AX          ; param5 = 0
PUSH DS / MOV AX,0x216d / PUSH AX    ; param4 = DS:0x216d（按鍵表）
PUSH DS / MOV AX,0x214f / PUSH AX    ; param3 = DS:0x214f（另一張旗標表，見下）
PUSH DS / MOV AX,0x2113 / PUSH AX    ; param2/1 = DS:0x2113（字串表）
CALLF FUN_2cdc_033d
ADD SP,0xe

; 第二次呼叫：flag=1（等玩家輸入，回傳選到的 index）
MOV AX,0x1 / PUSH AX  ...(同上三張表)...
CALLF FUN_2cdc_033d
ADD SP,0xe
MOV [BP-0x2],AX        ; 儲存選到的 index
CMP AX,0xffff / JZ ...  ; -1 = 取消/ESC
CMP AX,0x3    / JLE ... ; <=3（Walk/PartyInfo/SaveGame/Camp）走另一條路徑，不查表三
ADD AX,0xfffc           ; index-4 存進 0x4c84（用途未展開）
MOV BX, index*2
MOV AX,[BX+0x2174]      ; 查表三，取得內部指令碼
```

`FUN_2cdc_033d` 本身反編譯品質很好（無跳表警告），完整簽名
`FUN_2cdc_033d(int *param_1, ..., int param_5)`：`param_5==0` 時只重繪畫面（含
「只重繪跟上次不同的項目」的差異偵測），`param_5!=0` 時進入輸入迴圈——用
`swi(0x16)`（**BIOS INT 16h 鍵盤服務**）讀鍵，辨識方向鍵（掃描碼 `0xf00`/`0xf09`，
上下移動游標）、Enter（`0x1c0d`）、以及呼叫 `FUN_2cdc_0059` 比對熱鍵字元（表二），
回傳選到的 index 或 `-1`。**這是整個遊戲共用的泛用選單元件**——程式啟動的第一個
畫面（`FUN_1000_003b`，§1.2）也呼叫它，代表遊戲裡所有「列表選單」（施法、選城鎮
設施、選存檔……）很可能都共用這同一支函式，只是傳入不同的三張表。這對 Go 重製
是個好消息：只要把這個元件實作對，所有選單畫面都可以復用同一套邏輯。

`param3`（`0x214f`）目前只確認是一張大多數為 `1`（啟用）、少數為 `0`（停用）的

## 4. 時間推進邏輯 `[機制已驗證，欄位語意有已知矛盾，誠實列出]`

### 4.1 三層進位計數器 `FUN_222f_0763`（`222f:0763`，207 bytes）

這個函式是 `FUN_222f_0b0e` 主迴圈**每一輪最先呼叫的函式**（`disassembly.asm`
`222f:0763` 附近的呼叫序列位在整個 dispatcher 最前段），反編譯完全乾淨、
零警告，邏輯如下（`decompiled/222f_0763_FUN_222f_0763.c`）：

```c
if (struct+0x9f == 0x26 /* 38 */) {
    struct+0x9f = 1;                      // 歸位
    struct+0x9e += 1;                     // 進位到中層
    if (struct+0x9e == 0x23 /* 35 */) {
        struct+0x9e = 1;                  // 歸位
        struct+0x9d += 1;                 // 進位到最外層
        if (struct+0x9d == 0x17 /* 23 */) {
            struct+0x9d = 1;              // 歸位
        }
    }
    if (dataset(0xa3) > 9) { /* 查月份對照表 0x209c，見 4.2 */ }
    return 0x1a;   // 26 —— 特殊回傳碼，推測「一輪完整循環發生」的訊號
} else {
    if (dataset(0xa3) > 9) { /* 同上查表 */ }
    if (struct+0x9f == 0x18 /* 24 */) { return 0xe; }   // 14，用途未查
    if (dataset(0xa3) > 8 && mode(0x52d4)==0 && (RNG()&0x3f)==0x34) {
        return 0x17;   // 23 —— 隨機遭遇觸發（見 §2.2）
    }
    return 0;

```

**注意：本函式沒有把 `struct+0x9f` 本身加 1 的動作**——它只檢查/歸位。真正讓
`0x9f` 遞增的程式碼本次沒有查到（合理猜測在移動/行走的指令處理裡，每走一步 +1，
但沒有反組譯出來，見 §6 建議）。

### 4.2 跟 `Hour %d, Day %d in the Month of the %s` 顯示的交叉驗證

`FUN_1000_33e8`（`1000:33e8`）建構這個字串時用的欄位（`disassembly.asm`
`1000:34ac`–`34d6` 逐行核對）：

```asm
MOV AL,[BX+0x9d] → 查表 [BX+0x50f2/0x50f4] 取得「月份名稱」遠指標
MOV AL,[BX+0x9e] → PUSH（第一個數值參數）
MOV AL,[BX+0x9f] → PUSH（第二個數值參數）
PUSH "Hour %d, Day %d in the Month of the %s"（31f0:0618）
CALLF FUN_2f30_000e（sprintf 類函式）
```

`struct+0x9d` 同時被 `FUN_222f_0763`（§4.1）當作**進位最外層、變動最慢**的欄位，
也被這裡當作**月份名稱查表索引**——兩處用法一致，可以確定 `struct+0x9d = 月份`。

### 4.3 矛盾與誠實結論

若照「進位速度」排序（`0x9f` 最快、`0x9e` 次之、`0x9d` 最慢，符合「時→日→月」
的直覺順序），則 `0x9f` 應是「小時內的計步」、`0x9e` 是「小時」、`0x9d` 是「月」，
但 `FUN_222f_0763` 的進位鏈只有兩級（`0x9f`→`0x9e`→`0x9d`），**沒有第四個更快的
欄位**，這代表 `0x9f` 本身很可能就是被顯示的「小時」欄位，而不是額外的計步層。

若 `0x9f`（wrap 於 `0x26`=38）＝小時、`0x9e`（wrap 於 `0x23`=35）＝日、
`0x9d`（wrap 於 `0x17`=23）＝月，則意味著這個遊戲世界是「一天 38 小時、
一月 35 天、一年 23 個月」——**跟任務單提到的「一天 26 小時（攻略已知）」
對不上（38 ≠ 26）**。

**本文的立場**：進位機制本身（三層 odometer 式進位、觸發函式、觸發時機＝主迴圈
每輪一次）**已驗證，信心很高**（反編譯乾淨、無警告、跟顯示函式的欄位交叉吻合）。
但「`0x9f` 到底是不是玩家理解的『小時』」**存疑**——可能是：
(a) 攻略記載的「26 小時」本身不準確或講的是別的東西，或
(b) `0x9f` 的遞增速度不是「每步 +1」而是某個非均勻節奏（例如某些動作 +1、某些不會），
    使得「wrap 於 38」跟「玩家觀察到的 26 小時一天」在體感上仍然一致（此假設未驗證），或
(c) 顯示字串的 `%d %d %s` 三個參數實際對應順序跟本文 §4.2 的推斷相反
    （因為 `FUN_2f30_000e` 內部消耗參數的精確順序本次沒有逆向到底，
    push 順序與 vararg 消耗順序不一定同向，見 `docs/re/02` 對同一類函式的類似警語）。

> **協調者補充假設 (d)（2026-07-25）：攻略的「26」很可能是把十六進位當十進位讀。**
>
> hour 的 wrap 常數在程式碼裡**字面就是 `0x26`**，而攻略寫的是「一天 26 小時」。
> 數字 2 和 6 完全一致，這不像巧合 —— 比較可能是某個環節（攻略作者本人、
> 或他參考的更早期資料）從十六進位編輯器 / 反組譯裡讀到 `0x26` 就直接寫成 26，
> 沒做進位轉換。若成立，遊戲的真實日長就是 **38 小時**，攻略記載才是錯的，
> 而反組譯結果沒有矛盾。
>
> 同一組數字也支持這個讀法：`0x23`=35（日）、`0x17`=23（月）——
> 若攻略作者只抄了小時那一個常數，就只會在「26」這一處露餡。
>
> **這個假設有極便宜的驗證方式**：DOSBox 跑原版，反覆行動推進時間，
> 看小時欄位是走到 25 就翻頁，還是走到 37 才翻頁。一次實測即可定案。
> 在實測前，本文維持「未解」不改判 —— 但假設 (d) 應列為最優先待驗項，
> 因為它同時解釋了矛盾、且不需要任何額外的未知機制。
>
> 附帶提醒：這也是**低層級 oracle 不可推翻高層級**原則的反例情境 ——
> 攻略（第 3 級）與反組譯（第 4 級）衝突時，通常以攻略為準；
> 但這裡有具體理由懷疑攻略本身有轉換錯誤，所以要靠 DOSBox 實跑（第 2 級）裁決。

**本文不強行調和這個矛盾，只把三層進位機制本身當作「已驗證」的成果，
欄位對應「小時/日/月」哪一個標籤，全部標記為「假設、信心中等」。**
這也連帶表示：**`docs/re/01-dosbox-reference.md` 提到的存檔候選欄位「`0x5b4` 每步
+1」，本次找到的 `struct+0x9f`（記憶體內、wrap 於 38）在數值行為上並不是同一件事
——`0x5b4` 是存檔格式內的位移，`0x9f` 是執行期記憶體位移，兩者換算關係本次沒有
建立，`0x5b4` 這個候選欄位本文既不能升級成已驗證，也沒有找到反證，維持原狀。**

## 7. 給 Go 引擎的藍圖

以現有證據，建議把「頂層互動」拆成三層，對應反組譯發現的實際邊界，而不是強行
套用 overworld/town/dungeon/combat 四個獨立 state（因為反組譯目前看到的實情是
「一個中樞選單迴圈 + 一堆各自獨立的子畫面函式」，不是四個平行的大狀態）：

1. **`GenericMenu` 元件**（對應 `FUN_2cdc_033d`）：吃三個表（labels、hotkeys、
   enabled-flags）與一個 draw/select flag，回傳選到的 index 或取消。這是全遊戲
   共用的 UI 原語，Go 端做成一個可重用的 widget，之後每個畫面（施法、選城鎮
   設施、主指令選單……）都用它組出來，不要每個選單各寫一套。
2. **`MainCommandLoop`**（對應 `FUN_222f_0b0e`）：中樞狀態，職責是：
   (a) 呼叫時間推進檢查（對應 `FUN_222f_0763`，含隨機遭遇判定）、
   (b) 顯示主指令選單（表一/二/三，§3.1）、
   (c) 依選到的指令碼分派到對應的「子畫面」函式（Look/Examine/Inspect/…），
