## 1. 為什麼這次找得到（方法論筆記）

`docs/re/10-character-and-economy.md` 上一輪的結論是「城鎮經濟程式碼落在 Ghidra
未發現區域」，本輪推翻了這個悲觀結論的一半。關鍵差異：

1. **直接搜尋字串在 `disassembly.asm` 裡的引用位置**（`MOV AX,0x<offset>` 這個 pattern），
   而不是只看 `decompiled_all.c`。多個目標函式的 decompiler 輸出完全損毀
   （`Removing unreachable block` 洗版、`Type propagation algorithm not settling`），
   但**原始指令都還在**，字串引用一樣抓得到。
2. **系統性列出「每個 segment 內，前一個函式結束到下一個函式開始之間的空隙」**，
   逐一檢查空隙裡有沒有落著目標字串的引用——這次靠這招額外抓到神殿/祈禱與碼頭。
3. **檢查 segment 最前面、在第一個被 Ghidra 命名的函式之前**的區域——這次靠這招
   抓到了治療所（整個函式，`functions.csv` 完全沒收錄，但 `disassembly.asm`
   仍然線性掃描出了完整、可讀的指令序列）。
4. **系統性列出全檔所有「扣款」指令**（`SUB word ptr ES:[BX + 0xa]` 這個特徵 pattern，
   對應 32-bit 金幣扣款）——這招把神殿、學院、碼頭、治療所四個地方的扣款點
   一次全部列出來，比逐一字串錨定更完整、更不會漏掉。

這四招合起來，把原本「Ghidra 完全沒找到」的判定，修正成「Ghidra 有反組譯、
只是沒建函式邊界、decompiler 沒被叫去分析」。

> **初版此處寫「市集／議價是唯一一個連 `disassembly.asm` 都找不到任何引用的例外」，
> 這是錯的**。市集的程式碼一直都在 `disassembly.asm` 裡（`278d:0098` 的初始化段、
> `278d:2500`–`2f61` 的主體），初版沒讀完是時間預算問題，不是資料不存在。
> **本專案沒有任何一段已知的遊戲邏輯真的落在「Ghidra 完全沒走到」的區域** ——
> 這四招目前為止百分之百有效。

### 3.2 捐獻（Donate）`[已驗證，含指令級證據]`

字串錨定：「Amount of gold to donate?」（`31f0:327c`）、
「I'm afraid you do not have that much!」（`31f0:3297`）、
「"Bless you, my son"」（`31f0:32bd`）。

```
278d:0c19-0c3e   選角色（傳入參數 0），取消則返回
278d:0c44        印 "Amount of gold to donate?"
278d:0c6e        呼叫讀數字輸入（0x2000:f1ef），結果存進 DX:AX（32-bit）
278d:0c7c-0c88   若輸入 < 1，跳過（不執行捐獻）
278d:0c8b-0c9d   32-bit 比較：輸入金額 vs 隊伍金幣(struct+0xa/+0xc)

278d:0cde-0cf9   char.EXP(記錄內 0xc4起) += 輸入金額（32-bit ADD/ADC，見下方 §3.2.1）
278d:0d0a-0d26   若 EXP 結果 > 0x00FFFFFF，封頂在 0x00FFFFFF
```

**公式：`捐獻 N 金幣 → 該角色 EXP += N`，1:1，無倍率。** 跟
`docs/manual/part-2.md`「每捐獻 1 枚金幣，該教堂的守護神就會回饋 1 點經驗值」
**完全吻合**，指令級證據，信心等級最高。

#### 3.2.1 副產品：解決了 `docs/re/10` §7.3 留下的 EXP 欄位寬度疑點

`docs/re/10-character-and-economy.md` §7.3 觀察到升級檢查讀 EXP 時是讀兩個相鄰
word（暗示 4 bytes），但攻略原文說是 3 bytes，該文誠實列為「觀察，非定論」。
**本文的捐獻程式碼給出決定性證據**：EXP 加法是 `ADD word[+0xc4],AX` /
`ADC word[+0xc6],DX`（32-bit 加法橫跨兩個 word），且緊接著的封頂檢查明確是
`CMP word[+0xc6],0xFF` / `CMP word[+0xc4],0xFFFF`（比較 32-bit 值是否超過
`0x00FFFFFF`）。

**結論：EXP 欄位實際上是 4 bytes（`0xc4`–`0xc7`）儲存空間，但遊戲邏輯把它的
有效值封頂在 `0x00FFFFFF`（16,777,215，也就是 3-byte 範圍的上限）。** 這解釋了
攻略「3 bytes」的說法（正常遊玩範圍內第 4 byte 恆為 0，肉眼／簡單工具檢查會
誤判成 3-byte 欄位）——兩份文件都對，只是描述的是同一件事的不同層面
（**儲存寬度 4 bytes** vs **數值上限對應 3 bytes**）。此為本次任務範圍外的
副產品發現，留給 `docs/formats/game-data-tables.md` 維護者合併。

### 5.2 四項服務的收費公式

> **2026-07-25 更正**：原本寫「四個費率由呼叫端傳入」，**這是錯的**。
> `[BP-2]`…`[BP-8]` 是負的 BP 位移，也就是**區域變數**，不是參數。
> 它們在函式開頭（`2aed:0011`–`005b`）就地從城鎮經濟係數算出來，沒有呼叫端參與。
> 完整推導見下方 §5.2.1。

四個服務的「每單位費率」存在區域變數 `[BP-2]`＝治療／`[BP-4]`＝解毒／
`[BP-6]`＝解束縛／`[BP-8]`＝復活，收費的**乘數結構**如下：

```
2aed:0159-016f  讀 char.status(記錄內 +0x102)：
                 0 = 正常（僅受傷，適用「治療」）
                 1 = 中毒（適用「解毒」）
                 2/3/4 = 束縛類狀態（三個子等級，適用「解除束縛」）
                 5 = 死亡（適用「復活」）

若 status == 5（死亡）：
    cost = char.level(+0xf4) × 復活費率[BP-8]

若 1 < status < 5（束縛類，2/3/4）：
    cost = char.field(+0xec) × 解束縛費率[BP-6]      ; +0xec，見 §7，猜測是「束縛法術的等級」

若 status == 1（中毒）：
    cost = 解毒費率[BP-4]                              ; 固定費用，不乘任何欄位

否則（status == 0，一般外傷）：
    damage = char.max_hp(+0xfc) - char.cur_hp(+0xfd)
    cost = damage × 治療費率[BP-2]
```

**驗收後續（成功付費）：**

```
2aed:0250-0258   隊伍金幣 -= cost（32-bit SUB/SBB，struct(0x4c76)+0xa/+0xc）
2aed:0268        char.status(+0x102) = 0（清除狀態，四種情況皆執行）
若原本 status==5（死亡）：
    2aed:0280    char.cur_hp(+0xfd) = 1        ← ★ 復活後恢復 1 點生命值
    2aed:0292    char.field(+0xec) = 0
若原本 status==0（一般外傷）：
    2aed:02af    char.cur_hp(+0xfd) = char.max_hp(+0xfc)   ← 治療後補滿生命值
```

**這跟手冊逐句對應，全部吻合：**

| 手冊原文 | 程式碼證據 |
|---|---|
| 「解毒收取固定費用」 | `cost = 解毒費率[BP-4]`，不乘任何欄位 |
| 「解除束縛……費用依束縛法術的等級而定」 | `cost = char+0xec（束縛等級）× 費率` |
| 「復活的費用則依待復活角色的等級而定」 | `cost = char.level × 復活費率` |
| 「在城鎮中的復活必定成功，並會為角色恢復 1 點生命值」 | 沒有任何失敗機率判定（純粹是金幣夠不夠的問題），成功後 `cur_hp = 1` |

#### 5.2.1 四個費率的來源 `[已解，2026-07-25]`

函式開頭 `2aed:0011`–`005b`，全部從城鎮經濟係數 `E = 城鎮表[+0x1ed]` 就地算出：

```asm
2aed:0023  MOV CX,0x5 / CWD / IDIV CX

2aed:002f  SHL AX,0x1 / SHL AX,0x1
2aed:0033  MOV [BP-0x4],AX

2aed:003f  MOV CL,4 / SHL AX,CL         ; 48E
2aed:0043  SUB AX,DX                    ; 47E
2aed:0045  MOV CX,5 / CWD / IDIV CX     ; 47E / 5

2aed:0053  SHL AX,1 / SHL AX,1 / ADD AX,DX / SHL AX,1
```

### 7.2 購買定價

`ITEMS.DAT` 是 30 件 × 8 個 NUL 分隔欄位的 ASCII 檔，第 1 個數值欄是價格
（匕首 2、小斧 6、短劍 15、釘頭鎚 13、晨星鎚 20、闊劍 30、戰斧 65、雙手劍 100…）。

所以是**全遊戲共用一份定價**，城鎮只決定「賣不賣」與係數，
不是每個城鎮各存一份價目表。（初版把這兩種可能並列，現已擇定。）

> 旁證：`ITEMS.DAT` 是 30 件，而議價狀態陣列 `0x6054` 正好初始化 30 格（`CMP AX,0x1e`）。
> 武器在檔案中的順序也與 `docs/spec/02-combat.md` 武器骰表索引 1–8 一致。

### 7.3 議價（Haggle）`[已全解]`

每件商品有一個議價狀態值，存在 `0x6054 + 商品索引 × 2` 的 word 陣列。

#### 說服技能怎麼介入：決定初始值

市集初始化（`278d:0098`–`0100`）：

```asm
haggle_state = 1
for 每個隊伍成員:
    if (char[+0xd1] != 0)        ; ← 「說服」技能旗標（技能 id 9）
        haggle_state = 0
for i in 0..29:                   ; 30 件商品
    [0x6054 + i*2] = haggle_state
```

`278d:00b8` 的 `CMP byte ptr ES:[BX + SI + 0xd1],0x0` 是**全檔唯一一處**讀這個旗標。

**效果**：隊伍中只要有一人會說服，所有商品的初始狀態從 1 變成 0，
而下面兩道判定的門檻都與狀態成正比 → **第一次議價變成必定成功**。
這就是手冊「隊伍中若有角色具備說服技能，議價時會自動納入考量」的實作。

#### 兩道判定

```
s = 該商品的議價狀態

1) 若 Roll(100) < s × 10:
       印 "You have insulted the merchant"
       狀態 = 1000            ← 此商品從此拒賣（1000×10 遠大於 100，之後必定觸怒）
       結束

2) 否則若 Roll(100) < s × 15:
       印 "The merchant stands firm"        ← 議價失敗，價格不變
       若 s < 100 → s += 100
       結束

3) 否則:
       議價成功
       s += 1
```

**第 2 步的 `+= 100` 是關鍵**：失敗一次後 `s ≥ 100`，第 1 步的 `s × 10 ≥ 1000` 恆大於
`Roll(100)` 的上限 → **只要「stands firm」過一次，下次議價必定觸怒商人、該商品永久拒賣**。
對應手冊「若不斷議價……可能會被冒犯，從此拒絕以任何價格出售」。

有說服（s 從 0 起算）時的風險曲線：

| 議價次數 | s | 觸怒機率 | 談不攏機率 | 成功機率 |
|---|---|---|---|---|
| 第 1 次 | 0 | 0% | 0% | **100%** |
| 第 2 次 | 1 | 10% | 15% | 75% |
| 第 3 次 | 2 | 20% | 30% | 50% |
| 第 4 次 | 3 | 30% | 45% | 25% |
| 第 5 次 | 4 | 40% | 60% | 0% |

無說服時整條往前挪一格（第 1 次就是 s=1 那一列）。

#### 成功後價格怎麼降

```
n = s
若 n == -1  → n = 0
若 n > 99   → n -= 100          ← 剝掉「談不攏」加的那 100
新價 = max(2, 基礎標價 − 基礎標價 × n × 0.06)
```

折扣常數 `0.06` 是 IEEE double，存在**程式段相對位址** `278d:0x35e2`
（file offset `0x1EAB2`，位元組 `b8 1e 85 eb 51 b8 ae 3f`）。

也就是**每次成功議價打掉基礎標價的 6%**，價格下限 2 金幣。
搭配上表：有說服的角色穩拿 6% 折扣，想要 12% 就得冒 10% 永久拒賣的風險。

### 7.4 出售（Sell）`[已解]`

```
售價 = ITEMS.DAT 基礎價 / 2          ← 整數除法
印 "The merchant offers you: %ld"
確認後：道具槽第 0 個 byte = 0xff（清空）
        隊伍金幣 += 售價，封頂 0x00FFFFFF
```

**售價不套用城鎮經濟係數** —— 買價會乘 `E/10`，賣價不會。
這是原版的不對稱設計，重製時要照做。

手冊「賣價約新品半價」**吻合**（而且不是「約」，就是精確的一半）。

### 7.5 鑑定（Identify）`[已解，與手冊有出入]`

```
若 道具槽[+0x10] != 0 → 印 "It's already identified!" 並中止
道具槽[+0x10] = 1
顯示道具完整資訊
隊伍金幣 -= 城鎮經濟係數 × 5
```

**費用 = `E × 5`，與道具種類無關。**

> 手冊寫「鑑定固定 75 金幣」。`E = 15` 時 `5E = 75`，所以手冊記的應該是
> 某個常見城鎮的實際值；「固定」要理解成**與道具無關**，而不是**每個城鎮都一樣**。
> 這與治療所、糧食、修船的模式一致（全部隨 `+0x1ed` 浮動）。

旁證：`[+0x10]` 是道具槽記錄的最後一個 byte —— 背包槽 stride 是 `0x11`（17 bytes），
與 `docs/re/20` §6 玩家單位讀裝備時用的 `裝備索引 × 0x11` 吻合。

### 7.6 城鎮經濟係數 `+0x1ed` 的完整用法一覽

到此共 **9 處**用到同一個欄位，全部是價格相關，可以確定它是城鎮的物價指數：

| 用途 | 公式 |
|---|---|
| 市集買價 | `基礎價 × E / 10` |
| 市集鑑定 | `E × 5` |
| 酒館糧食 | `E / 5`（下限 1）|
| 碼頭修船 | `(75 − 船體值) × E / 2` |
| 治療所・治療 | `E / 5` 每點傷 |
| 治療所・解毒 | `E × 4` 固定 |
| 治療所・解束縛 | `47E / 5` 每級 |
| 治療所・復活 | `E × 10` 每級 |

（碼頭買船用的是另一個欄位 `+0x1f5`，售價 `= 該值 × 10`；市集賣價則完全不看城鎮。）
