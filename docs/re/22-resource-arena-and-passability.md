## 1. 資源記憶體區（18 段）

`FUN_1d9f_*` 的初始化段把一整塊 buffer 切成 18 個連續區塊：

```c
*(int *)0x548c = 基底 + 起始偏移;                    // 指標[0]
for (i = 0; i < 0x11; i++) {                         // 17 次
    len = *(int *)(i*4 + 0x1535);                    // 長度表，stride 4
    if (len % 2 == 1) len++;                         // 補齊到偶數
    指標[i+1] = 指標[i] + len;
}
```

指標陣列在 `0x548c + i*4`，長度表在 `DS:0x1535`。

### 長度表定位

用兩個已知錨點反推：`0x5508`（＝指標索引 7）指向技能學費表（`FILES.DAT 0x158`，310 bytes），
`0x5510`（＝索引 9）指向種族上限表所在的區塊。搜尋 `DEMON.INT` 裡「310 後接 404、stride 4」
的位元組樣式，**唯一命中 `0x27051`**，回推長度表 index 0 在 file offset `0x27035`。

### 18 段的內容

| idx | 長度 | 全域指標 | 已知內容 |
|---|---|---|---|
| 0 | 1494 | `0x548c` | **＝ `PARTY.DAT` 的檔案大小**，隊伍存檔緩衝區 |
| 1 | 0 | `0x5490` | 空 |
| 2 | 256 | `0x5494` | 未知（256-byte 檔的緩衝區）|
| 3 | 5829 | `0x5498` | 未知 |
| 4 | 64 | `0x549c` | `FILES.DAT 0x000`，未知 |
| **5** | **104** | **`0x5500`** | **`FILES.DAT 0x040`，可通行性表**（見 §2）|
| 6 | 176 | `0x5504` | `FILES.DAT 0x0A8`，未知 |
| 7 | 310 | `0x5508` | `FILES.DAT 0x158`，**技能學費表** 31×10 |
| 8 | 404 | `0x550c` | `FILES.DAT 0x28E`，未知 |

**索引 4–9 六段的長度加總 = 64+104+176+310+404+1196 = 2254 = `FILES.DAT` 的檔案大小**，
且索引 9 的 1196 恰好等於 `docs/re/20` §1 那條指標鏈的四段之和（60+430+420+22+264）。
兩條獨立推導互相吻合，**`FILES.DAT` 的整份布局到此完全閉合**。

> 這也解釋了 `EXITS.DAT` 為什麼可以讀到 `0x1ff`（511）——
> 緩衝區就是 511 bytes，比 330 bytes 的檔案大，尾端留給傳送目標座標。
> `docs/re/20` 曾把這點列為「緩衝區佈局未確認」，現已確認。

## 2. 可通行性表（`FILES.DAT 0x040`）

### 索引方式

移動主路徑（`222f:0e05`–`0e44`）：

```asm
AX = 面向 × 2 → BX
[BP-0x8] = 目前線性位置 + [BX + 0x2107]     ; 線性位移增量表
[BP-0xa] = 目前 X       + [BX + 0x15da]     ; ΔX 表
[BP-0xc] = 目前 Y       + [BX + 0x15d2]     ; ΔY 表
LES BX,[0x4c94]                              ; 地圖緩衝區
AL = 地圖[新線性位置]
AX &= 0x7f                                   ; ← 遮罩，tile 值域 0–127
[BP-0xe] = AX
LES BX,[0x5500]
AL = 表[tile]                                ; ← 可通行性查表
```

**tile 值先與 `0x7f` 遮罩**，所以理論索引範圍是 0–127。
但區塊只配置 104 bytes，而**實際用到的最大 tile 值是 `0x64`(100)**
（`docs/re/05` 的五個特殊 tile 之一）。索引 101–103 的值（141/160/211）
與其他項的值域（`0–7` 與 `253–255`）明顯不同調，判定為填充。

> **有效範圍是 tile 0–100，共 101 項。** 實作時對 ≥ 101 的 tile 應視為未定義，
> 不要照抄記憶體裡的相鄰位元組。

### 表的內容

```
tile:   0   1   2   3   4   5   6   7
  0 |   4   0   0   0   0   0   0   0
  8 |   0   0   0   0   0 255   3   2
 16 |   2 254 254   4 255 254 254   1
 24 | 255 255   1 255 255   1 255 255
 32 |   1 255 255   1 253 254 254   1
 40 |   7   1 255   3 253 253 254 253
 48 | 254 255 254 255 254 254 253 253
 56 |   1 253 255 255 255 255 255 254
 64 | 254 254 254   7   7   7   7 255
 72 | 255 255 255 255 255 255 255   1
 80 | 255 255 255   4 255 253   6 255
 88 | 255 254   5 254 253 255 255 255
 96 | 255 255 255 254 254   —   —   —
```

值的分布（tile 0–100）：`255` 38 個、`254` 19 個、`253` 9 個、`0–7` 共 35 個。

### 語意（依所在圖層而不同）

`222f:0e4a` 之後依 `0x52d4`（子地圖巢狀深度）分兩條：

```
深度 == 0（大地圖）:
    表[tile] == 0xff → 撞牆（播音效，移動結果碼 0xfffe）
    否則              → 可通行

深度 > 0（子地圖／城鎮內）:
    表[tile] == 0xff → 撞牆，但 tile 0x14 與 0x62 例外，可以走
    表[tile] != 0xff → 踏出了子地圖 → 深度 −1，退回上一層
```

**這就是 `docs/re/08` §6.3 列為未解的「退出（pop）路徑」。**

機制上很合理：城鎮／建築的子地圖疊在大地圖上，子地圖自己的圖塊都屬 `0xff` 類（牆），
其中 `0x14` 與 `0x62` 是可走的街道／地板 —— **兩者的表值確實都是 `0xff`**，
正是 `0xff` 類裡唯二被開特例的。一旦踏到不屬於子地圖圖塊集的一般地形，就自動退回大地圖。

> `0–7` 這 35 個小值與 `253`/`254` 的細部語意尚未逐一確認。
> 已知 `253` 在另一處被單獨比對（`222f:10d6`，回傳 `0x14`），
> 且第三處讀取點以 `≤ 200` 當分界（`222f:2a8e`），暗示「小值群」與「大值群」是兩類。
> **不擋移動實作** —— 通行與否只看是不是 `0xff`。

## 3. 事件類別 0 的消費者

### 舊斷言不成立

`docs/re/05` §4 寫「類別 0 在 `FUN_222f_0a90` 的閘門邏輯裡被排除，不觸發任何事件」，
並指出這與「多數房間都該顯示文字」矛盾，列為最大未解項。

**該文看的是閘門，不是消費者。** 真正讀事件文字的路徑不經過 `FUN_222f_0a90`。

### 真正的消費者：`FUN_25be_0263`

`FUN_25be_0e77`（讀 `DATA*.TXT`）全檔**只有一個呼叫端**，在 `FUN_25be_0263` 裡：

```c
if (*(int *)0x5c62 == 3 || *(int *)0x5c62 == 6) {
    ... 特殊處理（類別 3／6）
}
if (*(int *)0x5c62 != 5) {
    local_14 = 0;
    if ((*(int *)0x5c62 == 1) && (struct[+0xa5] != 0)) {
        struct(0x52f8)[2] = (類別 << 5) + 1;        // 改寫 EXITS 記錄的 type byte
        if (struct[+0xa5] != 3) { struct[+0xa5] = 0; return 2; }
        local_14 = 1;
    }
    return FUN_25be_0e77(param_1, local_14);         // ← 讀並顯示事件文字
}
// 類別 5 走另一條
```

**判定條件是「類別 != 5」，不是「類別 ∈ {1, 2}」。**
所以**類別 0 會正常顯示事件文字**，`EXITS.DAT` 裡那 94 筆類別 0 的記錄沒有任何異常。

`FUN_25be_0263` 的兩個呼叫端：

| 呼叫 | 位置 | 說明 |
|---|---|---|
| `FUN_25be_0263(0)` | `FUN_222f_0003` 的一個 switch case | 頂層指令分派器。**不重新呼叫 `FUN_222f_1321`**，直接消費已經設好的 `0x52f4` |
| `FUN_25be_0263(1)` | `FUN_222f_30dc` | 另一條路徑 |

這正是 `docs/re/05` §4 推測的 **(a) 假設**：
「`case 0xa` 那條**不經過閘門**的路徑直接讀 `0x52f4` 現值」。假設成立。

> 順帶更正 `docs/re/08` §5.4：該文把 `FUN_25be_0263` 標為「Look 陷阱搜查」。
> 從本文看到的內容，它是**依事件類別分派的事件處理器**，
> 讀 `DATA*.TXT` 顯示房間文字是它的主要工作之一。

### 一次性遭遇的消費

`1990:0ce2` 與 `1990:2191` 兩處（戰鬥結束後）：

```c
0x52f4 = 隊伍 X;  0x52f6 = 隊伍 Y;
FUN_222f_1321();                          // 重新查一次，取得記錄的遠指標 0x52f8
*(byte *)(0x52f8 + 2) = 0;                // ← 把該筆 EXITS 記錄的 type byte 清零
```

清零後該座標的類別變成 0 且不再被計入事件計數 —— **這就是「打完就不再重複觸發」的機制**。
