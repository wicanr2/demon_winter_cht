# 36 — 戰場的形狀：15×15，每格是世界 tile 的五分之一

`docs/re/35` §4 列了三條互相不相容的觀察，結論是「戰場邊界還沒解，別動 9×9 模型」。
這一篇解開了 —— 而且三條觀察全部各歸各位。

**戰場是 15×15，座標 (6,6)–(20,20)，中心 (13,13)。
地形是大地圖上隊伍周圍的 3×3 個 tile，每一個攤成 5×5。**

---

## 1. 開戰時建圖的四個步驟

```c
memset(地圖, 0, 0x1000);                    // 64×64 清 0
base = 地圖 + 0x145;                        // 0x145 = 5×64 + 5 → (5,5)
for (i = 0; i < 0x11; i++) {                // 17 格
    base[i]           = 3;                  // 上邊
    base[i*0x40]      = 3;                  // 左邊
    base[i*0x40+0x10] = 3;                  // 右邊
    base[i+0x400]     = 3;                  // 下邊
}
for (i = 0; i < 9; i++) {                   // 九個區塊
    tile = [0x5210 + i];
    for (row = 0; row < 5; row++)
        for (col = 4; col >= 0; col--)
            地圖[[0x0a0e + i*2] + row*0x40 + col] = tile;
}
```

**牆框是 17×17，畫在第 5 與第 21 列／欄**（`0x145` = (5,5)，`+0x10` = 右邊界
在 21，`+0x400` = 下邊界在 21）。框內就是 15×15 的可站範圍，
中心 `(5+21)/2 = 13` —— 佈陣把隊伍放在 (13,13) 的道理在這裡。

**九個區塊的起點來自 `ds:0x0a0e`**，實際值：

```
0186 018b 0190 02c6 02cb 02d0 0406 040b 0410
```

換算成 64 寬緩衝的座標：(6,6) (11,6) (16,6) (6,11) (11,11) (16,11)
(6,16) (11,16) (16,16) —— **3×3 個 5×5，一格不差**。

所以手冊那句「戰場是該區域的放大地圖」是字面意思：**真的放大五倍**，
不是取一小塊。你在大地圖上看到的那一格草地，打起來就是 5×5 格的草地。

---

## 2. 三條觀察各歸各位

`docs/re/35` §4 卡住的那三條，現在對得起來了：

| 觀察 | 真相 |
|---|---|
| 單位座標是 64 stride 緩衝的索引，中心 (13,13) | 對。緩衝 64×64，戰場只用左上角那塊 22×22 |
| 畫面是 9×9 視窗、跟著行動單位捲動 | 對，而且**必要** —— 戰場 15×15 比視窗大 |
| 另有一塊 9 stride 的緩衝（`[0x514e]`，`0x172f4` 依光照內縮填入）| **那不是戰場。** 它是另一個 9×9 的檢視，光照內縮也屬於那裡 |

第三條是本專案一直搞錯的地方：`internal/game/battleterrain.go` 原本照著
`0x172f4` 寫，把戰場當成「大地圖的 9×9 局部，外圈依光照變黑」。
真正的戰場建圖在別的地方，**整段沒有任何光照內縮**。

> **教訓**：`0x172f4` 確實在填一塊地形緩衝，也確實有光照內縮，
> 每一句都對 —— 錯的是「這塊緩衝就是戰場」這個沒有驗證的連接。
> 找到一段看起來對的程式碼之後，還要問「誰讀它」。這又是 `rulebook/62`。

## 3. 能不能站：只有一條判定

```c
// FUN_1990_07ed
目標X = ΔX表[面向] + 現在X;
目標Y = ΔY表[面向] + 現在Y;
if (地圖[目標Y*0x40 + 目標X] == *(char*)0x51d8) { 走過去 }
```

`[0x51d8]` 是**空地值**，開戰時從 `地圖[0x34d]`（= (13,13)，隊伍腳下）取樣。
一條判定同時擋掉「地形不對」與「有人站著」，因為擺好的單位會把圖塊蓋進地圖
（`docs/re/35` §3）。

**所以戰場的可走範圍，就是與隊伍腳下同一種地形的那一片。** 站在草地上開打，
草地那幾個 5×5 區塊是戰場，旁邊的森林區塊是牆。地形決定戰場的形狀，
不需要另一張可通行性表。

ΔX／ΔY 用的是 `0x15da`／`0x15d2` —— **與大地圖移動同一組表**（`docs/re/08`）。

## 4. 本專案的改動

座標**沿用原版的絕對值**：緩衝 22×22、牆框在 5 與 21、可站 6–20、中心 (13,13)。
之後任何反組譯發現都能直接對號入座，不必再換算。

| 檔案 | 改了什麼 |
|---|---|
| `internal/game/battlefield.go` | 常數改成 22×22 + 牆框 + 15×15 可站範圍；`CanStep` 加地形判定 |
| `internal/game/battleterrain.go` | 改成 3×3 世界 tile 各放大 5×5 + 牆框；新增 `Ground`／`Walkable`／`InArena` |
| `internal/game/battle.go` | `Battle.Terrain` |
| `internal/game/deploy.go` | 中心改用共用常數（原本自己定 (4,4)）|
| `cmd/demonwinter/battleui.go` | 9×9 攝影機（`battleCam`），對準行動單位、夾在牆框內 |
| `cmd/demonwinter/main.go` | 移除 `battleLight`（光照不屬於戰場，見 §2）|

### 踩到的兩個坑

**一、`0` 是合法的世界 tile。** 第一版拿「地形值 != 0」當「這一格有東西，畫它」，
結果地形 0 的區塊整片畫成黑的。改成看座標（`InArena`），世界地圖界外的區塊
也改填牆而不是留 0。

**二、視線遮蔽不能用在擺位上。** 中途一度拿遮蔽過的地形去判定落點，
看不見的格子一律變 0、對不上空地值，怪物一隻也放不下 —— 進戰鬥直接
「怪物全滅」。遮蔽只影響畫得出什麼。（後來連遮蔽本身也一起移出戰場了，
理由同 §2。）

### 實機驗收

`workplace/dump/persist/51-battle-15x15.png`（`-x 38 -y 22`）：
戰場鋪滿放大後的地形，五名隊員照陣型站在中央、四隻怪物散在 ±2，
攝影機對準行動中的 Stumpy。

另一個位置（`-x 9 -y 32`）打起來整片戰場是黑的。**那不是 bug** ——
查過了：`DEMON.SHP` 裡 tile **0、17、86、92 本來就是整格純黑**，
`Tile()` 回傳的是正常的 16×16、每個像素都不透明，只是顏色全黑。
隊伍站在這種地形上開打，整片戰場當然是黑的，原版也一樣。

一度把它寫成「取不到圖」的缺口，是看到黑畫面就先假設「圖沒載到」。
`internal/assets/gfx` 現在有 `BlackTiles` 常數與一條測試釘住這四個值，
免得日後有人去「修」解碼器。

## 5. 後續解開與仍未知的部分

- ~~tile 4 的 `ds:0x0a20`／`0x0a32` 分支~~：**已解並實作**（`docs/re/108`）。
  兩張表依同列相鄰值選橫／直窄道，中央五格寫 0，再把中心恢復為 4；
  兩方向逐格測試及 `MAP3 (17,46)` 實機戰鬥通過。敘事上的地形名稱仍未知，
  不影響幾何。
- `param_1 >= 0x80` 那條路徑走的是**預製戰場**：把 `[0x514e]` 直接複製到
  `地圖 + 0x186`（= (6,6)，可站範圍的左上角）。什麼場合會用還沒查。
- `[0x5210]` 那九個 tile 從哪裡取樣（一定是大地圖的 3×3，但取樣點的程式碼沒讀）。
- tile 0／17／86／92 為什麼是純黑（是「虛空」之類的地形，還是沒用到的索引）。
  可通行性表說它們**都不擋路**（tile 0 = `0x04`、17 = `0xfe`），所以不是「牆」。
