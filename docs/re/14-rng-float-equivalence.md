# RNG 浮點路徑 vs 整數實作 —— 等價性驗證

> 對應 `docs/spec/01-rng.md` §演算法 `Roll(n)` 段落標註的未驗證假設：
> 「遊戲中最大只到 `Roll(100)`，遠小於模數，兩者結果一致」。

## 1. 段 `310e` 軟體浮點函式庫解析

### 1.1 兩個平行的「暫存器」

這套函式庫不是單一堆疊,而是**兩個獨立的浮點值槽位**,指標分別存在：

- `[0x482e]`：暫存器 **A**(主運算元/累加器)
- `[0x4830]`：暫存器 **B**(次運算元)

多個函式共用同一段程式碼,靠呼叫端**進場前先把目標指標放進 DI**（或不放,用預設值 `[0x482e]`）來決定操作 A 還是 B。證據：

```asm
310e:01a5  PUSH DI
310e:01a6  MOV DI,word ptr [0x4830]      ; DI = 暫存器 B 的指標
310e:01aa  JMP 0x3000:1220               ; 跳進 013b 函式「中段」(偏移 +5)，跳過它自己的
                                          ; "MOV DI,[0x482e]" 開頭，直接複用同一段解包邏輯
```

`FUN_310e_0127` 呼叫同一段程式碼但**不**預先覆寫 DI，會落在 `013b` 的完整開頭
（`MOV DI,[0x482e]`），因此操作的是暫存器 A。這個「同一份程式碼、靠進場前置狀態
決定操作哪個暫存器」的手法在下面幾組函式對裡重複出現，是這套函式庫最主要的
程式碼重用手段，一旦看懂就能解釋大部分「為什麼呼叫序列裡有些函式沒有顯式參數」
的疑惑。

### 1.2 內部值格式

每個浮點值在暫存器裡的完整格式（透過 `FUN_310e_0732`、`FUN_310e_07a4`、
`FUN_310e_045e`、`FUN_310e_0588` 交叉核對）：

```
[ptr]     : 1 byte  符號位元 (0x00=正, 0x80=負)
[ptr-2]   : 1 word  偏移量指數 (bias = 0x3ff = 1023，與 IEEE 雙精度慣例相同)
[ptr-4..] : 4 words 尾數 (64 bit，MSB 在高位址、LSB 在低位址)
```

指數偏移 `0x3ff`（1023）已用兩處獨立證據交叉確認：
- `FUN_310e_07e2`（float→int）：`SUB AX,0x3ff` 把儲存的指數還原成真實二進位指數。
- `FUN_310e_0010`：`SUB AX,0x7f; ADD AX,0x3ff`，把 IEEE 單精度（bias=0x7f=127）的
  指數改成內部 bias（0x3ff），證實內部 bias 確實是 1023，不是原本猜測的 x87
  擴充精度 bias `0x3fff`（16383）——**這點與規格文件先前的敘述不同，已修正**。

尾數乘法核心（`FUN_310e_0588`）明確對 4 個 16-bit word（`[SI-0xa..SI-4]` ×
`[BX-0xa..BX-4]`）做長乘法，累加進 5-word（80-bit）暫存區 `[0x4856..0x485e]`；
除法核心（`FUN_310e_045e`）用 `DIV` 指令跑 4 輪迴圈（`MOV CX,0x4`）產生 4-word
商——兩處都指向**內部運算精度為 64-bit 尾數**。

### 1.3 記憶體常數是標準 IEEE 雙精度——關鍵的直接證據

反組譯 `FUN_30c2_0006`（LCG 狀態推進函式）結尾：

```asm
30c2:0052  MOV AX,[0x481c]        ; AX:DX = 剛完成模運算的新狀態(32-bit 整數)
30c2:0055  MOV DX,word ptr [0x481e]
30c2:0059  CALLF 0x3000:1884      ; = FUN_310e_07a4：把 AX:DX 當整數推入暫存器 A
30c2:005e  MOV BX,0x92            ; BX = 本函式(30c2)自己code段內偏移 0x92 的常數
30c2:0061  CALLF 0x3000:1276      ; = FUN_310e_0196：把 30c2:0092 的常數推入暫存器 B
30c2:0066  CALLF 0x3000:153e      ; = FUN_310e_045e：A ÷ B，結果留在暫存器 A
30c2:006b  RETF
```

直接讀 `30c2:0092` 的原始位元組（8 bytes）：

```
00 00 00 80 55 55 45 41
```

以小端序 IEEE-754 double 解讀 → **2796203.0**（跟 `docs/spec/01-rng.md` 的模數
逐位元吻合，用 Python `struct.unpack('<d', ...)` 直接驗證過）。

**這是本次任務最關鍵的一筆證據**：它直接證明 `FUN_30c2_0006`——也就是「LCG 狀態
推進」這個函式本身——在完成 `(state × 125) mod 2796203` 的整數運算之後，
**緊接著就在同一個函式裡把新狀態除以 2796203.0，把商（一個 `[0,1)` 之間的浮點小數）
留在暫存器 A**。這代表「除以模數」這一步發生在狀態推進的當下，**不是** `Roll(n)`
呼叫時才做——`Roll(n)` 拿到的已經是除好的小數，只需要乘上 `n`。

同樣手法也出現在 `1d9f:2cb2`（`FUN_1d9f_0dda` 用到的常數，見 §3.1）：位元組
`00 00 00 00 00 00 70 40` 解讀為 IEEE double **256.0**，佐證「呼叫端把編譯期
浮點字面值直接以標準 8-byte IEEE double 格式塞進自己的 code segment，靠
`FUN_310e_0196` 這類函式讀取」是這個編譯器的通用手法，不是只有模數常數這一處。

### 1.4 `Roll(n)` 的完整呼叫序列（逐指令核對）

`FUN_1d9f_0e0b`（`n<0` 取絕對值、`n∈{0,1}` 提早回傳之後）：

```
FUN_1d9f_0dd4 → FUN_30c2_0006   ; 整數 LCG 推進 + 立刻除以 2796203.0，留在暫存器 A
FUN_310e_021e                    ; 把暫存器 A(= state/Modulus)「打包」成 8-byte 緊湊格式，
                                  ; 存進呼叫端(FUN_1d9f_0e0b)自己堆疊上暫時借用的 8 bytes
                                  ; scratch buffer；打包過程含捨入(見 §1.6)
MOV AX,[BP+6]                    ; AX = n
FUN_310e_0732(AX)                ; 把 n 轉成浮點，推入暫存器 A(覆蓋掉剛才的 state/Modulus，
                                  ; 但已經先備份進 scratch buffer 了)
FUN_310e_0242                    ; 把 scratch buffer(state/Modulus)解包回暫存器 B
FUN_310e_0588                    ; 暫存器 A(=n) × 暫存器 B(=state/Modulus) → 暫存器 A
FUN_310e_07e2                    ; 暫存器 A 轉整數(截斷)，回傳於 AX
+1                               ; Roll(n) 最終回傳值
```

換句話說，原版實際執行的是：

```
result = truncate( n × (state / 2796203.0) ) + 1
```

在有理數層面與現行 Go 實作 `floor(state*n / Modulus) + 1` 完全等價
（`a/b×c = a×c/b`），差別只在於原版是「先做一次浮點除法、再做一次浮點乘法」
（兩次捨入機會），Go 是「一次整數乘法、一次整數除法」（零捨入誤差，因為
`uint64` 完全裝得下 `state×n`，見 §2）。

### 1.5 截斷語意（`FUN_310e_07e2`）

```asm
310e:07e2  MOV SI,[0x482e]         ; SI = 暫存器 A
310e:07f6  MOV AX,word ptr [SI-2]  ; AX = 指數
310e:07f9  SUB AX,0x3ff            ; 還原成真實二進位指數
310e:07fc  JS  ...                 ; 指數<0(值<1) → 直接回傳 0，不進位、不四捨五入
310e:0803..: 依指數決定要複製幾個完整 byte、剩下幾個 bit 用移位湊出來
             全部是「把尾數位元搬到整數對應的位元位置」，沒有出現任何
             「看下一位是否 ≥0.5 就加 1」的捨入邏輯
310e:083b  TEST byte ptr [SI],0x80 ; 檢查符號
310e:0840  NEG DX; NEG AX; SBB DX,0x0   ; 負數轉兩補數(往 0 方向截斷，不是四捨五入)
```

**已驗證：截斷（truncate toward zero），不是四捨五入。** 這與現行 Go 實作用整數
除法（`uint64(...) / uint64(Modulus)`，本質上就是截斷）完全一致，不需要修改。

### 1.6 打包/解包中途的精度：實測是 IEEE 雙精度（53-bit 有效位元）

`FUN_310e_021e`/`FUN_310e_0242` 這對「打包進 8-byte scratch buffer 再解包」的
操作，字面上看起來只是搬運，但打包時會先呼叫 `FUN_310e_075d` 做**捨入**
（檢查超出範圍的低位元，決定要不要進位到保留的位元寬度），這代表 `state/Modulus`
在進入最後乘法之前，精度被縮到這個 8-byte 格式的寬度，不是全程都用內部
64-bit 尾數。逐位元核對這個 8-byte 格式的位元配置（`FUN_310e_01b8` 打包 /
`FUN_310e_013b` 解包，兩者互為反操作）：

```
第 1 個 word：符號(1 bit) + 指數(11 bit，與內部格式相同) + 尾數最高 4 bit
接下來 6 bytes：尾數其餘 48 bit(直接位元組搬移)
```

`1(符號) + 11(指數) + 4 + 48(尾數) = 64 bit`，尾數部分 `4+48=52` bit
外加解包時用 `AND DH,0xf; OR DH,0x10` 明確補回的隱含前導 1 bit——
**這正是標準 IEEE-754 雙精度（binary64）的位元配置**（1+11+52，隱含前導位元）。
換句話說，這個「緊湊格式」不是隨便湊的，就是把內部 64-bit 尾數的擴充精度
四捨五入回標準 double，用來在暫存器之間搬運——與 §1.3 觀察到「編譯期常數用
標準 IEEE double 字面值嵌在 code segment 裡」的手法完全吻合，指向這整套
軟體浮點庫的存放格式就是相容 IEEE double，只有運算過程中的中介暫存器
（乘法/除法核心的工作緩衝區）額外多留了一點內部精度。

**這對本檔 §2 的數論論證是保守方向的修正**：精度上限不是內部核心的
64-bit，而是 53-bit 有效位元（IEEE double 的 1+52）。下面 §2 的論證直接用
這個較保守的數字。

## 2. 等價性驗證：數論證明 + 窮舉複查（不是抽樣）

### 2.1 為什麼不需要完整位元級模擬就能窮舉證明

完整重建這套軟體浮點庫的每一個 bit-exact 行為（捨入模式、每個中介步驟的精度）
工作量很大，且每多一個假設就多一個可能出錯的地方。但驗證「兩條路徑的
`floor()` 結果是否相同」不需要走到這一步——只需要知道**精度的下界**，
就能用數論直接證明捨入誤差不可能大到讓 `floor()` 跨過整數邊界。

**論證**：

1. `Modulus = 2796203` 是質數（已知事實，Wagstaff 質數 `(2²³+1)/3`；本次任務
   用試除法在程式裡重新驗證一次，見 `tools/rng_float_equiv_check.go`）。
2. 遊戲會用到的 `n`（`1..12`、`100`，含武器骰表 `3,4,6,7,8,10,12`）全部滿足
   `1 < n < Modulus`。因為 `Modulus` 是質數，`gcd(n, Modulus) = 1` 對所有這些
   `n` 成立——`n` 不可能是 `Modulus` 的倍數。
3. `state` 恆在 `[1, Modulus-1]`（規格保證，狀態不會是 0，見
   `docs/spec/01-rng.md` §邊界條件），所以 `state` 也不是 `Modulus` 的倍數。
4. 因此 `state × n mod Modulus` **恆不為 0**——`state×n` 這個整數絕不會恰好落在
   `Modulus` 的整數倍上。
5. 這代表精確有理數 `state×n / Modulus` 的小數部分，離最近的整數邊界（0 或 1）
   **至少差 `1/Modulus ≈ 3.578×10⁻⁷`**（約 21.4 bit 的安全邊界）。
6. 原版的浮點路徑精度下界（見 §1.6）是 IEEE double 的 53-bit 有效位元，
   相對誤差 `≈ 2⁻⁵³`，比上面的安全邊界小了超過 **31 個 bit**。
7. 因此無論原版浮點路徑的捨入細節究竟怎麼實作（只要精度不低於 53-bit，
   而它明顯遠高於此），`floor()` 的結果**在數學上保證**與精確有理數運算
   （也就是 Go 現行整數實作）逐一相同。

這個論證涵蓋 `state` 的**全部** `2,796,202` 個合法值與所有測試的 `n`，
是完備的窮舉證明，不是抽樣外推。

### 2.2 實際跑出來的數字

`tools/rng_float_equiv_check.go`（`docker run ... go run ./tools/rng_float_equiv_check.go`）：

```
Modulus = 2796203
Modulus is prime: true

n=  2: 窮舉 2796202 個 state，最小 margin=1（≈3.576e-07，~21.4 bit）
n=  3..12, 100：同上，每個 n 的最小 margin 都是 1（~21.4 bit）

總計窮舉組合數：33,554,424（13 種 n × 2,796,202 個 state，扣掉 n=1 不走浮點路徑）
state*n ≡ 0 (mod Modulus) 出現次數：0
全域最小 margin：1（發生於 n=2, state=1398101），相對誤差邊界 ≈ 3.576e-07，約 21.4 bit
```

**結論**：33,554,424 組 `(state, n)` 全數檢查，`state×n` 從未恰好是 `Modulus`
的倍數，最緊的安全邊界都還有約 21.4 bit，而原版浮點精度下界是 53 bit——
兩條路徑的 `floor()` 結果**保證逐一相同，等價性已驗證，不是假設**。

`docs/spec/01-rng.md` 目前把這句話標成推論（「遠小於模數，兩者結果一致」），
可以升級為已驗證陳述；但依任務邊界規則，`docs/spec/` 由協調者更新，本檔
只負責把證據準備好。

### 2.3 `internal/rng/rng.go` 需要修改嗎

**不需要**。現行 `Roll()` 用 `uint64` 做 `state*n/Modulus`：`state < 2²²`、
`n ≤ 100 < 2⁷`，乘積 `< 2²⁹`，`uint64` 完全裝得下，整數除法本身就是精確的
`floor()`，沒有額外捨入誤差——它本來就精確等於 `floor(state×n/Modulus)`，
而 §2.1 證明了這就是原版浮點路徑的結果。已在 `internal/rng/rng_test.go`
加上 `TestRollFloatEquivalence` 做**回歸測試**（用同一個數論不等式抽樣複查，
註解裡引用本檔與 `tools/rng_float_equiv_check.go` 的完整窮舉，測試本身不用
每次都跑 279 萬次）。

## 3. 播種機制

### 3.1 `FUN_1d9f_0dda`：觸發條件與作用

**觸發條件（已驗證）**：`FUN_1d9f_0e0b`（`Roll(n)`）裡：

```asm
1d9f:0e38  CALLF 0x2000:f46a     ; FUN_2f46_000a：更新系統時鐘累加器(百分之一秒單位)，
                                  ; 回傳目前累加值
1d9f:0e3d  TEST DX,0x0
1d9f:0e41  JNZ ...
1d9f:0e43  TEST AX,0x1           ; 累加值最低位元
1d9f:0e46  JZ  ...               ; 偶數 → 跳過
1d9f:0e48  CALLF 0x1000:e7ca     ; 奇數 → 呼叫 FUN_1d9f_0dda
```

即：**每次擲骰時，若系統時鐘累加器（`FUN_2f46_000a` 維護，單位是百分之一秒、
跨日會加上 `0x83D600` 進位，見 `docs/re/06-combat-system.md` §4.2）目前是奇數，
就多做一件事**。

**`FUN_1d9f_0dda` 本體（逐指令核對）**：

```
CALLF FUN_30c2_0006              ; 【有持久效果】多推進一次 LCG 狀態
                                   ; (FUN_30c2_0006 順便把新狀態除以模數留在暫存器 A)
MOV BX,0x2cb2                     ; 常數位址：呼叫端(FUN_1d9f_0dda 自己)code段內偏移
CALLF FUN_310e_0196               ; 把 1d9f:2cb2 這個常數(= 256.0，見 §1.3)推入暫存器 B
CALLF FUN_310e_0588               ; 暫存器 A(state/Modulus) × 暫存器 B(256.0) → A
CALLF FUN_310e_01b2 (打包到局部緩衝區)
CALLF FUN_310e_0127 (從局部緩衝區解包回暫存器 A)  ; 精度來回一趟，效果等同於
                                                     ; 把中間值捨入到 double 精度
CALLF FUN_310e_07e2               ; 暫存器 A 轉整數，結果在 DX:AX
MOV SP,BP; POP BP; RETF           ; 【沒有任何指令把 DX:AX 存到別的地方】
```

**已驗證的結論**：這段計算出 `int((state/Modulus) × 256)`，但**這個結果從未被
使用**——函式直接返回，呼叫端（`FUN_1d9f_0e0b`）也沒有讀取任何回傳值
（下一行就是無條件呼叫 `FUN_1d9f_0dd4` 繼續正常的 `Roll()` 流程）。搜尋全域
沒有找到任何寫回 `0x481c`/`0x481e` 以外位址、且看起來像「種子」的動作。

**這不是傳統意義的「重新播種」**（沒有重新讀系統時鐘、沒有把新值寫進一個獨立的
種子變數）。它的**唯一持久效果**是：當 tick 為奇數時，這次 `Roll(n)` 呼叫會讓
LCG 狀態多推進一步（`FUN_30c2_0006` 被呼叫兩次而不是一次），其餘是算完即丟的
死值。**淨效果**：`Roll(n)` 消耗的 LCG 步數本身是不確定的（1 步或 2 步，取決於
呼叫當下的系統時鐘奇偶），這是原版序列裡真正不可預測、不可靜態重現的部分。

**旁證**：`FUN_1d9f_0dda` 不是 RNG 專用函式——它同時被 `FUN_1d9f_0008`（見下）
在一個與 RNG 語意無關的「依時鐘決定跑幾次迴圈」情境下呼叫，說明它本質上是
一個**共用的「消耗 N 步 LCG」的計時輔助函式**，被 `Roll()` 借用來當作額外的
不可預測性來源，不是特別為「reseed」設計的獨立機制。

### 3.2 初始種子：新發現——編譯期常數 + 系統時鐘驅動的暖機迴圈

`0x481c`/`0x481e`（LCG 狀態）在全部 353 個已分析函式裡，**只有 `FUN_30c2_0006`
會寫入**（用 `SUB`/`SBB` 做模運算更新）——沒有任何函式用 `MOV` 對這兩個位址做
「設定初始種子」這種一次性寫入。

直接讀取 `DEMON.INT` 檔案裡這兩個位址對應的**靜態初始值**（未執行任何程式碼時
的資料段內容）：

```
0x481c: a1 86  → 0x86a1
0x481e: 01 00  → 0x0001
組合(高:低) = 0x0001_86A1 = 100001（十進位）
```

**已驗證**：程式的 LCG 狀態變數在編譯期就被初始化成固定常數 **100001**。

那麼「隨機」從哪來？追 `FUN_2f46_000a`（系統時鐘累加器）的呼叫點，全域只有
兩處：`FUN_1d9f_0e0b`（`Roll()` 內，見 §3.1）與 `FUN_1d9f_0008`。後者反組譯：

```asm
1d9f:0008  PUSH BP; MOV BP,SP; ADD SP,-0x2
1d9f:000e  MOV AH,0xf; INT 0x10        ; BIOS 查目前顯示模式
1d9f:0012  CMP AL,0x10; JNZ ...        ; 0x10 = EGA 640x350 16色
1d9f:0016  MOV word ptr [0x19fb],0x1   ; 設 EGA 旗標
...
1d9f:0034  CALLF FUN_2f46_000a          ; 更新並取得系統時鐘累加值
1d9f:0039  AND AX,0x8ff                 ; 遮罩成 [0, 0x8ff] = [0, 2303]
1d9f:0040  MOV [0x5396],AX              ; 迴圈次數 = tick & 0x8ff
1d9f:0043  MOV word ptr [BP + -0x2],0x0 ; i = 0
1d9f:004a  CALLF FUN_1d9f_0dda          ; 迴圈本體：呼叫 §3.1 的函式
1d9f:004f  INC word ptr [BP + -0x2]     ; i++
1d9f:0052  ...; JL   ...                ; while (i < 迴圈次數)
```

`FUN_1d9f_0008` 只有一個呼叫端（`decompiled_all.c` 裡的 `FUN_304b_000a`，
一個典型的 C runtime 命令列參數解析函式，呼叫慣例是 `main(argc, argv)`），
換句話說 **`FUN_1d9f_0008` 就是這個程式的 `main()`（或緊接在 runtime 啟動碼
之後、`main()` 呼叫的第一個函式）**，只在程式啟動時執行一次。

**已驗證的完整播種鏈**：

```
程式啟動
  → main()(FUN_1d9f_0008) 一開始先用 BIOS 偵測顯示卡
  → 讀系統時鐘累加器，取低 11 bit（0~2303）當「暖機次數」
  → 迴圈呼叫 FUN_1d9f_0dda 這麼多次，每次都會讓 LCG 狀態多推進一步
  → LCG 狀態從編譯期常數 100001 開始，被系統時鐘決定的次數(0~2303)推進
```

這解釋了任務指示裡「已確認的事實：種子來自 DOS 系統時鐘」為什麼成立，但精確
機制不是「把時鐘值直接寫進狀態變數」，而是**「用時鐘值決定要把固定起始狀態
往前推進幾步」**——效果上一樣是「每次開機序列不同、只跟系統時鐘有關」，
但實作方式是間接的迭代推進，不是直接賦值。這點原本的規格文件與任務描述都
沒有這麼精確，屬於本次任務的新發現。

**對重現的意義**：與規格文件既有結論一致——這整條播種鏈依賴真實系統時鐘，
本質上不可靜態重現。重現時用**固定種子**（直接呼叫 `NewWithSeed(固定值)`，
跳過整條暖機鏈）是正確作法，不影響 §2 已證實的演算法等價性。

## 5. 未解 / 未逐一確認的部分（誠實記錄）

1. **`FUN_310e_01b8`/`013b` 的 8-byte 緊湊格式位元配置**是透過交叉比對兩個
   方向（打包/解包）的位元操作推出來的，**沒有**做位元組級的窮舉模擬驗證
   （例如：拿已知的 `state` 值手動排出完整位元組序列、跟原始檔案位元組
   逐一核對）。信心等級高（結構上跟 IEEE double 完全吻合），但嚴格說仍是
   「結構推論」而非「窮舉核對」。
2. **`FUN_310e_0010`/`007a`/`0092`** 這組讀寫 IEEE 單精度的函式群，用途沒有
   追到呼叫端——可能是浮點數存檔格式或跨模組資料交換用，與 RNG 無關，
   本次任務範圍內沒有深入。
3. **沒有做動態 DOSBox 對拍**：本檔的等價性證明是「數論證明 + 靜態反組譯
   證據」的組合，沒有另外跑 DOSBox debugger 對特定 `(state, n)` 組合單步
   驗證浮點路徑的實際輸出。之所以選擇這條路而非動態驗證，是因為：
   (a) §2 的數論論證本身已經是完備、窮舉、且不依賴任何精度細節猜測的證明
   （只需要精度下界，不需要精確重建捨入行為）；(b) 完整重建這套自製 80-bit
   軟體浮點庫的每一個 bit-exact 行為工作量遠超過本任務範圍，且每個重建細節
   都是潛在的錯誤來源；(c) 現有的 DOSBox 環境（`docs/re/01`、`docs/re/11`）
   是互動式鍵盤自動化，沒有「呼叫任意函式、灌入任意暫存器狀態、窮舉跑
   279 萬次」的批次腳本能力，要另外建置這種能力的成本明顯高於數論證明的
   路徑。如果後續有人需要更強的驗證（例如懷疑本檔的精度分析有誤），
   建議的下一步是用 DOSBox debugger 對少數幾個 `(state, n)` 組合做單步
   交叉核對，而不是重跑整個窮舉。
4. **`FUN_1d9f_0008` 是不是真的等同 `main()`**：只確認了它是
   `FUN_304b_000a`(命令列參數解析)之後被呼叫的唯一函式，呼叫慣例（傳入
   `argc`/`argv`）與典型 C runtime 的 `main()` 呼叫慣例吻合，但沒有反查
   C runtime 啟動碼本身逐行確認這條呼叫鏈的每一步。信心等級高，但標記
   為推論而非鐵證。
5. **`FUN_310e_0242`/`0dda` 呼叫點的 `RETF 0x8` 堆疊平衡**：本檔的解讀是
   「呼叫端(`FUN_1d9f_0e0b`/`FUN_1d9f_0dda`)刻意用 `FUN_310e_021e`/`01b2`
   多分配 8 bytes 局部空間、讓後續的 `0242`/`0127` 讀取並用 `RETF 0x8` 回收」
   ——這個「跨函式共享未宣告堆疊空間」的模式沒有在其他函式對裡找到第三個
   案例佐證，只有這一組。結構上自洽（呼叫前後堆疊平衡、參數位址對得上），
   但屬於「單一案例的結構推論」而非「多案例交叉驗證」。

## 6. 給後續 agent 的建議

- `docs/spec/01-rng.md` §演算法 `Roll(n)` 的「原版此處走自製軟體浮點函式庫……
  兩者結果一致」這段可以從推論升級成已驗證陳述，引用本檔 §2；§未解可以把
  「播種時機」那條的信心等級提升（觸發條件與函式本體已驗證），但保留
  「初始種子的暖機迴圈是新發現、只有靜態證據、沒有動態交叉核對」這個註記。
- 若之後要精確重現原版某一局（對拍 DOSBox 錄影），§3.2 的暖機迴圈（初始狀態
  100001 + 系統時鐘低 11 bit 決定的推進次數）是必要的一塊拼圖，目前
  `internal/rng` 只支援直接指定固定種子（跳過暖機鏈），這是刻意的設計取捨
  （見 spec 的既有結論），不是遺漏。
