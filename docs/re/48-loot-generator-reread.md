# 48 — 掉寶生成器重讀：一個 `+1` 讓五處判讀集體偏一格

`docs/re/47` §1 留了一個坑：材質類別（`+0x0f`）的規則沒讀，
所以掉寶生成器一直沒填它，估價的第一個乘數永遠是 0。

去補那一段的時候發現，`1990:11b9` 的前三行就把整篇 `docs/re/30` 掀了：

```
e6ad  al = [bp-0x4]          ; 道具型別
e6b0  les bx,[bp+0x8]
e6b3  es:[bx] = al           ; 寫進槽 +0x00
e6b6  inc word [bp-0x4]      ; ← 這一行
```

**型別寫進槽之後，區域變數被 +1 了。** 從這裡開始，函式裡每一次
「型別 == 幾」的比較用的都是 `型別 + 1`。`docs/re/30` 把那些常數
（8、15、25、26）直接當成 0-based 的型別讀，五處全部偏一格。

---

## 1. 材質類別（原本要查的東西）

```
if 型別+1 ∈ {9, 10, 15, 20, 25, 26} → 類別 1
else
    n = rnd(等級 + 10)
    n < 9 → 1、n < 13 → 2、n < 15 → 3、n < 17 → 4、其餘 → n − 12
```

那六個型別（0-based 是 **布甲、皮甲、藥瓶、寶石、藥膏、藥瓶**）永遠是類別 1。
看名稱表就知道為什麼 —— `ds:0x1852` 那張遠指標表存的是名稱前綴：

| 類別 | 前綴 | 倍率 |
|---|---|---|
| 1 | （空白）| 1 |
| 2 | Well made | 2 |
| 3 | Silver | 5 |
| 4 | Jade | 20 |
| 5 | Crystal | 35 |
| 6 | Gold | 50 |
| 7 | Platinum | 60 |
| 8 | Jewel encrusted | 75 |

布與皮鍍不了銀，藥水藥膏是液體，寶石本身就是那個材質。
**名稱表與倍率表是同一個索引的兩張平行表** —— `docs/re/30` 說 `+0x0f` 是
「名稱類別」、`docs/re/44` 說是「材質倍率」，兩邊講的是同一件事，
只是各自看到了一個讀取端。

> 找到名稱表的方法是最笨也最快的：`ds:0x1852` 的九個遠指標一路解到底，
> 讀出來的字串自己會招供。段值 `0x21f0` 補上 +0x1000 之後
> （`docs/re/32` §1 那條）算出來剛好等於 DS 基底，一次就對上。

**這條公式在等級 10 以上會越界。** n 最大 `等級 + 10`，類別最大 `等級 − 2`；
超過 8 就讀到倍率表後面那張遠指標表的 bytes（`d0 18 f0 21…` → 208、24、240…），
價格會暴衝。原版沒有防呆，本專案鉗在 8：照抄表外的垃圾值不叫忠實，
那是把記憶體布局的巧合當成遊戲規則。

---

## 2. 偏一格的五處

`+1` 之後的比較，換算回 0-based：

| 位置 | 原本寫的 | 實際是 | 差別 |
|---|---|---|---|
| 附魔減半 `1990:1cbd` | 型別 > 8 | 型別 ≥ 8 | **布甲原本沒被減半** |
| 附魔範圍 `1990:126e` | （沒實作）| 型別 ≤ 12 | 王冠以上**根本沒有附魔** |
| 充能固定 200 `1990:14ba` | 戒指與火把 | **兩種藥瓶** | 東西完全換人 |
| 效果硬寫 39 `1990:1433` | 型別 25／26 | 藥膏與第二種藥瓶 | 同上 |
| 詛咒範圍 `1990:124a` | （沒實作）| 型別 ≤ 12 | 只有武器護甲會被詛咒 |

「王冠以上沒有附魔」在畫面上一眼就看得到：修之前的商隊貨單列著
「寶石 +4」「魔杖」，修之後 `+N` 只出現在武器與護甲上。

### 這個 `+1` 不是猜的

`1990:1315` 讀道具資料時寫的是 `es:[bx + si − 0xa]`，`si = 14 × (型別+1)`——
兩個一減正好是 `14 × 型別 + 4`，落在記錄裡的第 5 個 byte。
**如果那時候是 0-based，偏移會是 `14 × 型別 − 10`，型別 0 就指到上一筆記錄外面去。**
編譯器補的那個 `−0xa` 就是 `+1` 的收據。

## 3. 型別重擲是價格**上限**，不是下限

`docs/re/30` §2.0 把 `1990:1136` 那道門檻讀成「最低價格」，方向反了。

```
T = 2.6^等級 + 25 × 等級        ; 2.6 是 CS:0x40e0 的 IEEE double
if T < 底價 → 重擲型別
```

`2.6` 這個常數是這一輪才解開的：呼叫鏈是
`210e:012d`（載入常數）→ `021e`（把 A 寄放到堆疊）→ `1990:0a83`，
而 `1990:0a83` 是一個**整數次方**（acc = 1.0，跑 n 次 `acc × 底`）。
指數就是等級。

解開之後方向不必再讀組合語言就能定：**`ITEMS.DAT` 最貴的是寶石 500，
而 `2.6^8 ≈ 2088`。** 當下限的話 8 級以上一件都選不出來，
那個迴圈會轉不完 —— 只有當上限講得通。

| 等級 | 上限 | 掉得出什麼 |
|---|---|---|
| 1 | 27 | 匕首、小斧、布甲、皮甲那些 |
| 4 | 145 | 加上雙手劍、鎖子甲、護身符 |
| 6 | 458 | 除了寶石以外都行 |
| 7 | 977 | 全部解鎖 |

所以正確的說法是**低等怪掉不出貴東西**，不是「高等怪不會掉匕首」。

## 4. 附魔與效果的範圍

```
型別+1 > 13 → 完全跳過附魔那一段
型別+1 > 8  → 附魔減半，(n+1)/2
```

三段式：**武器拿全額附魔、護甲減半、飾品以上沒有附魔**。
原版起始存檔那 11 件平凡武具看不出這條，因為它們的附魔都是 0。

第一道門檻（`rnd(100) > 2×等級 + 6`）沒過的話**整支函式就結束了** ——
不只沒有效果，連後面兩組特效、兩組附帶法術都不會長。那才是真正的平凡貨。

## 5. 詛咒：掉落與商隊是兩條完全不同的路

```
模式 0（戰鬥掉落）：rnd(10) == 10 且 型別+1 < 14 → 區域變數「詛咒」= 1
模式 1（商隊）    ：rnd(100) < 呼叫端給的機率     → 全域 ds:0x4e2e = 1
```

**兩條路的後果完全不一樣。**

| | 模式 0 的詛咒 | 模式 1 的旗標 |
|---|---|---|
| 附魔取負 | ✔ | ✘ |
| 擋掉效果 | ✔ | ✘ |
| 特效值取負 | ✔ | ✘ |
| 寫驅邪成功率 | ✔ | ✘ |
| 其他作用 | — | **跳過第一道效果門檻** |

模式 1 那個旗標在生成器裡**只做一件事**：讓這件貨免掉
`rnd(100) > 2×等級 + 6` 那一關。方向是好的不是壞的。

商隊在呼叫前後各碰一次 `ds:0x4e2e`（`1d69d` 寫 0、`1d6b8` 讀回來存進
自己的陣列），所以它是一個 in/out 參數，逐件記著。
**商隊後續拿那個陣列做什麼還沒讀** —— 本專案存在 `MerchantWare.Guaranteed`，
先保存不使用。

於是 `docs/re/32` 的「商隊的貨可能被詛咒（附魔為負、沒有效果）」是錯的：
商隊那條路**一件詛咒品都生不出來**。把 `rnd(120) − 80` 命名成「詛咒機率」
是從「掉寶生成器會生詛咒品」推過去的，中間少了一步驗證。

## 6. 兩組特效與兩組附帶法術（全新）

門檻過了之後還有兩段，`docs/re/30` 整段沒讀。

### 6.1 特效對 `+0x09`–`+0x0c`（武器與護甲）

兩輪，各自擲一次通過機率（`rnd(100) − 1 <= 等級 + 8` 與 `+ 5`）：

- 不是詛咒品而且擲中四成 → 條件碼 `rnd(8) − 1`（0–7）、值寫死 12
- 其餘 → 條件碼 `rnd(5) + 16`（17–21）、值是一個隨等級爬升的級數

級數怎麼爬：`k = 1`，只要 `rnd(15) − 1 < 等級 − k` 就再加一級。
詛咒品取負，存進去的是 `k + 10`。

**2026-07-29 更正：17–21 全都有作用，不是只有 21。** `sub_11CBF`
證明 17／18／19／20 分別是 MaxSP／速度／力量／技巧，21 才是戰鬥碼另讀的
武器特效（`docs/re/109`）。21 對護甲禁止，所以護甲拿不到的是**武器傷害特效**；
17–20 正是護甲仍能持有的常駐屬性效果。舊結論只追到戰鬥消費端，漏了換裝常式。

估價第四項那個 `n = 槽[+0x0a] − 10` 加上取絕對值（`docs/re/46` §3）
到這裡才對得起來：`n` 就是這個級數 `k`，負號來自詛咒。

### 6.2 附帶法術 `+0x01`–`+0x04`（只有武器）

```
強度 = rnd(22 × 等級 / 10) + 4
法術 = rnd(43) − 1，重擲到「最低法力 <= 強度」且法術表 +4 欄不為 0 為止
      （詛咒品而且強度 > 14 時硬寫成 26）
+4 欄 == 2 → 索引再點上最高位元 0x80
```

兩輪的門檻不一樣：第一輪 `<= 等級 + 3`，第二輪 `<= 等級` ——
第二個法術明顯難得多。

**估價的已鑑定加價 `(槽[+0x02] + 槽[+0x04]) × 270` 就是這兩個強度相加**
（`docs/re/44` §3）。那兩個「兩份原版存檔裡都是 0、看不出語意」的 byte
到這裡有了名字：起始裝備是平凡武具，本來就不該有附帶法術。

## 7. 驅邪成功率 `+0x0d`

只有模式 0 的詛咒品才寫，而且要**真的變壞了**才寫：
兩組法術強度、效果強度、兩組特效值全是 0 而且附魔沒有變負，就跳過。

```
成功率 = 51 − rnd(5 × 等級)
```

11 級以上減得出負數，原版用 `mov al` 存進一個 byte —— 繞回 247 附近，
**反而變成一驅就掉**。本專案照著取低位元組，理由與充能種類 3 同一條：
不取的話記憶體是負數、存檔讀回來是大正數，同一件道具在存檔前後行為會不一樣。

## 9. 這一輪的教訓

**「這個常數對應哪個東西」比「這個常數是幾」難得多。**
`cmp [bp-0x4], 0x19` 這一行本身沒有任何歧義，錯的是它比的那個變數
在三行之前被 `inc` 過。讀組合語言時盯著指令看，很容易把
「變數現在是什麼」這件事丟在腦後。

防呆的辦法不是更小心，是**找一個對不上就會爆的旁證**：
這裡是 `es:[bx + si − 0xa]` 那個負偏移。它只在 1-based 的前提下成立，
一次就把整段的基準釘死。`docs/re/46` §2 的「除數 0 剛好被守衛擋住」
是同一類東西。

`docs/re/30` 的結論不是全錯，是**每一條都對，只是各差一格** ——
這種錯最難靠「重看一遍」抓到，因為每一步看起來都合理。
會抓到它，是因為 `docs/re/47` 把價格接上去之後，
「寶石 +4」這種東西出現在畫面上了。
