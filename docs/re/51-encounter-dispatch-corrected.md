# 51 — 那道 1/64 不是隨機戰鬥，是商隊

`docs/re/50` §1.1 把事件動作分派表挖出來之後，`case 0x17` 是商隊。
但 `docs/re/04` §2.2 早就寫過：

> 則回傳特殊碼 `0x17`（23）。這條路徑**沒有經過 `EXITS.DAT` 或 `DATA*.TXT` 事件表**，
> 是純粹的「地城裡每次行動都有 1/64 機率隨機遭遇」機制

同一個碼，兩個結論。這一篇把它裁決掉 —— 順便發現**本專案照著錯的那個實作了**。

---

## 1. 完整的呼叫鏈

```
外層主迴圈（222f:0000 一帶）
  結果 = FUN_222f_0b0e()                       ; 0x16204
  隊伍[+0xa1] = ds:0x50f0 ; 隊伍[+0xa2] = ds:0x50ee   ; 把座標寫回
  switch (結果 − 6) → 21 個事件動作             ; 0x1647d

FUN_222f_0b0e（移動／指令迴圈）
  結果 = FUN_222f_0763()                       ; 0x16a37
  if 結果 != 0 → 原封不動 retf                  ; 0x16a3f–0x16a49

FUN_222f_0763（時間推進）
  if 隊伍[+0xa3] >= 9 且 ds:0x52d4 == 0:        ; 0x166fc
      if (rnd_raw() & 0x3f) == 0x34:            ; 1/64，0x1670b
          回傳 0x17                             ; 0x16718
```

三段接起來：**1/64 擲中 → 回傳碼 `0x17` → `case 0x17` → 商隊**。
中間沒有任何一步會把它轉成別的東西（`0b0e` 是 `if != 0 → retf`，
連碰都沒碰）。

`docs/re/04` 當時卡在「接續的分派邏輯落在 `FUN_222f_0b0e` 內被
decompiler 弄壞的那段 switch 裡」—— **分派根本不在 `0b0e` 裡面，
在它的呼叫端**。往函式裡面找當然找不到。

---

## 2. 順帶訂正兩處

**「地城裡」講反了。** 閘門是 `隊伍[+0xa3] >= 9`（`cmp 9 / jb 跳過`），
而子地圖編號 10 以上才是戶外（`internal/assets/scenario/save.go`）。
所以這一擲是**戶外**才有，地城反而沒有。

**是 `>= 9` 不是 `> 9`。** 邊界上那一張圖（編號 9）也會擲。

這兩點合起來剛好回答 `docs/re/50` §4 掛著的矛盾：
存檔 `+0xaf`（地城用的規模基準）是 1，會擲出等級 0 而讓型別重擲轉不完 ——
**但商隊只在戶外發生，戶外的基準來自地圖記錄**，那條退化路徑走不到。
（編號剛好是 9 的那一張圖是唯一的縫，留著。）

---

## 3. 隨機戰鬥掛在別的碼上

挑怪那一支 `222f:2a5b`（`internal/game/encounter.go` 實作的那個）
是分派表的 **`case 0x16`**。它的觸發在 `0x16aee`：

```
16aee  if 隊伍[+0x9c] != 0 → 不觸發
16af6  回傳 0x16
```

**是倒數計時器歸零，不是機率。** `+0x9c` 的動作：

| 位置 | 做什麼 |
|---|---|
| `0x17157` | `dec` |
| `0x189ad` | `= 1` |
| `0x189ce` | `= 10`（`ds:0x52d4 != 0` 且 `隊伍[+0xa3] < 9`，也就是地城裡的抑制）|
| `0xe1b4`／`0x10700`／`0x14934`／`0x19eb7` | 從別處寫入（沒讀）|

**重設規則沒解**，所以「打完一場之後隔多久才會再遇到」還算不出來。

---

## 4. 本專案照著錯的那個實作了

`cmd/demonwinter` 的 `checkRandomEncounter` 拿 `EncounterTriggered`
（就是那道 1/64）去開戰鬥。訊號本身抄對了，**接錯了地方**。

改法：

- 1/64 → `checkMerchantEncounter`，開商隊。這條是驗證過的。
- 隨機戰鬥保留，但在程式碼裡標明**那是替身** —— 真正的觸發是
  `+0x9c` 倒數，重設規則未解。不接的話野外完全不會打架，
  比接一個標著「這是替身」的機率更失真。

`M` 鍵留著：現在它是「不想走到 1/64 也能叫出畫面」的偵錯捷徑，
不再是「代替沒解的觸發」。

---

## 5. 為什麼會錯

`docs/re/04` 的三個事實（訊號存在、1/64、閘門條件）**全部正確**，
錯的只有最後那一步推論：「這是隨機遭遇戰鬥」。

推論的來源看得出來 —— 一個「每走一步小機率觸發、不經過事件表」的訊號，
在 CRPG 裡幾乎一定是隨機遭遇。**先驗太強，就不會去確認 case 編號。**
而確認 case 編號要先找到分派表，分派表當時被判在
「decompiler 弄壞的那段」裡面，於是就停在推論上了。

兩層教訓：

1. **「decompiler 弄壞了」不等於「讀不到」。** 這次是掃
   `jmp word ptr cs:[bx+d16]` 的指令碼直接找到跳表 —— 反編譯器認不出
   switch，不代表機器碼裡沒有一張攤開來的表。
2. **越像常識的推論越要標成推論。** `docs/re/04` 有誠實寫「沒有追完整」，
   但那句話講的是「怎麼接到 `FUN_17c5_000d`」——
   已經預設了它會接到戰鬥。**未解的是連接，不是目的地**，
   這種寫法會讓下一輪的人（就是我）把目的地當成已知。
