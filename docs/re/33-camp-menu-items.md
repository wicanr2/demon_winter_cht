# 33 — 紮營選單的 14 項與道具管理

`docs/re/26` 把紮營選單認成「13 個選項」，還警告過「選單顯示順序 ≠ 跳表索引順序」。
**兩件事都要訂正。** 選單是 **14 項**，而且顯示順序與跳表索引**完全一致** ——
當初的錯亂只是因為漏看了排在最前面的那一項。

---

## 1. 選單長什麼樣（`ds:0x94` 三張平行表）

主迴圈（`1000:007d`）把三個遠指標交給選單常式 `0x1cdc:0x33d`：

```
1000:0080  push 2                     ; 模式 2 = 等玩家選
1000:0084  push ds:0xcc               ; 快捷鍵字串
1000:0089  push ds:0xda               ; 每一項的可選旗標
1000:008e  push ds:0x94               ; 項目名稱的遠指標表
1000:0090  lcall 1cdc:033d
1000:009b  回傳 0xffff → 重問
1000:00a1  ax → 0x1000:01e3 的跳表
```

三張表都是 **14 項**，長度自己就對得起來：`ds:0x94` 是 14 個遠指標（56 bytes，
剛好在 `0xcc` 前結束）、`ds:0xcc` 是 14 個字元、`ds:0xda` 是 14 個 word（全 1）。

| # | 名稱 | 鍵 | 處理常式 |
|---|---|---|---|
| 0 | **Party** | `P` | `1000:33e8`（見 `docs/re/40`）|
| 1 | **Reorder** | `R` | `1000:0379`（見 `docs/re/34`）|
| 2 | **Sleep** | `S` | `1000:0206` |
| 3 | **Identify** | `I` | `1000:1e46`（見 `docs/re/37`）|
| 4 | Worship | `W` | `1000:0ed0`（規則見 `docs/re/42` §4，缺一張表）|
| 5 | **Xorcise** | `X` | `1000:1959`（見 `docs/re/41`）|
| 6 | **View land** | `V` | `1000:097b`（見 `docs/re/38`）|
| 7 | **Trade** | `T` | `1000:05a6` |
| 8 | **Drop** | `D` | `1000:20e9` |
| 9 | Equip | `E` | `1000:24ad` |
| 10 | **Use** | `U` | `1000:2262`（見 `docs/re/39`）|
| 11 | **Hunt** | `H` | `1000:07f0` |
| 12 | **Cast** | `C` | `1000:293d`（見 `docs/re/42`）|
| 13 | Quit | `Q` | `1000:0187` |

粗體是本專案已實作的。

> **`docs/re/26` 的兩處錯**：（一）選單是 14 項不是 13 —— 漏掉了 `Party`，
> 那一項的字串 `ds:0xf8` 排在 `Reorder`（`0xfe`）與 `Sleep`（`0x106`）前面，
> 只從 `0x106` 開始讀字串就會少一項。（二）「顯示順序 ≠ 跳表索引」是誤判 ——
> 補上 `Party` 之後兩者一一對應，連快捷鍵 `PRSIWXVTDEUHCQ` 都同一個順序。
>
> 只讀字串區、沒讀指標表，就會少一項並得出「順序對不上」的結論。
> 表格類資料要從**用它的那段程式**回頭讀，不能從資料區猜邊界
> —— 這正是 `rulebook/62`「找讀取端」。

`Quit`（case 13）不只是離開：它先檢查時辰是否為 24，是的話印
`"You are sleepy"`（`ds:0x15e`）才走人。`docs/re/26` §2 末尾提到的
`1000:018b` 就在這裡，那不是獨立的一支，是 Quit 的一部分。

## 2. 兩個共用的子常式

| 位址 | 做什麼 | 取消時回傳 |
|---|---|---|
| `1000:053c(0)` | 選一名隊員 | **隊伍人數**（`party+0x9a`），即越界值 |
| `0x7c5:151d(誰, 2, 模式)` | 模式 0 畫道具欄、模式 2 選一格 | **10**（10 格的越界值） |

兩者都用「回傳越界值」當取消訊號 —— 不需要另一個旗標，也不會與合法值撞號。

道具槽的位址算式在每一支裡都重算一次：

```
槽位址 = [0x4c7e:0x4c80] + 角色×0x104 + 槽×0x11 + 0x0c
```

`0x104` = 260 bytes 一名角色、`0x11` = 17 bytes 一格、`0x0c` = 道具欄在角色記錄
裡的起點。三個常數與 `internal/assets/scenario/save.go` 已有的定義一致。

## 3. Drop（`1000:20e9`）

四道關卡，順序照原版：

```
2191  型別 > 0xfd            → "Dungeon items cannot" / "be dropped in camp"
21c4  槽 == char[+0x101]     → "That item is equipped!"        ; 護甲
21d0  槽 == char[+0x100]     → 同上                             ; 武器
21f2  型別 == 0x1c           → "I don't think you" / "want to do that!"
21f8  型別 == 0x1d 且 party[+0xc1] == 0 → 同上
222e  槽[+0x00] = 0xff       ; 只改型別，其餘 16 bytes 不動
```

**型別 0xfe 是地城道具。** 判定寫成 `> 0xfd` 而不是 `== 0xfe`，所以空格（`0xff`）
也會撞上同一句「地城道具不能在營地丟」。這是原版的隨手複用，不是設計 ——
本專案把兩者分開講，對空格說「這一格是空的」。

型別 0x1d 的門檻 `party+0xc1` 是 trailer 的**最後一個 byte**，語意未解，
起始存檔是 0（所以那一型現在丟不掉）。它的唯一已知讀取端就是這裡。

「只改型別、不清其餘 bytes」不是偷懶，是**可觀察的原版行為** ——
`docs/re/25` 早就記過起始存檔裡 Wopple 清空的那一格留著前一件的殘值 `2`。
兩邊對得上。

## 4. Trade（`1000:05a6`）

```
05b1  giver = 選人；取消 → 離開
05f5  印 "Trade item:"，選一格
0628  槽 == 武器槽 或 護甲槽 → 印 "That item is equipped"，**回到選道具**
06d4  saved = giver[+0x102]      ; 暫存戰鬥狀態
06de  giver[+0x102] = 6          ; 讓自己在選人清單裡不可選
06f0  0x990:179b(0, 5, 1)        ; 畫選人清單
0709  giver[+0x102] = saved      ; 還原
071a  receiver = 0x990:179b(2, 5, 1)
0725  receiver == 隊伍人數 → 取消
0765  for i := 0..9: 找 receiver 第一個 型別 == 0xff 的格
0777    複製整整 17 bytes 過去
0794    來源槽[+0x00] = 0xff
07a8  沒有空格 → sprintf("%s is full", receiver 的名字)
```

與 Drop 的三個差別，每一個都不是細節：

| | Drop | Trade |
|---|---|---|
| 撞到裝備中 | 結束 | **退回選道具再問一次** |
| 地城道具 | 擋 | **完全不檢查，給得出去** |
| 沒地方放 | — | `"%s is full"`，道具留在原處 |

**「把自己的戰鬥狀態暫時改成 6」是這一段最有意思的一手。** 選人清單本來就會
依狀態過濾，與其為 Trade 寫一個「排除某人」的參數，不如借用既有的過濾規則，
選完再改回來。1980 年代省程式碼的典型作法 —— 也順帶告訴我們**狀態 6 是
「不可選取」**。

找空格用的是 `== 0xff` 而不是 `> 0xfd`，所以 **0xfe 確實不是空格**，
是一個真的型別值。這獨立支持了 §3 對「地城道具 = 0xfe」的判讀。

## 5. 本專案的實作範圍

- `internal/game/camp.go`：`DropItem`／`GiveItem`／`ItemTypeDungeon`
- `internal/assets/scenario`：`SaveGame.UnknownC1`（trailer `+0xc1`）雙向
- `cmd/demonwinter/campitems.go`：紮營選單的 `D` 丟棄、`T` 交給隊友

實機驗收（`workplace/dump/persist/42`–`46`）：
Wopple 的匕首是裝備中的武器，Drop 與 Trade 都在**選道具那一步**就擋下來；
把小斧交給 Stumpy 之後存檔，與原版 `PARTY.DAT` 逐 byte 比對只差四個 byte：

| 位址 | 變化 | 意義 |
|---|---|---|
| char0 slot0 `+0x00` | `01 → ff` | 來源清空（其餘 16 bytes 原封不動）|
| char1 slot1 `+0x00` | `ff → 01` | 收方收下 |
| char1 slot1 `+0x0e` | `00 → 0a` | 附魔 0 的儲存值是 `0+10` |
| char1 slot1 `+0x0f` | `00 → 01` | 新造一格填 1（`docs/re/25` 記過的觀察）|

後兩個是本專案「重建整格」與原版「複製整格」的差異。值本身與原版一致
（來源那一格的 `+0x0e`/`+0x0f` 就是 `0a`/`01`），所以結果相同，
但成因不同 —— 如果哪天遇到來源 `+0x0f != 1` 的道具，兩邊就會分岔。

**沒實作**：Worship（規則已讀完，缺 `[0x4cc4]` 那張「神祇 → 法術」表）
（入口位址都在 §1 的表裡，規則沒讀）。
