# 61 — 結局函式找到了：`0000:xxxx` 不是「靜態看不到」

`docs/re/50` 說動作 `0x0e` 是「重定位補的遠呼叫，目標由載入器填，**靜態看不到**」。
`docs/re/60` §2 對 `call 0000:3575` 照抄了同一句。

**兩處都錯。** 這一篇推翻它，並用同一個方法確認了結局函式。

---

## 1. segment 欄是 0，但 offset 是真的

找 UNCURSE 選單的呼叫端時，掃 `9a <off16> <seg16>` 撞到一件事：
呼叫它的三處全都是 `9a 53 2a 00 00` —— **segment 欄就是 `0000`**。

```
06623  9a 53 2a 00 00     call 0000:2a53
0b693  9a 53 2a 00 00     call 0000:2a53
0fb43  9a 53 2a 00 00     call 0000:2a53
```

而被呼叫的函式入口在 `0x6653` ＝ `1000:2a53`。**offset 完全對得上。**

原因很單純：**同一個 segment 內的 far call，連結器把 segment 欄留給重定位表填**，
但 offset 在連結期就定死了。所以「`0000:` ⇒ 目標未知」是誤解 ——
**用 offset 反查就找得到**，只要試幾個已知 segment 看哪個落在函式開頭。

> 這正是 `rulebook/62` 講的「別太早退回『看不出來』」。
> 「重定位」聽起來像 thought-terminating cliché，點破它就繼續追。

---

## 2. `0000:3575` ＝ 結局

`docs/re/60` §2：IMPRISON 成功後 `6c2b call 0000:3575`。
拿 offset `0x3575` 對各已知 segment 試：

| 候選 | 檔案位移 | 前 4 bytes | |
|---|---|---|---|
| `1000:3575` | `0x07175` | `55 8b ec 81` | **★ 函式開頭** |
| `122f:3575` | `0x09465` | `61 13 9f 0d` | |
| `15be:3575` | `0x0cd55` | `74 03 e9 4b` | |
| `1cdc:3575` | `0x13f35` | `8b 46 06 f7` | |
| `25be:3575` | `0x1cd55` | `04 eb 65 c4` | |
| `222f:3575` | `0x19465` | `26 50 9a 61` | |

**只有一個命中**，而且與呼叫端同段（`1000`）—— 與 §1 的模式一致。

`0x07175`（853 bytes）裡的字串：

```
ds:0x066a  CONGRATULATIONS! You have won Demon's Winter.
           I hope you have enjoyed your adventure.
0x7321     %s followed in the footsteps of %s
0x73c4     %s %s
```

**這就是破關畫面。** `docs/re/60` §5 把「那是結局」列為推論 —— 現在是事實。

## 3. UNCURSE／IMPRISON 是施法選單的條件性替換

`1000:2a53` 不是主線專屬的函式，是**通用施法選單**。三個呼叫端各帶一個模式參數：

| 呼叫端 | 模式 | 提示字 |
|---|---|---|
| `0x6623` | 0 | `Cast what spell:` |
| `0xb693` | 1 | `Which spell do you wish to cast ?` |
| `0xfb43` | 2 | `Enter desired spell: ` |

在某個條件下，這支選單列的不是 43 筆法術，而是：

```
6a14  "UNCURSE "      ┐
6a1f  "IMPRISON"      ├ 選項文字
6a2a  "EXIT"          ┘
6a35  mov [bp-0x37],'U' / 'I' / 'E'    ← 熱鍵
6a41  11 個槽初始化為 0xfffe
```

所以 `docs/re/60` §1 說它們「走自己的選單」**方向對但不精確**：
它們走的是**同一支施法選單的另一組選項**，不是另一個函式。

## 4. 破關路徑（完全閉合）

```
① 三個緋紅符印                       docs/re/59
   子地圖 55／56／66，站上 tile 0x63
   施法選單選 U（UNCURSE，50 SP）
   → party[+0x96 + (子地圖−55)] = 0x80

② 光之環的門                         docs/re/59 §3
   三個旗標都非 0 才放行

③ 禁錮                               docs/re/60 §2
   子地圖 5（地城）或 Y ≤ 6
   施法選單選 I（IMPRISON，100 SP）
   → call 0000:3575

④ 結局                               本篇 §2
   "CONGRATULATIONS! You have won Demon's Winter."
```

**四段全部有反組譯依據，①② 另有攻略獨立佐證。**
這是本專案第一次有一條從第一步到破關畫面的完整鏈。

| 項目 | 說明 |

| **切換條件** | 什麼時候施法選單會變成 U/I/E？不是近跳進 `0x6a14` 的（掃過 `0x6300`–`0x6a14` 的 `e9`/`eb`/`jcc` 全部沒命中），可能來自跳表或更遠的 `jmp` |
| `FUN_222f_0619` | 符印的傷害實作（325 bytes）|

| `EREGORE.TXT`／`T2C.TXT`／`T.TXT` | 其餘劇情文字的時機 |

`WIN.TXT` 的**載入點**仍未定位，但已不影響結論 ——
結局文字是**寫死在 `DEMON.INT` 的資料段**（`ds:0x066a`），不是從 `WIN.TXT` 讀的。
那四個 `.TXT` 是另一回事。

## 6. 方法

這一輪推翻的兩處斷言，根因是同一個：**把「連結期留白」讀成「執行期才知道」**。

檢查法很便宜：拿 offset 對各已知 segment 算檔案位移，看哪個落在
`55 8b ec`（Turbo C 的函式序言）。八個候選裡通常只有一個命中，
再用「與呼叫端同段」交叉確認。

一併記進 `tools/xref.py` 的使用慣例：遇到 `9a xx xx 00 00`，
不要當成未知，直接用 offset 反查。
