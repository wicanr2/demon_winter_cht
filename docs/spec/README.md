# 規格層（Spec）— SDD 工作方式

這個目錄放**引擎實作的唯一依據**。原則很簡單：

> **spec 齊了才動手，不邊做邊挖。**

反組譯文件（`docs/re/`）記錄的是「我們怎麼查出來的」——含探索過程、排除掉的假設、
卡住的地方。那些對追溯很重要，但不適合當實作依據：篇幅長、混雜未驗證的推測、
而且同一個機制的資訊散在好幾份文件裡。

規格（`docs/spec/`）記錄的是「要實作成什麼」——把已驗證的結論收攏成單一來源、
寫到可以直接轉成程式碼的精確度，並且**明確標出哪些部分還不能實作**。

---

## 為什麼堅持先寫規格

這個專案有 ground truth（原版遊戲），而有 ground truth 的專案最容易踩的坑是：
沿著「編譯過、測試綠、子系統完成」這些**內部訊號**一路推進，越推越自洽，
但跟原版的距離不一定縮短。等到真的跑起來才發現整層流程驅動缺席，
「能通關」是 debug 捷徑串出來的假象。

規格層就是防這件事的閘門。一個機制要能進 `docs/spec/`，必須先回答：

1. 原版的實際行為是什麼？（反組譯證據，或 DOSBox 實測）
2. 邊界條件呢？（0、負數、上限、溢位、空集合）
3. 怎麼驗收？（拿什麼跟原版對拍）

答不出來的，就還不能實作——那是 `docs/re/` 待辦，不是 `docs/spec/` 條目。

---

## 規格的分級

每個規格條目都要標明成熟度。**只有 `READY` 的部分可以動手實作。**

| 等級 | 意義 | 能否實作 |
|---|---|---|
| `READY` | 行為、公式、邊界條件、驗收方式都明確，有反組譯或實測證據 | ✅ 可以 |
| `DRAFT` | 主要行為清楚，但邊界條件或部分數值待確認 | ⚠️ 需先補齊缺口 |
| `BLOCKED` | 有已知的未解問題擋著，強行實作等於猜 | ❌ 不可以 |

**不准為了讓規格看起來完整而把 `DRAFT` 寫成 `READY`。** 留白比錯誤的確定性有價值——
一條被當成已驗證的錯誤公式，會造成日後極難追查的行為偏差。

---

## 每份規格的固定結構

```markdown
# <機制名稱>

> 狀態：READY / DRAFT / BLOCKED
> 證據來源：docs/re/NN 的哪一節、哪些函式位址
> 最後複核：YYYY-MM-DD

## 行為
（原版實際怎麼運作，用中性敘述，不用組合語言術語）

## 資料
（用到哪些資料檔、哪些欄位，指向 docs/formats/）

## 演算法
（可直接轉成程式碼的精確描述：公式、順序、條件分支）

## 邊界條件
（0、負數、上限、溢位、空集合、同時觸發…）

## 驗收
（拿什麼跟原版對拍：DOSBox 實測步驟、預期數值、截圖比對點）

## 未解 / 風險
（明確列出，沒有就寫「無」）
```

## 工作循環

```
反組譯（docs/re/）→ 收攏成規格（docs/spec/）→ 實作 → 對原版驗收
       ↑                                                    │
       └──────────── 驗收發現落差就回頭補 ←──────────────────┘
```

每一輪結束都要做的事：

1. 更新受影響的 markdown
2. **重新檢視既有斷言，清掉被推翻的**（不是加註解就算，要讓讀者不會被舊結論誤導）
3. commit + push

第 2 點特別重要。這個專案已經推翻過自己好幾次結論了：
`EXITS.DAT` 的記錄長度、`FILES.DAT` 的用途、`TEMPLAT*.DAT` 的角色、
`SUM.MAP` 的游標方向、3.5 倍規律的適用範圍。
每一次推翻，舊斷言若留在文件裡，就是下一個人踩坑的陷阱。

---

## 驗收的優先序

沿用專案既有規則，由高到低：

1. **人親自實測原版**
2. **DOSBox 原版實跑**（`tools/dosbox_run.sh`）
3. 官方手冊 / 社群攻略（`docs/manual/`、`docs/walkthrough/`）
4. 反組譯推論

低層級的結論**不能推翻高層級**。反組譯看起來再合理，
被原版實跑打臉就是反組譯錯了。
