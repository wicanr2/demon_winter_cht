# 亂數產生器（RNG）

> 狀態：**READY**
> 證據來源：`docs/re/06-combat-system.md` §RNG；反組譯 `30c2:0006`、`1d9f:0e0b`
> 最後複核：2026-07-25（協調者以指令級與整數算術雙重驗證）

這是整個引擎「行為對齊原版」的基石。戰鬥命中、傷害骰、隨機遭遇、升級成長
全部依賴它；序列不一致的話，其他部分再正確也對不上原版。

---

## 行為

原版使用一個線性同餘產生器（LCG）。狀態是一個 32 位元整數，
存在 real mode 記憶體 `0x481C`（低字）與 `0x481E`（高字）。

每次取亂數時，狀態先自我推進一步，再由推進後的狀態換算出所需範圍的整數。

遊戲中所有的擲骰都經由同一個頂層函式 `FUN_1d9f_0e0b`（`1d9f:0e0b`，全域 234 處呼叫），
語意是「擲一個 n 面骰，回傳 1 到 n」。

---

## 資料

不讀任何資料檔。種子來自 DOS 系統時鐘（`INT 21h, AH=2Ch`，`FUN_2f46_000a`）。

> 重現時應改用**可指定的固定種子**，否則無法與原版對拍。
> 原版的時鐘種子只影響「每局不同」，不影響演算法本身。

## 演算法

### 狀態推進

```
state ← (state × 125) mod 2796203
```

- 乘數 `125`（原版立即數 `0x7D`）
- 模數 `2796203`（原版 `0x2AAAAB`），是 Wagstaff 質數 (2²³+1)/3
- 狀態值域 `[1, 2796202]`

原版用兩次 16 位元 `MUL` 湊出 32 位元乘法，再用 `SUB`/`SBB` 做 32 位元借位減法：

```asm
30c2:000f  MOV BX,0x7d      ; 乘數 125
30c2:0012  MUL BX           ; 低字 × 125
30c2:0017  MUL BX           ; 高字 × 125
30c2:0029  MOV CX,0xaaab    ; 模數低位
30c2:002c  MOV BX,0x2a      ; 模數高位 → 0x2AAAAB
30c2:004a  SUB word ptr [0x481c],AX
30c2:004e  SBB word ptr [0x481e],DX
```

因為 `state < 2796203 < 2²²`，乘 125 後小於 2²⁹，用 64 位元中介運算不會溢位，
結果與原版逐位元相同。

### 擲骰 `Roll(n)`

```
若 n < 0        → n ← -n
若 n = 0 或 1   → 回傳 1（且不推進狀態）
否則            → 回傳 floor(next_state × n / 2796203) + 1
```

回傳值域 `[1, n]`。

> **原版此處走自製軟體浮點函式庫**（段 `310e`），不是硬體 x87。
> （PLAN V7 已確認全檔只有 6 筆真 x87 指令，全在啟動期 runtime 樣板。）
>
> **原版是「先除後乘」**：LCG 狀態推進函式 `FUN_30c2_0006` 做完整數模運算後，
> 結尾立刻呼叫浮點除法把新狀態除以 `2796203.0`；`Roll(n)` 拿到的已經是小數，
> 再乘 `n`、截斷。而本規格的整數實作是「先乘後除」。
>
> **兩者等價性已證明（2026-07-25），不再是假設** —— 見下方「等價性證明」。

---

### 等價性證明（原版浮點路徑 vs 本規格整數路徑）

原版：`floor( (state / 2796203.0) × n ) + 1`（先除後乘，走軟體浮點）
本規格：`floor( state × n / 2796203 ) + 1`（先乘後除，純整數）

兩者在有理數上恆等，問題只在**浮點捨入會不會讓 `floor()` 跨過整數邊界**。不會，理由：

1. **模數 2796203 是質數**（Wagstaff 質數 (2²³+1)/3，已用試除法重驗）。
2. `state` 恆非 0，且遊戲用到的 `n` 都遠小於模數
   → `state × n` **絕不會恰為模數的倍數** → 精確商的小數部分永不為 0。
3. 因此小數部分與整數邊界至少相差 `1 / 2796203`，即約 **2⁻²¹·⁴** 的相對邊界。
4. 原版用的是 **IEEE double（53 bit 有效位）**，不是我原先誤寫的 80 位元擴充精度。
   判定依據：除數常數在 binary 中的原始位元組是 `00 00 00 80 55 55 45 41`，
   以 IEEE double 解讀正好是 `2796203.0`，且該樣式**全檔只出現一次**
   （file offset `0x248B2`）；浮點打包/解包格式的位元配置也是 `1+11+52`。
5. **53 bit 精度 ≫ 21.4 bit 邊界**，捨入誤差不可能跨越 `floor()` 邊界。

另已用程式窮舉 **33,554,424 組 `(state, n)`**（13 個 n × 2,796,202 個 state）確認：
`state × n ≡ 0 (mod 2796203)` 出現 **0 次**，全域最小 margin 恰為 **1**。

截斷而非四捨五入也已確認：float→int 的 `FUN_310e_07e2` 指令序列中
沒有任何「加半 ULP」的捨入邏輯，只有位元搬移。

完整推導見 `docs/re/14-rng-float-equivalence.md`，窮舉工具 `tools/rng_float_equiv_check.go`。

### 播種機制（已驗證）

- LCG 狀態的**編譯期初始值是常數 `100001`**（直接讀靜態資料段確認）。
- 程式啟動時 `main()`（`FUN_1d9f_0008`）讀系統時鐘取低 11 bit（0–2303），
  據此**重複推進 LCG 對應次數**，把系統時間**間接**注入起始狀態。
- 所以「種子來自系統時鐘」的說法成立，但機制是「用時鐘決定推進次數」，
  **不是把時鐘值直接寫入狀態**。
- `FUN_1d9f_0dda` 在時鐘累加器為奇數時觸發，內容是「多推進一次 LCG +
  一段算完即丟的死值」，**不寫回任何全域種子** —— 不是傳統意義的重新播種。

重現時仍應改用可指定的固定種子，以便對拍。

## 邊界條件

| 情況 | 行為 |
|---|---|
| 種子為 0 | 必須正規化為非 0。狀態一旦變 0，LCG 永遠停在 0 |
| `n = 0` 或 `n = 1` | 回傳 1，**且不推進狀態**。這點很重要——推進了會讓後續序列偏移 |
| `n < 0` | 取絕對值後照常處理 |
| 狀態值域 | 恆為 `[1, Modulus−1]`，不會出現 0 或 ≥ 模數 |

## 驗收

1. **與原版算術逐步對拍**：實作一份模擬原版 16 位元 `MUL`/`SUB`/`SBB` 指令序列的
   參考函式，與正式實作跑 10 萬步比對，每一步都必須相同。
2. **狀態值域**：跑 100 萬步，狀態不得為 0 或 ≥ 模數。
3. **`Roll` 不消耗**：`Roll(0)` 與 `Roll(1)` 前後狀態必須相同。
4. **序列可重現**：相同種子必須產生相同序列。
5. **週期夠長**：10 萬步內狀態不得回到起點。

> 更強的驗收（尚未做）：與 DOSBox 原版對拍實際戰鬥結果。
> 需要能讀出原版的 `0x481C` 狀態或固定種子，屬後續工作。

## 未解 / 風險

**無阻塞項。** 這是目前證據等級最高的一塊：公式有指令級證據、
浮點等價性有數論證明 + 3,355 萬組窮舉、播種機制已追出、實作 8 項測試全綠。

殘留的次要不確定性（都不影響實作）：

- 8-byte 緊湊浮點格式的位元配置是結構推論（信心高，未做逐位元窮舉核對）。
  但這不影響結論 —— 等價性證明只需要「精度 ≥ 22 bit」這個下界，
  而 IEEE double 的 53 bit 有極大餘裕。
- `FUN_310e_0010` / `007a` / `0092` 這組單精度轉換函式的呼叫端未追到，
  與 `Roll()` 路徑無關。
- 未做 DOSBox 動態單步交叉核對。判斷不必要：數論證明本身已完備，
  且現有 DOSBox 環境是互動式鍵盤自動化，沒有「批次呼叫任意函式」的能力，
  建置成本高於數論路徑的價值。
