## 行為

世界地圖與地城都是 64×64 的方格。隊伍有座標與**面向**（四方向）。
按方向鍵會先轉向再前進；`Walk` 指令沿目前面向前進。

移動的每一步都可能推進遊戲時間、觸發隨機遭遇、或踏上會觸發事件的格子。

---

## 資料

| 位址 | 內容 | 說明 |
|---|---|---|
| `struct(0x4c76)+0xa1` / `+0xa2` | 隊伍 X / Y | 進入移動函式時刷新到全域 |
| `struct+0xa4` | 面向 | 刷新到 `0x4e32` |
| `struct+0xa0` | **步數計數器** | 每步 +1（某些 tile +2），達 11 時小時 +1 |
| `0x2107` | 面向 → 線性位移表 | `−64, 1, 64, −1` |
| `0x15da` | 面向 → ΔX 表 | `0, 1, 0, −1` |
| `0x15d2` | 面向 → ΔY 表 | `−1, 0, 1, 0` |
| `0x5500` | 遠指標 → **可通行性對照表** | **`FILES.DAT` offset `0x040`**，有效範圍 tile 0–100 |
| `0x4c94` | 遠指標 → 當前地圖 tile 陣列 | 64×64，索引 `y*0x40 + x` |

### 面向編碼

| 值 | 方向 | ΔX | ΔY |
|---|---|---|---|
| 0 | 北 | 0 | −1 |
| 1 | 東 | +1 | 0 |
| 2 | 南 | 0 | +1 |
| 3 | 西 | −1 | 0 |

順時針。線性位移 `= ΔY × 64 + ΔX`，與 `0x2107` 表逐項吻合。

## 演算法

### 一步移動的完整順序

```
1. 從 struct 刷新 X / Y / 面向 / mode 到全域
2. 推進遊戲時間 → 若回傳非 0（例如隨機遭遇碼 0x17）→ 直接返回，本步中止
3. 繪製 viewport
4. 讀取玩家指令
5. 指令 0–3（方向鍵）→ 面向 = 指令值，續 6
   指令 4（Walk）    → 沿用目前面向，續 6
   其他指令          → 走各自的處理，不移動
6. 目標座標 = 目前座標 + (ΔX, ΔY)[面向]
7. 目標 tile = 地圖[目標Y × 64 + 目標X]
8. 查可通行性表 [0x5500][目標 tile]
      不可通行 → 撞牆訊息，座標不變
      可通行   → 座標更新為目標座標
9. 若 目標 tile ∈ {0x0e, 0x2b} → 先執行一次「步進」
   無條件再執行一次「步進」
10. 依目標 tile 值判斷是否觸發事件（見 `03-events.md`）
```

### 步進（`FUN_222f_05c6`）

```
步數計數器 += 1
若 步數計數器 < 11 → 結束，回傳 0

飢餓／中毒判定
若 判定回報隊伍全滅 → 回傳該碼；計數器不重設、小時不推進
否則:
    步數計數器 = 1          ← 歸 1，不是歸 0
    小時 += 1
    執行時／日／月三層進位（見 06-time.md）
```

> **兩個容易寫錯的點：**
>
> 1. **計數器歸 `1` 不是 `0`。** 下一輪從 1 起算，所以「滿 11 步推進一小時」
>    之後的每一輪其實只要再走 10 步。指令級證據見 `docs/re/08` §8。
> 2. **困難地形是「呼叫兩次步進」，不是「一次加 2」。** 兩者在跨越 11 門檻時
>    行為不同 —— 呼叫兩次會各自檢查門檻，可能先推進小時、再從 1 數起第二步。
>    寫成 `+= 2` 會漏掉中間那次檢查。
>
> 會多算一步的 tile 是 **`0x0e`／`0x2b`** 兩個值（`docs/re/08` §6.4）。
>
> **這兩個是山丘**：把 `DEMON.SHP` 的第 14 與第 43 塊畫出來，兩者都是
> 「起伏的等高線 + 零星植被」——山丘的典型俯視畫法，彼此是同一種地形的兩個變體，
> 與 96–98 的尖角山脈明顯不同；`WINTER.SHP` 的對應圖塊是它們的雪地版。
> 手冊 p.20 也寫山丘「穿過本地形所花費的時間可能是一般地形的兩倍」。
> 圖形、手冊敘述、程式機制三方一致。
>
> 嚴格說這是「圖形辨識 + 手冊敘述」的推定，不是指令級證明
> （程式碼裡沒有「山丘」這個名字），但三方獨立吻合，實作上照 tile 值做即可。

### 可通行性

**不要硬寫死 tile 值。** 原版查的是 `[0x5500]` 指向的對照表，以 tile 值為索引。

```
tile = 地圖[y × 64 + x] & 0x7f          ← 先遮罩
可通行性 = 表[tile]
```

表在 **`FILES.DAT` offset `0x040`**，有效範圍 tile `0`–`100`（101 項）。
內容見 `docs/re/22` §2。

**判定依所在圖層而不同**：

```
深度(0x52d4) == 0（大地圖）:
    表[tile] == 0xff → 撞牆，座標不變，移動結果碼 0xfffe
    否則              → 可通行

深度 > 0（子地圖／城鎮內）:
    表[tile] == 0xff → 撞牆；但 tile 0x14 與 0x62 例外，可以走
    表[tile] != 0xff → 踏出子地圖 → 深度 −1，從歷史堆疊還原座標與面向
```

> 子地圖的邏輯看似反直覺，但機制是合理的：城鎮／建築疊在大地圖上，
> 子地圖自己的圖塊都屬 `0xff` 類，其中 `0x14`／`0x62` 是可走的街道。
> 一旦踏到不屬於子地圖圖塊集的一般地形，就自動退回上一層。
> 這也是**子地圖唯一的退出方式**。

### 子地圖／城鎮進出

**進入**：一張 10 筆的「入口對照表」，每筆含座標、dataset 差值、面向。
玩家新座標命中某筆入口 → 深度 `0x52d4` 加一，
並把舊的座標／dataset／面向壓進 6 bytes/層的歷史堆疊
（`struct+0x22`..`+0x26`，以深度值當堆疊指標）。

**退出**：見上方可通行性判定 —— 在子地圖內走到表值非 `0xff` 的 tile 即彈出一層。

## 邊界條件

| 情況 | 行為 |
|---|---|
| 目標座標超出 64×64 | **未確認**是否有邊界檢查，或靠可通行性表擋住 |
| 方向鍵按向已面對的方向 | 仍會執行完整移動流程（轉向是無操作）|
| 時間推進回傳非 0 | 本步**不移動**，直接返回（隨機遭遇會吃掉這一步）|
| 步數計數器 | 達 11 進位，不是 10 —— 這個數字要照抄。重設值是 **1 不是 0** |
| 困難地形（`0x0e`／`0x2b`）| 呼叫**兩次**步進，不是一次 +2 |
| 飢餓判定回報全滅 | 該次步進不重設計數器、不推進小時，直接把碼往上回傳 |

## Remake 操作決策：現代絕對方向

原版底層的方向命令 `0–3` 會先把面向設為北／東／南／西，並在同一次命令中
執行完整移動流程；紙本介面則把它包成「左右相對轉向、`Return` 前進」。
Remake 的戶外與地城探索採用前一層語意：四個方向鍵代表**絕對方向並前進一格**。
這是已定案的現代操作，不是尚未確認的漂移。

- 方向鍵：轉向到該絕對方位並嘗試前進一格。
- 撞牆時仍完成轉向，位置不變。
- 背後攻擊仍依移動後保存的實際面向計算，規則沒有刪除。
- 海戰不套用這項簡化；左右轉舵與直行仍分開，保留原版轉向點數成本。

這個決策減少鍵擊，但不宣稱與紙本鍵位逐鍵相同。原版／remake 的差異與理由
集中列在專案 `README.md` 的畫面與操作比較。

## 驗收

1. **面向位移表**：四個方向的 `(ΔX, ΔY)` 必須等於 `(0,−1) (1,0) (0,1) (−1,0)`，
   且 `ΔY×64 + ΔX` 等於 `−64, 1, 64, −1`。
2. **步數→時間**：從計數器 0 起連續走**一般地形** 11 步，小時恰好 +1、計數器回到 1；
   再走 10 步，小時再 +1。**第二輪是 10 步不是 11**——歸 1 造成的，寫錯歸 0 這條會紅。
3. **困難地形**：計數器為 10 時踏上 `0x0e`，結果是小時 +1 且計數器停在 **2**
   （第一次呼叫 → 11 達門檻 → 推進並歸 1；第二次呼叫 → 2）。
   若實作寫成一次 `+= 2`，會得到「計數器 12、只推進一次」或「計數器 1」，兩者都錯。
4. **與 DOSBox 原版對拍**（尚未做）：從已知座標往固定方向走 N 步，
   比對最終座標與時間。

## 未解 / 風險

| 項目 | 影響 |
|---|---|
| 可通行性表值 `0–7` / `253` / `254` 的細部語意 | 通行判定只看是否 `0xff`，這些值影響的是別的行為（`253` 另有單獨比對）。**不擋移動實作** |
| tile 值 ≥ 101 | 遮罩後理論範圍到 127，但表只有 101 項有效。原版靠「實際 tile 不超過 100」成立；實作時應視為未定義 |
| 64×64 的邊界處理 | 未確認是否有明確檢查 |
| 其餘六種地形的 tile 值 | 山丘（`0x0e`／`0x2b`）已認出，但平原／森林／沼澤／凍土／樹叢／沙漠分別對應哪些 tile 值尚未逐一對照。**不擋移動實作**（移動只看可通行性表），影響的是隨機遭遇表與地形敘述 |
| `0x210f` 玩家 glyph 動畫表 | 只確認用途是畫面渲染，內容未解讀。不影響移動邏輯 |
